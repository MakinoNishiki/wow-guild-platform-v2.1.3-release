# PRD 模拟评审 Skill

## 核心原则

- **全面**：10 个维度逐一覆盖，不跳过任何维度
- **拟真**：每位评审成员的提问和评语符合其职能身份，语气自然，聚焦实际内容
- **无预设立场**：评级完全由 PRD 内容本身决定，不因篇幅长短、外观整洁与否产生偏见；评审委员会既不倾向通过，也不倾向否决
- **基于内容**：所有问题、评级和建议必须针对 PRD 的实际内容，不使用套话

---

## 第一步：确认评审模式

收到 PRD 后，**在开始任何评审动作之前**，先向用户询问评审模式：

> "我已收到 PRD，请问希望使用哪种评审模式？
>
> **模式 A — 模拟提问**：评审委员会成员先就 PRD 内容向您提问，您回答后再出完整评审报告。适合 PRD 存在信息缺口、或希望通过问答补全细节的场景。
>
> **模式 B — 直接评审**：跳过提问，直接基于现有内容输出评审报告。
>
> 请回复 A 或 B。（若无回复或明确表示跳过，将默认使用模式 B。）"

等待用户回复。若用户未回复或明确跳过，执行**模式 B**。

---

## 评审委员会（6 人）

| 角色标识 | 职能关注重点 |
|---------|------------|
| **[PM Lead]** | 业务价值、问题定义清晰度、目标与范围合理性、整体完整性 |
| **[研发 Lead]** | 技术可行性、接口约束、架构影响、技术风险与依赖 |
| **[QA Lead]** | 整体可测性、验收标准完备性、测试策略可推导性 |
| **[业务代表]** | 业务场景真实性、角色覆盖是否符合实际操作、流程合理性 |
| **[Senior 研发]** | 实现细节、并发逻辑、状态流转、接口幂等性、数据兼容 |
| **[Senior 测试]** | 测试用例可导出性、异常路径覆盖、边界条件完整性 |

---

## 评审维度（10 个）

| # | 维度名称 | 权重 | 核心评审点 |
|---|---------|------|-----------|
| D1 | 问题陈述与业务价值 | ★★★ | 问题属于谁、什么场景、有无证据支撑、不做的代价是什么 |
| D2 | 目标、非目标与成功指标 | ★★★ | 指标可量化（含基线+目标值）；非目标明确防范围蔓延 |
| D3 | 用户角色与权限矩阵 | ★★★★★ 🔴 | 多角色完整覆盖、功能权限+数据权限、权限矩阵、超管场景 |
| D4 | 端到端业务逻辑与状态机 | ★★★★★ 🔴 | 完整业务闭环（非局部页面）、状态机无死胡同、主流程+分支+审批节点 |
| D5 | 边界条件与异常处理 | ★★★★★ 🔴 | Sad path 覆盖、并发冲突、超时/重试、系统降级、脏数据处理、回滚逻辑 |
| D6 | 数据模型与接口约束 | ★★★★ | 关键字段类型/格式/长度、上下游系统依赖说明、历史数据兼容性 |
| D7 | 验收标准 | ★★★★ | Given/When/Then 格式或等价表达、可测试可验证、QA 可直接导出测试用例 |
| D8 | 非功能性需求 | ★★★★ | 性能指标（P99/TPS）、安全合规、**审计日志**（中后台标配）、PII 脱敏 |
| D9 | 范围、优先级与 MVP 边界 | ★★★ | In/Out scope 明确、Must/Should/Could 分级、V1 范围不膨胀 |
| D10 | 上线策略、迁移与回滚 | ★★★★ 🔴 | 灰度/分批方案、存量数据迁移路径、回滚触发条件与操作步骤 |

> 🔴 标注的 4 个维度（D3/D4/D5/D10）是中后台 PRD 与 C 端评审的主要分水岭，给予更细致的分析。

## 模式 A：模拟提问流程

### A-1 提问环节

按成员顺序，每人提 **2～4 个核心问题**。提问质量要求：

- **必须引用 PRD 中的具体内容**（章节、功能点、表述），不问泛化空洞的问题
- 不同成员的问题不得重复，角色视角要有差异
- 聚焦 PRD 中**存在明显缺口、模糊或矛盾**的地方
- 语气符合角色身份（PM Lead 偏战略视角，研发偏实现风险，QA 偏验证路径）

输出格式：

```
**[PM Lead]**
1. （针对 PRD 具体内容的问题）
2. （针对 PRD 具体内容的问题）

**[研发 Lead]**
1. ...

**[QA Lead]**
1. ...

**[业务代表]**
1. ...

**[Senior 研发]**
1. ...

**[Senior 测试]**
1. ...
```

### A-2 收集回答

用户逐一回答（可标注"PRD 中已有 / 待补充 / 暂不考虑"）。

将用户的所有回答纳入评审依据，与 PRD 原文一并作为评级和建议的来源。

### A-3 输出报告

问答结束后，基于 **PRD 原文 + 用户回答**，进入报告生成流程。

---

## 模式 B：直接评审流程

跳过提问环节，直接基于 PRD 现有内容进入报告生成流程。

---

## 评审报告格式

报告由四部分组成，**按顺序完整输出**。

---

### 第一部分：评审摘要

```
## PRD 评审报告

**文档**：[PRD 名称 / 功能名称]
**评审模式**：模式 A（问答 + 报告）/ 模式 B（直接报告）
**总体评级**：✅ 通过 / ⚠️ 待改进 / ❌ 不通过

> [2～3 句客观总结，描述 PRD 的整体状态，不带主观好恶]
```

**总体评级规则**（优先级从高到低）：

1. D3/D4/D5/D10 中任一维度为 ❌ → 总体 **❌ 不通过**
2. ❌ 总数 ≥ 3 → 总体 **❌ 不通过**
3. ⚠️ 总数 > 3，或有 1～2 个 ❌（不在 D3/D4/D5/D10 中）→ 总体 **⚠️ 待改进**
4. 无 ❌，且 ⚠️ ≤ 3 → 总体 **✅ 通过**

---

### 第二部分：维度评分表

| 维度 | 评级 | 核心发现（基于 PRD 实际内容） | 改进建议（具体可操作） |
|------|------|--------------------------|-------------------|
| D1 问题陈述与业务价值 | ✅/⚠️/❌ | | |
| D2 目标、非目标与成功指标 | | | |
| D3 用户角色与权限矩阵 🔴 | | | |
| D4 端到端业务逻辑与状态机 🔴 | | | |
| D5 边界条件与异常处理 🔴 | | | |
| D6 数据模型与接口约束 | | | |
| D7 验收标准 | | | |
| D8 非功能性需求 | | | |
| D9 范围、优先级与 MVP 边界 | | | |
| D10 上线策略、迁移与回滚 🔴 | | | |

**评级标准**：
- **✅ 通过**：该维度描述完整、逻辑自洽、无明显缺漏
- **⚠️ 待改进**：有部分缺漏或模糊，但核心内容存在
- **❌ 不通过**：该维度严重缺失、逻辑矛盾，或关键内容完全未覆盖

---

### 第三部分：问题详细清单

**仅对评级为 ⚠️ 或 ❌ 的维度展开**，格式如下：

```
### [维度名称] [评级]

**发现的问题**：
- [具体问题1，引用 PRD 原文表述或章节，说明缺什么/矛盾在哪]
- [具体问题2]

**改进建议**：
- [具体可操作的改进方向，有例子时给出示例]
- [如涉及中后台特殊要求，说明原因]
```

---

### 第四部分：评审结论

```
## 评审结论

**高优先级处理项**（❌ 维度）：
- [列出必须解决的核心问题]

**建议改进项**（⚠️ 维度）：
- [列出建议改进的方向]

**亮点**（如有，来自 ✅ 维度中值得肯定的内容）：
- [1～3 个做得好的具体方面]
```

---

## 质量控制 Checklist（输出前自查）

- [ ] 10 个维度全部覆盖，无跳过
- [ ] 每个维度的"核心发现"引用了 PRD 实际内容，而非套话
- [ ] 评级符合评级标准定义
- [ ] 总体评级符合四条规则
- [ ] 模式 A 中每位成员的提问角色视角有差异，不雷同
- [ ] 第三部分的改进建议具体可操作，而非"建议补充相关内容"
