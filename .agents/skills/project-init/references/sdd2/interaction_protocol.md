# 分级授权交互协议

> **适用声明**：本协议是模型与厂商无关的治理内核。完整执行型运行时按全文执行；辅助执行型可用于判断和产出建议，但缺失的文件/工具动作转人工；对话参考型不承担项目状态或自动执行。定档见 `references/sdd2/runtime_compatibility.md`。

## 0. 第零原则

**吞吐优先于单次通过率**：长任务持续推进，人工验证后置到产物级，重做是可接受的纠错手段。

project owner 裁定依据（2026-07-27）：除非特别紧急、必须一次通过，否则更愿意让长任务持续进行、由本人验证不同产物的结果，以获得更直观、更接近一线的判断；即使因 R 层归类不准导致问题也可以接受——大不了重做一次。

- **适用边界**：声明"求一次过"的紧急任务除外（§8）。
- **裁定作用**：agent 遇到"要不要停下来问"的模糊情况时，按本原则**倾向继续推进**。注意与 §6.4"归类存疑从 A"不矛盾——前者管推进节奏（不轻易停），后者管归类判断（拿不准某决策归哪级时从严归 A）。

## 1. 四级授权总表

| 级 | 名称 | 机制 | project owner 的动作 | agent 的动作 |
|---|------|------|-------------|-------------|
| A | 事前裁定 | **阻塞停等**：批准前不推进 | 拍板 | 提案 + 停等；能攒批尽量攒批，一次交互只停一次 |
| R | 事后必审 | **不阻塞**：定稿后继续推进，产物挂"待过目" | 异步必审（可批量），异议即提 | 定稿 + 登记 task_registry「R 待审区」+ 继续推进 |
| B | 自决留痕 | 自决 + 自决清单 | 抽查（可不看，优先看低把握区） | 按判据自决，逐条记入自决清单 |
| C | 自决 | 无记录义务 | 无 | 直接执行 |

**提问纪律**：一次交互中上抛给 project owner 的问题只能是 A 类；R/B/C 层疑问按判据自行处理。

## 2. A 类判据（事前裁定）

满足任一即为 A。

**通用 Gate（全场景）**
1. 对外动作：发消息 / 邮件 / 对外发布 / 生产系统写入
2. 不可逆操作：删除、覆盖他人内容、push 冲突处置
3. 项目范围 / 优先级 / 定位变化
4. SDD 元规则变更
5. project owner 在任务定义时点名保留的事项

**PRD 场景细化（意图层 + 策略层）**

| 细目 | 包含 |
|------|------|
| 意图 | 为什么做 / 做到什么程度 / 不做什么、功能清单与优先级 |
| 业务流程 | 业务流走向、状态机（状态定义与迁移条件）、审批与单据流转链路 |
| 数据链路 | 数据来源与去向、系统间同步时机与方向、口径与计算规则、主数据归属 |
| 权限管控 | 角色定义、数据可见范围 |
| 接口语义 | 接口职责、触发时机、失败与幂等策略（字段明细除外 → B） |
| 逆向策略 | 异常处理的方向选择（如冲正 vs 红字、拦截 vs 放行） |
| 场景矩阵骨架 | 场景维度切分与场景取舍（project owner 裁定归 A；配套串讲机制见 §7） |
| 外部依赖 | 依赖外部团队 / 外部系统的事项（责任归属维度） |

**归类原理**（判据表未覆盖的新情况按此判断）：一个决策必须由人做，当且仅当满足以下任一——
① 决策所需关键信息只在 project owner / 组织侧（业务意图、组织现实），AI 从任何语料拿不到；
② 纠错成本高、下游扇出大（被 TRD / 代码 / 测试 / 外部系统继承越多越接近单向门）；
③ 需要人对外担责（承诺、合规、签字背书）；
④ 属 project owner 个人偏好且尚无规范兜底（应问一次后规范化，转为 B 类判据来源）。

## 3. R 类运作（事后必审）

**承接内容（结构层）**：接口划分与职责分配、页面划分、正向案例主干，以及其他"AI 定稿质量可靠、但 project owner 需要看见"的结构性产物。

**运作三则**：
1. **登记**：R 类产物定稿后，登记到 `task_registry.md` 对应任务节「R 待审区」（产物名 + 相对路径 + 定稿日期），agent 随即继续推进，不等待。
2. **异议处理**：project owner 过目后有异议 → agent 评估下游影响面（哪些后续自决建立在该产物上）并报告返工成本 → project owner 决定改法。返工是第零原则下可接受的成本。
3. **交付门槛**：**「R 待审区」全部过目清零，是任务最终交付 / 验收的门槛**。R 不阻塞过程，但阻塞收尾——保证"一定被看到"，防止 R 在忙碌时退化为 B。

## 4. B 类（自决留痕）

**承接内容（明细层）**：接口表 / 数据表字段明细、字段规格 7 属性、查询条件、页面字段布局、通用边界场景补全（空值 / 超长 / 重复提交类）、文案措辞。

**四判据（须同时满足）**：
1. 所属框架已经 A 类裁定（框架未裁定时，B 类不得先行）
2. 存在可引用的规范或先例
3. 改错成本低（双向门）
4. 不跨系统边界

**自决清单格式**（project owner 裁定 2026-07-27）：
- 每条两列：**决定 + 依据简述**。依据写"规范/先例说了什么"，**禁止编码跳转引用**（不写"见规范 §x.y"）——project owner 阅读当屏内容即可获得足够判断信息，无需反复跳转。
- **低把握项置顶加标 ❗**（agent 自评判断成分较大的条目），project owner 抽查优先看此区。
- 示例：
  > **❗低把握** ｜ 退款单列表默认排序取"申请时间倒序" ｜ 依据：现状三个单据列表页均为创建时间倒序，本页无明文规范，按同类页面惯例推定
  > 常规 ｜ "停用-手工停用"状态码取 9100 ｜ 依据：状态码规范——首位 9 为停用类，第二位 1 表示主动停用
- 位置：随产出物交付（产物文档尾部或任务节内），`task_registry.md` 任务节放指针。

## 5. C 类（自决）

纯格式排版、中间产物、检索路径、工具选择。无记录义务。

## 6. 漂移补偿机制（四道）

1. **任务基线**：任务定义阶段产出简短基线，字段：目标 / 范围内 / 范围外 / 不动项 / 场景与用户预期（串讲落点，§7）。基线经 project owner A 类裁定。此后一切自决以基线为参照；**任何自决触碰基线（范围外条目、不动项）= 自动升 A 停等**。
2. **漂移自检点**：长任务按自然段落（如 prd-write 簇间 reset 处）做基线对照自检：累积自决有无方向性偏移、有无互相矛盾。疑似偏移即上抛，不等交付。
3. **自决清单分级**：低把握项置顶（§4），把 project owner 有限的抽查注意力导向最需要的地方。
4. **升级触发条件**（满足任一，B 自动转 A）：
   - 自决之间出现冲突
   - 单任务自决数量异常膨胀（提示任务定义不清，应回头补基线）
   - 发现与既有文档矛盾（元指令 v2 #12 场景）
   - **无先例可循的新模式（novel）**
   - **归类存疑——拿不准归哪级，一律按 A 处理**

## 7. 串讲固化

project owner 对场景矩阵等 A 类内容做口头串讲（哪些人、在什么场景、预期如何使用功能）后：

1. agent **当场**将串讲内容整理成文字，写入任务基线「场景与用户预期」节；
2. 向 project owner 确认转述无误——**此确认即该项 A 类裁定完成；口头串讲不落文字 = 未完成裁定**（写进文档才算确认）；
3. 固化后的串讲内容成为后续 B 类自决与边界场景补全的判据来源；多任务并行时其他 agent 同样读取。

## 8. 紧急模式

任务定义时 project owner 声明**"本任务求一次过"** → 该任务的 R 层整体前置为 A（结构层产物也事前批准后再推进）。仅此一条变化，不新建模式体系。

## 9. 交互节奏（会话生命周期）

```
任务定义（1 轮）：对齐目标 + 产出任务基线（含点名保留项、是否紧急模式）→ A 类裁定
→ 连续推进：B/C 自决；R 定稿登记后继续；漂移自检点按段执行
→ A 类停等：攒批上抛，一次交互只停一次
→ 交付：R 待审区清零（门槛）+ 自决清单随产物提交（低把握置顶）→ project owner 验收
→ 归档：按元指令 v2 #13（步骤 0 保留）
```

**试行期反馈环**：project owner 抽查发现某类 B 自决频繁出错 → 该类判据收紧回 A。判据本身可调，不赌模型一次到位。
