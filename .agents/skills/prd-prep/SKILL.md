## 快速开始

本 Skill 引导 Agent 在正式写 PRD 之前，通过功能清单确认 + 结构化访谈，将功能需求转化为 prd_prep 文档，作为 `prd-write` 的直接输入。

**输入**：MRD 基线章节 + PRD 统一规范基线（如有）
**输出**：`prd_prep_{module}.md`，10 章结构，涵盖功能边界、场景矩阵、逐功能规格、外部依赖、非功能需求等。

```
上游（MRD / 设计共识）       本 Skill（prd-prep）                                  下游（prd-write）
  功能设计基线    →  grill 对齐 → 读取 → 清单确认 → 提问 → 确认  →  prd_prep_{module}.md
```

---

## 适用场景

- 多模块 PRD 管道中，进入 prd-write 前的前置阶段
- 功能清单含前端页面、后端任务、接口、配置等多种类型
- 需要产出标准格式 prd_prep 文档供后续 Agent 消费

**前提**：MRD 基线已存在且经过评审（或基本稳定）。

---

## 五阶段工作流

```
阶段 0            阶段 1          阶段 2           阶段 3                 阶段 4
需求对齐逼问  →  读取 MRD 基线 → 功能清单确认  →  结构化提问         →  输出 prd_prep 文档
     ↓               ↓              ↓                ↓                       ↓
grilling 逼问    功能清单提取    按类型列出建议    全局组 G1–G6           10章结构落地
关键决策/歧义    TBD 识别        用户确认范围      逐功能组 F1–F5         写入目标路径
共识后→阶段1     边界梳理        确认后进入阶段3   无更多问题→阶段4      prd-prep-status: completed
```

### 阶段 0：需求对齐逼问（grilling）

> **定位**：进入四阶段清单式收集之前的高层对齐环节。纳入 mattpocock `grilling`（一次一问逼问决策树，每问给建议）。**MRD 已充分明确时本阶段可快速通过。**

**触发**：prd-prep 启动、读取 MRD 基线之后立即进行。

**做法：**

1. 基于 MRD 与设计共识，识别"关键设计决策 / 歧义分叉"——尚未定夺、存在多解、或影响后续多个功能规格的点。
2. 用**一次一问**的方式与 project owner 对齐决策；仅当运行时已安装 grilling 且获得显式授权时才把它作为辅助工作流：每次只抛一个决策点并给出推荐答案，等 project owner 定夺后再问下一个（一次问多个会造成困惑）。**事实性问题**（可从 MRD / 代码 / 现状查到的）自己查，不占问题额度；**决策**留给 project owner。
3. 决策逐条达成共识后，记入 prd_prep §2（TBD 解析）；若属跨模块关键决策，另记入项目 `important_conclusion.md`。
4. 达成共识后进入阶段 1。

**与 G/F 清单的分工（不重复）：**

- **阶段 0 grilling** 管 **高层设计决策对齐**（要不要做、架构分叉怎么定、口径歧义）。
- **阶段 3 G/F 清单** 管 **逐项规格收集**（字段、交互、接口、状态机等具体规格）。

**完成标志**：关键决策 / 歧义已逼问对齐，进入阶段 1。

---

### 阶段 1：读取 MRD 基线

**读取顺序：**

1. `agent_handoff.md` — 确认当前项目阶段和目标模块
2. `important_conclusion.md` — 提取已确认的核心设计决策
3. 目标模块对应的 MRD 章节
4. PRD 统一规范基线（如有 `temp_prd_unified_baseline.md`）
5. 如有已完成的相邻模块 prd_prep，读取用于避免重复

**提取维度：**

| 维度 | 识别标志 |
|------|---------|
| 已确认功能（In Scope） | MRD 中明确描述的功能 |
| 排除项（Out of Scope） | 标注"不做""架构预留"的内容 |
| TBD 项 | 标注 TBD、待定、需确认的内容 |
| 跨模块依赖 | 本模块与其他模块的接口、输入/输出关系 |
| 用户类型 | 涉及哪些人员/角色 |
| 功能类型线索 | 是否涉及页面、任务、接口、配置等 |

**完成标志**：功能清单和 TBD 清单已提炼完毕，进入阶段 2。

---

### 阶段 2：功能清单确认

Agent 基于 MRD 阅读结果，**按类型**提炼功能清单草稿，呈现给用户确认。

**输出格式示例：**

```
根据 MRD 初步识别本模块功能清单如下，请确认或补充：

前端页面
  - 账号列表页
  - 新建账号弹窗
  - 账号详情页

任务/调度
  - 账号状态同步任务（定时）

函数/脚本
  - 无

接口
  - 无

配置
  - 无

外部依赖
  - HR系统提供员工数据（导入用）
```

**确认规则：**
- 用户可增删功能项、调整类型归属
- 确认后形成**功能清单基准**，后续 F1–F5 提问以此为准
- 用户说"确认"后进入阶段 3

---

### 阶段 3：结构化提问

**提问顺序：**

1. 先完成全局组（G1–G6），整个模块问一次
2. 再按功能清单基准，逐功能过逐功能组（F1–F5）
3. 每个功能点首次提问时，**F1–F5 全部类型都要问**，不预设跳过
4. 用户明确回复"无此类型"后，该功能后续该类型可跳过；跳过前须说明"根据之前确认本功能无 XX 类型，跳过"

**提问原则：**
- 已有明确共识的跳过，不重复问
- 对 TBD 项逐条提问，给出建议值供选择
- 按分组批次提问，不一次堆出所有问题
- 用户回答后如有新的不确定项，可追加追问
- 用户明确"没有更多问题"后进入阶段 4

---

### 阶段 4：输出 prd_prep 文档

**文件命名规范**：`project_doc/prd_prep_{module_name}.md`

**Header 格式**：

```
> **文档名称**: PRD 准备文档 — {模块名}（prd_prep）
> **所属项目**: {项目名}
> **用途**: 作为{模块名} prd-write 的直接输入。
> **Owner**: project owner
> **最后更新**: {YYYY-MM-DD}
> **内容概述**: prd-prep 提问全部完成，信息来源为 {MRD章节} + {baseline} + project owner 访谈确认（{日期}）。
> **上游基线**: {MRD路径} + {章节}
```

**YAML 状态块**（Header 后紧跟）：

```yaml
---
prd-prep-status: completed
module: {module_name}
mrd-source: {path} {section}
completed-at: {YYYY-MM-DD}
---
```

**完成标志**：文档保存完成，向用户确认"prd_prep 已生成，可执行 prd-write 开始编写 PRD"。

## 全局提问组（G1–G6）

### G1. 功能边界（必问）

> 明确本模块的能力范围，锁定 In Scope / Out Scope / TBD 项。

G1-1. 本模块的核心功能边界是否明确？In Scope 清单是否与 MRD 描述一致，还是有需要补充/裁剪的？
G1-2. Out of Scope 清单是否已穷举？是否有"本期不做、二期预留"的功能需要标注？
G1-3. MRD 中是否有标注为 TBD 或"待确认"的功能项？请逐一给出建议方向，等待 Owner 确认。
G1-4. 是否有功能点的所有权存在跨模块争议（即不确定归属于本模块还是相邻模块）？
G1-5. 功能边界是否存在与已完成模块的重叠？如有，请说明接口/复用方式。

---

### G2. 场景矩阵（必问，需确保覆盖完整）

> 明确所有用户类型及其核心操作场景，覆盖正向流程、逆向流程和异常降级。必须覆盖全部用户角色 × 全部触发路径，禁止遗漏非主流角色或低频场景。

G2-1. 本模块涉及哪些用户类型（如系统管理员、业务管理员、普通用户、外部用户、API 账号）？
G2-2. 每个用户类型的核心操作场景是什么？请按"触发用户 × 场景描述 × 涉及功能"逐一整理。
G2-3. 每个核心场景的 happy path 是什么？请按操作序列描述步骤。
G2-4. 每个主流程是否有对应的逆向流程（撤销/回滚/纠错/停用）？触发条件是什么？
G2-5. 上游依赖不可用时（如 IAM 服务、认证系统宕机），系统如何响应？是否有降级策略或只读模式？
G2-6. 数据不一致时，容忍窗口是多少？关键操作失败时，是否有人工兜底机制？
G2-7. 是否有需要特殊处理的边缘用户类型（如服务账号、临时授权用户）？
G2-8. 是否有场景跨越多个用户类型协作完成（如申请→审批→生效）？请描述完整流转链路。

**G2 覆盖度自检（Agent 在用户回答后执行，确认无遗漏再进入 G3）：**

```
□ 所有已确认用户类型均有对应场景描述
□ 每个场景均有 happy path 描述
□ 每个主流程均明确是否有逆向流程
□ 上游异常降级已覆盖
□ 跨角色协作流程（如有）已完整描述
□ 若有遗漏，追加提问补全后再进入 G3
```

---

### G3. 权限管控（首题必问，按答案展开）

> 先确认是否引入新权限设计，再决定展开范围。

**G3-0（必问）**：本需求是否涉及新角色/新数据权限的定义和分配？

- **若否**：G3-1 至 G3-4（角色与数据权限子问）跳过，直接判断是否有审批流
- **若是**：展开 G3-1 至 G3-4

G3-1. 本需求引入了哪些新角色？每个角色的职责范围和与已有角色的区别是什么？
G3-2. 新角色的数据权限范围如何定义（如按部门/按业务线/按数据标签）？
G3-3. 新数据权限的分配机制是什么（管理员直接分配/申请审批/自动归属）？
G3-4. 各操作项的权限矩阵是什么（谁能执行哪些操作）？是否有"仅限本人资源"规则？

**审批流（跳过条件：若本需求无审批流则跳过 G3-5 至 G3-8）：**

G3-5. 是否有需要审批的操作？审批入口在哪里（系统内审批/外部工单系统）？审批流程几步？
G3-6. 是否支持直授（绕过审批直接授权）？直授的触发条件和适用范围是什么？
G3-7. 权限快照策略：哪些操作需要记录操作前快照（用于审计和回滚）？快照保留时长？
G3-8. 权限拷贝/克隆功能：拷贝范围包括哪些内容？是否有跨租户限制？

---

### G4. 运营策略（条件：无通知/回收/埋点/数仓场景可跳过）

> 确认通知渠道与时机、权限回收触发条件、埋点与数仓需求。

G4-1. 系统通知的渠道有哪些（站内信/邮件/企业微信）？哪些操作需要触发通知？通知时机（即时/定时/汇总）？
G4-2. 权限回收的触发条件有哪些（如账号停用、合同到期、部门变更）？回收是立即生效还是有宽限期？
G4-3. 是否有权限申请的快捷重申机制（如历史申请一键重申）？重申时是否需要重新审批？
G4-4. 本模块需要哪些埋点（关键操作上报）？是否有数仓/BI 分析需求？
G4-5. 是否需要运营大盘（如账号活跃度、权限使用率统计）？大盘数据来源和刷新频率是什么？

---

### G5. 外部依赖（条件：无外部系统依赖可跳过）

> 记录本模块依赖外部系统提供数据或服务的情况，作为工作跟踪用，不需要写很具体。

G5-1. 本模块是否依赖外部系统提供数据或服务？请列出依赖方（如 HR 系统、ERP、第三方平台）。
G5-2. 每个外部依赖：提供什么数据/服务？用于本模块的哪个功能？
G5-3. 外部依赖的对接方式是什么（实时接口/定时同步/文件导入）？
G5-4. 外部依赖目前的状态如何（已确认/待对接/未启动）？预计就绪时间？

---

### G6. 非功能需求（必问）

> 确认 SLA、容量规划、合规审计、性能、可用性要求。

G6-1. SLA 要求：关键操作（如授权生效、账号创建）的时间窗口是多少？告警响应时间目标是多少？
G6-2. 容量规划：当前数据量级估算（账号数、权限条目数、并发操作量）？未来 1–2 年增长预期？
G6-3. 合规与审计要求：操作日志需保留多长时间？是否需要满足特定合规标准（如 SOX、ISO 27001）？
G6-4. 性能要求：列表页最大响应时间？批量操作最大耗时？导出任务最大等待时间？
G6-5. 可用性要求：系统可用性目标（如 99.9%）？核心功能降级策略（如主链路故障时的备用方案）？

## 逐功能提问组（F1–F5）

**执行方式**：针对功能清单基准中的每个功能点，逐功能过一遍 F1–F5。首次提问时 F1–F5 全问；用户明确回复"无此类型"后，该功能后续同类型跳过，跳过前须说明原因。

---

### F1. 前端页面（适用于有界面的功能）

> 覆盖菜单路径、字段规格、查询条件、静态文案、交互点五个维度。

**F1-1. 菜单结构与导航路径**

F1-1a. 本页面在系统菜单中的路径是什么（如：系统管理 > 账号管理 > 账号列表）？
F1-1b. 是否有权限控制决定菜单项的可见性？触发条件是什么？

**F1-2. 字段规格**（每个字段逐一确认以下 7 项）

每个字段需明确：**名称**（中文）/ **含义**（业务含义）/ **类型**（文本/数字/下拉/日期/开关/文件等）/ **取值来源**（手动输入/下拉枚举/关联查询/系统自动填充）/ **校验规则**（必填性、长度限制、格式要求）/ **示例**（一个合法值）/ **备注**（只读条件、联动逻辑等特殊说明）

F1-2a. 本页面/表单涉及哪些字段？请列出字段清单，逐一确认以上 7 项。
F1-2b. 是否有字段在特定条件下切换为只读？触发条件是什么？
F1-2c. 是否有字段存在联动关系（A 字段变化触发 B 字段更新）？

**F1-3. 查询条件**（适用于有筛选/搜索的页面）

F1-3a. 查询交互方式是什么（即时搜索/点击搜索/回车搜索）？
F1-3b. 查询条件来源是什么（手动输入/下拉选择/日期范围/级联选择）？
F1-3c. 各查询条件的默认值是什么？是否有默认筛选范围（如默认只看本部门数据）？
F1-3d. 分页规格（每页默认条数/最大条数）？排序规则（默认排序/是否支持自定义排序）？

**F1-4. 静态文案**

F1-4a. 页面上有哪些固定显示的说明性文案（如表单填写说明、空状态提示、操作成功/失败提示语）？
F1-4b. 是否有需要 hover 展示的气泡文案（tooltip）？分别在哪些字段或操作项上？文案内容是什么？

**F1-5. 交互点规格**（通常是按钮，每个交互点逐一确认）

F1-5a. 本页面有哪些交互点（按钮/链接/操作项）？请列出清单。
F1-5b. 每个交互点的后端处理逻辑是什么？请分步拆解，需要端到端闭环描述（触发→处理→结果反馈）。
F1-5c. 涉及状态变更的交互点，是否需要状态机和状态流转图？请描述所有合法状态及转换条件。
F1-5d. 是否有触发式校验规则（如提交时校验金额不超预算、保存时校验必填项完整）？
F1-5e. 每个交互点的边界与异常场景是什么（如权限不足时的提示、操作失败时的回退策略）？
F1-5f. 是否需要说明交互动效（如按钮 loading 状态、成功后页面跳转行为）？

---

### F2. 任务/调度（适用于后端定时或触发式任务）

F2-1. 任务基础信息：任务名称、所属系统、任务类型（定时/事件触发/手动触发）？
F2-2. 任务逻辑：核心处理步骤是什么？请分步描述（数据读取→处理→写入→通知）。
F2-3. 执行条件和调度顺序：触发条件是什么？是否依赖其他任务完成？调度优先级？
F2-4. 状态机和状态流转图：任务有哪些状态（如待执行/执行中/成功/失败/取消）？各状态转换条件？
F2-5. 数据量级预估 & 超时阈值：单次处理数据量预估？任务超时时间设置？超时后的处理策略？
F2-6. 任务异常和告警机制：哪些异常需要告警？告警渠道和接收人？失败后是否自动重试？重试策略？

---

### F3. 函数/脚本（适用于可复用的业务函数或执行脚本）

F3-1. 函数/脚本基础信息：名称、所属系统/模块、语言/运行环境？
F3-2. 函数/脚本逻辑：核心处理逻辑是什么？输入是什么，输出是什么？
F3-3. 使用场景和触发条件：在哪些场景下被调用？由谁（用户/系统/其他函数）触发？
F3-4. 边界与异常场景：输入为空或非法时如何处理？执行失败时的行为（抛出异常/返回错误码/静默处理）？

---

### F4. 接口（适用于本模块作为服务提供方向外部暴露的接口）

F4-1. 接口信息：接口名称、请求方式（GET/POST/…）、接口路径？
F4-2. 接口字段：接口的核心业务字段有哪些？字段含义和类型？
F4-3. 入参和示例：必传参数和可选参数分别是什么？请提供一个完整入参示例。
F4-4. 返参和示例：成功返回的数据结构是什么？失败返回的错误结构是什么？各提供一个示例。
F4-5. 幂等性与重试策略：接口是否需要幂等性保证？调用方重试时如何处理重复请求？
F4-6. 预期 QPS & 响应时间目标：接口预期调用频率？响应时间 SLA？

---

### F5. 配置（适用于需要初始化或手动配置的系统参数）

F5-1. 配置对象：需要配置什么？配置项的名称、含义、类型和取值范围是什么？
F5-2. 配置步骤：配置由谁操作（运维/管理员/用户）？步骤是什么？是否需要重启或有生效时延？

## 补充说明

- **阶段 0 前置对齐**：进入清单式收集前，先对关键设计决策和歧义做一次一问的人工对齐；grilling 管高层决策对齐，G/F 清单管逐项规格收集，两者不重复。MRD 已充分明确时阶段 0 可快速通过。
- **功能清单确认先行**：阶段 2 是强制步骤，不可跳过，确保 F1–F5 提问有明确范围
- **全问原则**：每个功能点首次提问时 F1–F5 全问，不预设跳过；用户明确说"无此类型"后才可后续跳过
- **G2 覆盖自检**：G2 完成后 Agent 必须执行覆盖度自检，确认无遗漏再进入 G3
- **G3 首题门控**：G3-0 是门控题，答案决定后续展开范围
- **无结论项**：统一标注 `todo`，收录到 §2 TBD 解析
- **跨模块引用**：相邻模块已完成内容标注"详见 {模块} prd_prep"，不重复描述
- **§6 条件写作**：若本模块无任务/函数/接口/配置，对应子节注明"本模块无此类型功能"并保留空节
- **§7 条件写作**：若无外部依赖，注明"本模块无外部依赖"并保留空节
