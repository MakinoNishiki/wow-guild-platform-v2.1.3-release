## 1. 结构化会议纪要（飞书智能纪要或等价导出）结构解析

结构化会议纪要（飞书智能纪要或等价导出）导出的 `.txt` 文件遵循以下骨架（取自实际样本 `noncashpayment2026042401.txt`）：

```
===== <docx 文件名> =====
智能纪要：<会议标题>
[该类型的内容暂不支持下载]
总结
<总结正文 — 通常一段，描述会议主旨与主要决策>
<主题 1>
  <子主题 1.1>
    <内容描述>
  <子主题 1.2>
<主题 2>
...
<后续工作计划>
  <分项行动>
[该类型的内容暂不支持下载]
待办
<待办 1>（来自 <人名>）@<被指派人>
<待办 2>
[该类型的内容暂不支持下载]
会议中的金句时刻 / 会议最佳表现成员
[该类型的内容暂不支持下载]
相关链接
妙记：<标题>
文字记录
<会议标题> <日期>
相关会议纪要
[Table 0]
会议主题：<标题> / 会议时间：<时间> / 参会人：<姓名列表>
[Table 1]
智能会议纪要由 AI 生成，可能不准确，请谨慎甄别后使用
[Table 2] ~ [Table N]
<结构化要点 — 通常分段，用 " / " 分隔短句，是 Agent 提取业务条目的主要来源>
```

### 1.1 关键提取点

| 区域 | 内容 | 用途 |
|------|------|------|
| 议题树 | 业务讨论主体 | 主分类来源 |
| 待办区 | 明确行动项（带"来自 <人名>"或 @ 标签）| 阶段二待办映射节 |
| Table 0 | 会议元信息（时间 / 参会人） | B 表 frontmatter |
| Table 1 | 免责声明 | 忽略 |
| Table 2+ | 结构化要点（用 " / " 分隔） | 议题细节二次扫描 |
| 相关链接 / 文字记录 | 妙记链接等 | 忽略 |
| `[该类型的内容暂不支持下载]` | 占位 | 忽略 |

### 1.2 Agent 解析顺序

```
Step 1: 提取 Table 0 元信息 → frontmatter（meeting-date / 参会人）
Step 2: 提取议题树 → 主分类候选
Step 3: 提取待办区 → 待办映射节
Step 4: 提取所有 Table 2+ → 二次扫描业务细节
Step 5: 去重合并（同一议题在议题树 + Table 重复出现时取最详尽的描述）
```

### 1.3 多场会议处理

若输入多份 `.txt`：

- 按会议时间顺序编号 M01 / M02 / ...
- 每场会议独立解析、独立编号
- frontmatter 中 `meeting-records` 列出全部文件
- `meeting-date` 取最近一场（多场跨日时）

## 2. 阶段一详细规则

### 2.1 PRD 章节树解析

**目标**：建立 PRD 章节路由表，供阶段二章节索引法使用。

**步骤**：

1. 扫描 PRD 全文，提取所有标题层级（`#` ~ `#####`）
2. 按章节号建立正向路由表：章节号 → 标题文本 → 文件偏移量（行号）
3. 建立"关键词 → 章节号"反向索引：
   - 从标题文本提取核心关键词
   - 同时补全已知同义词（见 §2.1.1）

#### 2.1.1 同义词扩展

PRD 演进过程中常存在同义词，Agent 应主动扩展：

| 主词 | 同义词 / 历史叫法 |
|------|------------------|
| ORDER_CLOSED | 订单关闭 / 订单取消（注：少发结案是不同事件，需区分）|
| ORDER_PAID | 下单 / 订单支付 / 支付完成 |
| 流水 | 计费流水 / 交易流水 / 费项 |
| 因子 | 计算因子 / 规则因子 |
| 加工 | 计费加工 / 预处理 |
| 平衡校验 | 流水校验 / 一致性校验 |
| 外部唯一键 | external_uuid / 判重键 |

同义词表在 Skill 运行中持续积累，本表只列基础项，业务专属项由 Agent 根据 PRD §1.3 名词解释段动态补全。

### 2.2 结构化会议纪要解析

按 §1 结构化会议纪要（飞书智能纪要或等价导出）结构骨架处理。

**注意点**：
- Table 附录中用 " / " 分隔的短句应拆为独立小条目（细颗粒）
- 占位文本 `[该类型的内容暂不支持下载]` 忽略
- 相关链接 / 文字记录段是元信息，忽略
- 议题树中的"后续工作计划"段是流程动作，多为待办性质，并入待办区处置

### 2.3 噪声预过滤（二维判定）

对每条议题问两个 Y/N：

- **① 业务相关性**：是否涉及具体业务规则 / 字段 / 接口 / 流程 / 状态机 / 模块？
- **② PRD 可映射性**：是否能映射到 PRD 章节（含潜在新建章节）？

| ① | ② | 处置 |
|---|---|------|
| Y | Y | 进入阶段二 |
| Y | N | 进入阶段二（可能是缺口）|
| N | Y | 进入阶段二（可能是会议未提及的补充信息）|
| N | N | **噪声候选** |

#### 2.3.1 典型噪声示例

- 工具讨论（IDE / 模型成本 / Claude / Cursor / 飞书 等）
- 会员订阅 / 费用价格
- 工作流程改进（评审方式 / 文档归档 / 提交规范）
- 团队建设 / 招聘 / 个人评价
- 与 PRD 模块完全无关的领域讨论

#### 2.3.2 噪声候选的可挑回机制

噪声候选清单作为 B 表的独立 section（§6）一次性呈现给 PM。**默认通过**——PM 若发现误判可手工标记挑回。**Agent 不逐条问 Y/N**，避免打断流程。

## 3. 阶段二详细规则

### 3.1 原子化编号规范

```
M{NN}-{NN}
  ↑     ↑
  |     └─ 条目序号（每场会议内独立，从 01 开始）
  └─────── 会议序号(按会议时间顺序，从 01 开始)
```

示例：
- `M01-01` = 第一场会议的第一条业务条目
- `M02-15` = 第二场会议的第十五条业务条目
- `M01-N01` = 第一场会议的第一条噪声条目（N 代表 noise，独立编号）

**编号原则**：
- 同一议题被多个 Table 重复提及只编一次（取最详尽的描述）
- 待办区与议题区有重合时合并为一条
- 噪声条目独立编号 `M01-N01, M01-N02 ...` 便于追溯

### 3.2 PRD 锚点对齐（章节索引法）

对每条原子条目执行：

```
Step 1: 提取条目关键词（业务名词 / 字段名 / 模块名 / 状态名 / 接口名）
Step 2: 用关键词查 PRD 章节路由表的反向索引
Step 3: 命中候选章节集合（通常 1-3 个）
Step 4: 在候选章节内精读匹配，确认锚点
Step 5: 候选为空 → 全文 grep（fallback）
Step 6: grep 仍为空 → 标记 "PRD 无"
```

#### 3.2.1 精读匹配判定

| 章节覆盖度 | 处置 |
|----------|------|
| **完整覆盖**（章节内容完全包含条目主旨）| 锚点确认 |
| **部分覆盖**（提及但不详尽）| 锚点确认 + 在"建议动作"列标"部分覆盖，需补 X" |
| **关键词碰撞但语义无关** | 回到 Step 5 fallback |

#### 3.2.2 多锚点处置

若同一条目对应多个 PRD 章节：

- 锚点列填主锚点（最详尽的那一个）
- 在"建议动作"列补充次锚点："同步更新 §X.Y.Z"

### 3.3 四象限分类决策树

```
原子条目（非噪声）
├─ PRD 锚点 = "PRD 无"？
│   └─ YES → ① 缺口
│
└─ PRD 锚点存在 → 比对内容：
    ├─ 措辞 + 数值 + 流程 完全一致 → ③ 一致
    └─ 任一不一致 → ② 冲突
```

注：④ 会议未提及 类别由阶段二步骤 4 单独补全，不走本决策树（见 §3.4）。

#### 3.3.1 "内容一致" 判定标准

| 维度 | 一致判定要求 |
|------|------------|
| 关键数值 | 匹配（如阈值 30% / 90% / 20% 等数值精确匹配）|
| 关键字段名 | 中文名 + 编码名都匹配（仅匹配其一不算一致）|
| 关键流程节点顺序 | 完全匹配 |
| 关键概念定义 | 实质相同 |
| 状态枚举 | 完全相同（数量 + 名称 + 4 位数字编码）|

任一维度不一致 → 归为 ② 冲突。

#### 3.3.2 冲突不细化二级标签

本 v1.0 版本所有冲突均归为 ② 冲突，不细分"方向冲突 / 语义冲突 / 重大冲突"等二级标签。

**理由**：凡需 PM 决策的都是冲突，二级标签对决策本身没有额外帮助。等 Skill 跑过 1-2 轮后有数据再考虑细化。

### 3.4 会议未提及补全

阶段二步骤 4：扫描 PRD 一级章节（§1 - §9）和 §5 下的二级章节（§5.1 - §5.x），对每个章节判断："本次会议是否讨论了这个章节？"

| 讨论度 | 处置 |
|--------|------|
| 完全未讨论 | 补 ④ 类条目 `U-NN，会议未提及 §X.Y` |
| 部分讨论 | 不补（已有原子条目落定对应内容）|
| 完全讨论 | 不补 |

**编号**：`U-NN`（U = uncovered）

**目的**：暴露评审遗漏的章节，让 PM 决定：
- **默认通过**（章节内容稳定，无需重新评审）
- **需补充评审**（章节本期内容有更新，应列入下次会议议题）

## 4. 阶段三详细规则

### 4.1 D 表（优先级提醒）抽取

从冲突 + 缺口条目中筛出满足**任一**条件：

| 条件 | 含义 |
|------|------|
| **跨章节影响** | 决策结果影响 ≥ 2 个 PRD 章节 |
| **级联决策** | 决策结果会改变其他条目的分类或处置方式 |
| **根本路线** | 代表两种根本路线（如方向冲突）|

#### 4.1.1 D 表精炼度控制

通常 5-15% 的条目入 D 表。若 D 表条目数 > 总条目数的 20%，判定标准过宽，需收紧。

样本对照（v3.1 → v3.2 B 表）：47 条原子条目，6 条入 D 表（约 13%）。

#### 4.1.2 D 表定位

**D 表是提醒型优先级建议**（非阻断门）。PM 仍需逐条看四象限主表，D 表的作用：

- 帮助规划决策顺序——先决 D 项再决其他条目，可避免决策反复
- 显式提示"这些决策牵涉面广，请投入更多思考"

### 4.2 改动量预估

| 维度 | 估算方法 |
|------|---------|
| 章节级触点 | 主表中所有冲突 + 缺口 + 部分会议未提及条目对应的 PRD 章节去重 |
| 行数估算 | 每条目按复杂度估：低（±5 行）/ 中（±15 行）/ 高（±30 行）|
| 净改动量 | Σ(新增) - Σ(删除) = 净 ±K 行 |

#### 4.2.1 复杂度判定标准

| 复杂度 | 典型场景 | 行数范围 |
|--------|---------|---------|
| 低 | 文案修订 / 单字段调整 / 单行删除 | ±1 ~ ±5 行 |
| 中 | 单 section 重写 / 表格行数变更 / ASCII 原型小幅调整 | ±5 ~ ±20 行 |
| 高 | 整章重写 / 多 section 联动 | ±20 ~ ±80 行 |
| 极高 | 概念体系重构 / 跨模块连锁改动 / 新增完整章节（如标准步骤库 S1-S10、Mapping 表全章）| ±80 ~ ±300+ 行 |

**提示**：当一条会议要点同时触发 ≥ 3 个 PRD 章节联动改写时，单独估"高"通常偏低，建议升级到"极高"。dry-run（v3.1 vs 0424 会议）发现：session-29 实际改动量约 1300 行 / 18 项，理论估算若仍按"高 ±30"会大幅低估。本细化条目（v1.0.1）来自 2026-05-15 dry-run 反馈。

#### 4.2.2 改动量预估的用途

- 帮 PM 评估"本期 PRD 改写工作量"
- 帮 prd-write 增量改写时规划批次（按逻辑簇分批 vs 一次性改完）

## 5. B 表完整模板

**输出形态**：默认**会话内 Markdown 渲染**，PM 即时决策。末尾主动询问"是否归档为文件？"，PM 答"是"才落盘到 `docs/prd/meeting_diff_PRD_v{from}_{YYYYMMDD}.md`。

**会话形态 vs 归档形态差异**：
- 会话形态：可省略 frontmatter / Header / 导航尾部（PM 在会话中看不需要这些追溯元信息）
- 归档形态：frontmatter / Header / 导航尾部全部必备（用于事后追溯和跨会话引用）

**为什么会话优先**：评审是高频活动，落盘会拖慢推进节奏。会话形态把 B 表内容直接渲染到 PM 眼前，沟通节奏紧凑；按需归档保留追溯能力。

下面是 B 表的完整骨架（归档形态），Agent 落盘时按此模板填充。会话形态可裁剪 frontmatter / Header。模板使用 `<...>` 表示占位字段。

````markdown
---
source-prd: <path>
source-version: <v>
source-prd-snapshot: <commit-hash 或日期>
meeting-records:
  - <path1>
  - <path2>
meeting-date: YYYY-MM-DD
target-version: TBD
status: pending-pm-review
generated-by: prd-update-from-meeting v1.0
generated-at: YYYY-MM-DD HH:MM
---

> **文档名称**: 会议纪要 vs PRD <version> 差异分类表 (B 表)
> **所属项目**: <项目名>
> **用途**: 将 <YYYY-MM-DD> N 场评审会议纪要拆解为原子条目，对齐 PRD <version> 章节，按四象限分类，作为 PRD 修订的输入清单。
> **Owner**: project owner
> **生成时间**: <时间>
> **内容概述**: 本表共 N 条原子条目（M01 X 条 + M02 Y 条 + ...）；噪声 X / 一致 X / 冲突 X / 缺口 X / 会议未提及 X。

- PRD 有 + 会议有 + 内容一致 → ③ 一致

- PRD 无 + 会议有 → ① 缺口
- PRD 有 + 会议无 → ④ 会议未提及（提醒）

**输入**：
- <meeting-record-1>
- <meeting-record-2>

**对齐基准**：<PRD-path> (<version>)

**分类汇总**：

| 分类 | 数量 | 处理方式 |
|------|------|---------|
| 噪声 | X | 不入主表，独立存档（§6）|

| ② 冲突 | X | 必须改 PRD（PM 决策方向）|
| ① 缺口 | X | 新增/补写 PRD 章节或字段 |
| ④ 会议未提及 | X | 提醒型，PM 判断默认通过 / 需补充评审 |

| 章节 | 改动类型 | 大致行数 | 复杂度 | 关联条目 |
````
