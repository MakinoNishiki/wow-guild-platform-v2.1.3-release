# MRD 文档生成 (MRD Generation)

> Version: 1.0 | Language: 简体中文 | License: Authorized portable distribution

## 快速开始

本 Skill 引导 Agent 将**已有的设计共识**转化为高质量的 MRD 文档。

**输入**：结构化的需求拆解成果（设计决策、分期策略、模块全景、优先级链等）
**输出**：格式完整、案例丰富、经过场景验证的 MRD 文档 + 关联文档更新

```
上游 Skill（project-scope-breakdown）         本 Skill（mrd-generation）
  模糊需求 → 范围锚定 → 设计决策     →     设计基线识别 → 路径拆解 → 场景验证 → MRD 生成
```

MRD 模板见 [reference.md](reference.md)，实践案例见 [examples.md](examples.md)。

## 适用场景

- 从已有设计共识生成 MRD
- 从讨论记录中提炼并结构化为正式需求文档
- 需要用案例论证设计合理性的文档场景

**前提**：设计层面的共识已基本形成（至少覆盖：做什么、不做什么、核心模型选型）。如果共识尚未形成，应先使用 `project-scope-breakdown` Skill。

## 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **概念即案例** | 每个提出的概念必须有正例（how it works）；关键决策必须有反例（不做的代价） |
| 2 | **场景三层覆盖** | 常规场景 + 常见边界场景 + 极端场景（提供不成立理由或兜底方案） |
| 3 | **拆解即验证** | 拆解每个功能点时自行模拟端到端场景，不合理则自主修正后再输出 |
| 4 | **文档闭环** | MRD 生成后，关联的项目文档（讨论记录、交接文档等）必须同步更新 |
| 5 | **读者视角写作** | MRD 的读者是决策层（IT Head、评审委员会），不是实现者——说清"为什么"比"怎么做"更重要 |
| 6 | **边界显式化** | "不做什么"和"架构预留"与"做什么"同等重要，必须显式列出 |

## 四阶段工作流

```
阶段 1          阶段 2          阶段 3          阶段 4
设计基线识别  →  路径拆解    →  场景验证    →  文档生成与闭环
    ↓               ↓              ↓              ↓
核心/外围分层   功能点逐项拆解  正反例补全     MRD + 关联文档更新
```

---

### 阶段 1：设计基线识别

**目标**：从已有共识中识别核心功能与外围功能的分层

**操作**：
1. 收集所有输入源（设计决策文档、讨论记录、交接文档、参考资料等）
2. 提取已确认的设计共识，按以下维度分类：

| 维度 | 内容 | 识别标志 |
|------|------|---------|
| **核心模型** | 系统的根本数据模型和架构选型 | 讨论中花费最多时间、被反复验证的设计 |
| **核心功能** | 必须做、做不了项目就没意义的能力 | 出现在优先级逻辑链的根节点 |
| **外围功能** | 有价值但非必须、可推迟的能力 | 出现在"二期""架构预留"等表述中 |
| **显式排除** | 明确不做的内容 | 讨论中被裁剪或移除的项 |
| **跨模块依赖** | 本模块与其他模块的接口关系 | "衔接""输入输出""上下游"等表述 |

3. 向用户展示分层结果，确认核心/外围的划分无误

**自检**：
- 是否遗漏了讨论中已确认但未显式记录的设计决策？
- 核心功能是否与优先级逻辑链一致？
- 排除项是否有遗漏——特别是讨论中被口头否定但未写入文档的内容？

**完成标志**：用户确认核心/外围分层

---

### 阶段 2：路径拆解

**目标**：将核心功能逐个拆解为可描述的功能点，并为每个功能点识别实现路径

**操作**：
1. 对每个核心功能模块，拆解为具体的功能点
2. 对每个功能点，描述：

```
功能点 X：
  ├─ 解决什么问题（关联痛点编号）
  ├─ 核心逻辑（一句话描述 how it works）
  ├─ 涉及的实体/概念（与核心模型的关联）
  ├─ 对外接口（与其他模块或外部系统的交互）
  └─ 已确定的设计约束（来自设计共识中的限制条件）
```

3. 为外围功能标注"架构预留方式"——即本期不做但如何确保后续可扩展

**自检——路径合理性模拟**：
对每个功能点，Agent 自行模拟一个端到端场景：
- 从用户触发动作开始
- 经过系统内部处理
- 到最终结果呈现

如果模拟过程中发现逻辑断裂（如：某个步骤需要的数据在前序步骤中不存在），则：
1. 标记问题
2. 尝试自主修正（调整拆解或补充前置条件）
3. 如果无法自主修正，标记为"需用户确认"并提出具体问题

**完成标志**：所有核心功能点拆解完成，路径模拟无逻辑断裂

---

### 阶段 3：场景验证与案例补全

**目标**：为每个功能点和设计决策补充具体案例，验证设计完备性

**操作**：

**第 1 步：场景选取（三层覆盖策略）**

| 层级 | 场景类型 | 选取标准 | 文档中的呈现方式 |
|------|---------|---------|----------------|
| **L1** | 常规场景 | 占使用量 80%+ 的主路径 | 完整正例（含人物、数据、流程） |
| **L2** | 常见边界场景 | 合理可预期、有一定概率发生 | 正例 + 处理规则说明 |
| **L3** | 极端场景 | 极低频或假设条件苛刻 | 简述 + 不成立理由/兜底方案 |

**第 2 步：正例构建规则**

每个正例必须包含：
- **具体人物**（用虚构但合理的姓名和角色，如"销售专员李明"）
- **具体数据**（用示意性但可信的数据值，如"工号 GQ-10234"）
- **完整流程**（从触发到结果，不跳步骤）

正例的验证标准：读者看完正例后，能不依赖任何其他说明，理解这个功能怎么工作。

**第 3 步：反例构建规则**

反例用于关键设计决策，说明"如果不这样做会怎样"：
- **选择另一个方案的代价**（如：用大宽表替代 M+N+E 分层的后果）
- **不做某个能力的风险**（如：不做自然人去重导致审计无法追溯）
- **当前状态的痛点**（如：各系统独立管理账号导致离职账号残留）

反例的验证标准：读者看完反例后，能理解为什么当前设计是必要的。

**第 4 步：场景覆盖度自检**

对照功能点清单检查：
- [ ] 每个核心功能至少有 1 个 L1 正例
- [ ] 涉及设计选型的功能至少有 1 个反例
- [ ] 涉及多方交互的功能至少有 1 个 L2 边界场景
- [ ] 识别到的 L3 极端场景已列出处理策略

**完成标志**：所有功能点的场景覆盖通过自检

---

### 阶段 4：文档生成与闭环

**目标**：按 MRD 结构输出文档，并完成关联文档更新

**操作**：

**第 1 步：MRD 文档生成**

按模板结构（见 [reference.md](reference.md)）生成 MRD，要点：

- **Header**：文档名称、所属项目、用途、Owner、更新日期、内容概述
- **正文**：按模板章节逐一填充，将阶段 2 的拆解结果和阶段 3 的案例嵌入对应章节
- **Tail**：关联文档索引

写作风格要求：
- 面向决策层，不面向开发者
- 用表格呈现结构化对比（如：方案 A vs B、本期 vs 排除项）
- 用流程图/架构图辅助复杂逻辑的表达
- 正反例用引用块（`>`）格式呈现，与正文形成视觉区分

**第 2 步：关联文档更新**

MRD 生成后，检查项目是否有以下要求并执行：

| 检查项 | 操作 |
|-------|------|
| 项目是否有元指令/运作规则？ | 按规则要求更新对应文档（如 discussion_record、agent_handoff 等） |
| 项目是否有交接文档？ | 更新项目状态、目录结构、文档关联关系 |
| 项目是否有讨论记录？ | 补充本轮讨论过程的摘要和索引 |
| 项目是否有关键结论文档？ | 检查 MRD 中是否引用了所有已确认的结论 |

**第 3 步：生成质量自检**

使用 [reference.md](reference.md) 中的质量检查清单逐项验证。

**完成标志**：MRD 文档通过质量自检 + 关联文档全部更新

## 与上游 Skill 的衔接

本 Skill 与 `project-scope-breakdown` 形成上下游关系：

```
project-scope-breakdown                    mrd-generation
┌────────────────────────┐              ┌──────────────────────┐
│ 阶段 1: 模糊输入→基线   │              │ 阶段 1: 设计基线识别   │
│ 阶段 2: 范围锚定        │ ──共识输出──→ │ 阶段 2: 路径拆解       │
│ 阶段 3: 设计深挖        │              │ 阶段 3: 场景验证       │
│ 阶段 4: 压力测试        │              │ 阶段 4: 文档生成与闭环  │
│ 阶段 5: 优先级链        │              │                      │
└────────────────────────┘              └──────────────────────┘
```

上游 Skill 的产出物（`important_conclusion.md`、`agent_handoff.md` 等）直接作为本 Skill 的输入。如果上游产出物不存在，Agent 应提示用户先完成范围拆解，或从现有讨论记录中自行提炼设计基线。
