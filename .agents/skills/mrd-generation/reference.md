# MRD 模板与质量检查清单

## MRD 文档模板

### Header（必须）

```markdown
> **文档名称**: [模块名称] MRD (Market Requirements Document)
> **所属项目**: [项目全称]
> **用途**: [一句话说明文档面向谁、解决什么问题]
> **Owner**: [Owner 姓名]
> **最后更新**: [日期]
> **内容概述**: [2-3 句话概述文档覆盖的核心内容]
```

### 正文结构

```
1. 项目背景与驱动力
   1.1 业务现状与痛点（列举 2~3 个核心痛点，配具体表现）
   1.2 驱动力与优先级排序
   1.3 "不做"的代价

2. 目标与成功指标
   2.1 项目目标（定性，每个目标配正例+反例）
   2.2 可量化的成功指标（表格：指标/基线/目标/衡量方式）

3. 用户与场景
   3.1 用户角色定义（表格：角色/描述/与系统的关系/画像）
   3.2 核心场景（每个场景：流程图 + 正例，关键场景配反例）

4. 解决方案概述
   4.x 每个核心设计点一个子节
   （每个子节：设计理念 + 详细定义 + 正例 + 反例/对比）

5. 范围与边界
   5.1 本期纳入（表格：能力项/说明）
   5.2 显式排除项（表格：排除项/排除理由/替代方案）
   5.3 架构预留项（表格：预留项/预留方式/启用时间）

6. 风险与依赖
   6.1 关键依赖（表格：依赖项/内容/风险等级/应对措施）
   6.2 已知风险与缓解措施（表格：风险/影响/缓解措施）
```

### Tail（必须）

```markdown
## 文档关联关系

| 关联文档 | 关系说明 | 索引 |
|---------|---------|------|
| [文件名] | [与本文档的关系] | [路径] |
```

## 章节编写指引

### §1 项目背景与驱动力

- 痛点描述用**两栏表格**（痛点 + 具体表现），避免大段叙述
- 驱动力排序要说清**隐性排序**——决策层心里的真实优先级，而非官方口径
- "不做的代价"用具体事件/数据论证，不用泛泛的"会变差"

### §2 目标与成功指标

- 定性目标不超过 3~4 个，每个配正例+反例
- 正例模式：`[人物] + [操作] + [系统行为] + [结果]`
- 反例模式：`[当前状态] + [具体问题] + [造成的后果]`
- 量化指标必须有基线值（可以是估算），否则目标数字没有参照意义

### §3 用户与场景

- 用户角色表格必须包含"典型人物画像"列——让读者脑中有具体的人
- 核心场景用**缩进流程图**（纯文本，不依赖渲染工具）展示步骤
- 每个场景下方紧跟正例（引用块格式）
- 至少 1 个场景需配反例（选择痛点最突出的场景）

### §4 解决方案概述

- 每个子节的结构：`设计理念 → 详细定义（含表格/图） → 正例 → 反例或对比`
- 涉及多方案选型的，用**对比表格**（维度 × 方案）
- 涉及层次结构的，用 **ASCII 架构图**
- 涉及数据流的，用**箭头流程图**
- **"为什么不选另一个方案"**比"为什么选这个方案"更有说服力

### §5 范围与边界

- 排除项必须有"排除理由"和"替代/缓解方案"——不能只写"不做"
- 架构预留项要说明"预留方式"——是留接口、留数据结构、还是留扩展点
- 本期纳入的能力项要与 §4 的解决方案子节一一对应

### §6 风险与依赖

- 依赖项要标注风险等级（高/中/低）和应对措施
- 风险描述要具体到场景（"飞书 webhook 延迟"而不是"第三方系统不稳定"）
- 缓解措施要可执行（"定时全量对账兜底"而不是"做好容错"）

## 正例与反例编写规范

### 正例格式

```markdown
> **正例**：[人物角色][姓名][执行操作]，[系统行为描述]，[最终结果]。
```

**要素清单**：
- 虚构但合理的人名和角色
- 具体但示意性的数据值（工号、部门名、金额等）
- 完整的因果链（触发 → 处理 → 结果）
- 不依赖其他段落即可独立理解

### 反例格式

```markdown
> **反例（[场景标签]）**：[当前状态/选择另一方案时的情况]，[导致的具体问题]，[造成的后果/代价]。
```

**常用场景标签**：
- `当前状态` — 说明现在的痛点
- `不做 XXX 的代价` — 说明某个能力不做会怎样
- `使用方案 B 的代价` — 说明为什么不选另一个方案

### 边界场景格式

```markdown
| 边界场景 | 处理规则 | 理由 |
|---------|---------|------|
| [场景描述] | [系统如何处理] | [为什么这样处理] |
```

## 场景覆盖度检查清单

### 按功能点检查

对 MRD 中每个核心功能点（§4 的每个子节），逐项确认：

- [ ] 至少 1 个 L1（常规）正例
- [ ] 涉及设计选型的功能，至少 1 个反例说明"为什么不选另一个方案"
- [ ] 涉及多方交互的功能，至少 1 个 L2（边界）场景
- [ ] 已识别的 L3（极端）场景，列出处理策略或不成立的理由

### 按场景类型检查

- [ ] 核心业务主路径（L1）全部覆盖（入职/转岗/离职/外部用户等）
- [ ] 跨系统交互场景至少有 1 个正例
- [ ] 异常/失败场景至少有 1 个正例（如同步失败的处理）
- [ ] 身份/状态变迁场景至少有 1 个正例（如内部→外包→再入职）

## MRD 质量检查清单

### 结构完整性

- [ ] Header 包含所有必填字段（文档名称、项目、用途、Owner、日期、概述）
- [ ] 正文 6 大章节全部存在（§1 可标注待补充）
- [ ] Tail 包含文档关联关系表
- [ ] 目录与正文标题完全对应

### 内容质量

- [ ] 每个核心概念有正例
- [ ] 每个设计选型有反例或对比说明
- [ ] 量化指标有基线值
- [ ] 排除项有排除理由和替代方案
- [ ] 架构预留项说明了预留方式
- [ ] 风险有具体的缓解措施（非泛泛而谈）

### 读者体验

- [ ] 决策层读者无需技术背景即可理解核心设计思路
- [ ] 正反例用引用块格式，与正文形成视觉区分
- [ ] 表格用于结构化对比，不滥用
- [ ] 架构图/流程图用于复杂逻辑，简单逻辑用文字

### 文档闭环

- [ ] 项目讨论记录已更新（记录本轮 MRD 生成过程）
- [ ] 项目交接文档已更新（反映 MRD 完成状态）
- [ ] MRD 中引用的关键结论与 `important_conclusion.md` 一致
- [ ] 文档关联关系表完整（上游文档、下游文档均已列出）
