# MRD 生成实践案例

## 案例概要

| 项 | 内容 |
|---|------|
| 项目 | 某快消集团 — 权限和账号系统建设 |
| 模块 | 统一账号管理平台 |
| 背景 | 集团账号体系分散，飞书 SSO 覆盖不全，数据权限各系统各自管，外部用工无统一管理 |
| 上游输入 | 讨论记录（20+ 轮对话）、关键设计决策文档（10 项共识）、压力测试问题清单（40+ 问题） |
| MRD 产出 | 6 章、600 行、5 个核心场景、4 项设计决策（含正反例）、9 项纳入 + 5 项排除 + 3 项预留 |

---

## 阶段 1 实践：设计基线识别

### 输入源

本案例的输入来自两条讨论线：

- **线索 A**（项目级文档）：IAM 5 模型框架、分期策略、核心痛点、赋权范式、优先级逻辑链
- **线索 B**（模块级讨论记录）：账号平台定位、person_id 策略、M+N+E 属性模型、生命周期同步

### 基线识别结果

| 维度 | 具体内容 |
|------|---------|
| **核心模型** | 统一账号平台（Operational SSOT）、自然人唯一标识（person_id + UUID）、M+N+E 三层属性模型 |
| **核心功能** | 主账号 CRUD、飞书 People 同步、自然人去重、M+N+E 属性存储、生命周期自动化、统一身份服务接口 |
| **外围功能** | 属性定义管理（N 层弹性域注册）、外部用户管理、基础审计日志 |
| **显式排除** | Session Revocation、函数计算、海外主体、外采 SaaS 深度同步、MFA |
| **跨模块依赖** | 与 PDP（权限决策服务）的衔接——M+N+E 属性作为 PDP 策略评估的输入 |

### 过程中的关键判断

识别核心 vs 外围时，Agent 通过以下方式判断：
- **优先级逻辑链回溯**：逻辑链的根问题是"规则引擎/赋权模型"，而账号模块是赋权模型的输入端——因此"为 PDP 提供准确的属性输入"是核心目标
- **讨论时间投入**：M+N+E 模型和 person_id 策略在讨论中各花了 2-3 轮深度对话，说明它们是核心设计；属性定义管理只在 M+N+E 讨论中被顺带提及，属于外围

## 阶段 2 实践：路径拆解

### 功能点拆解示例

以"自然人唯一标识"为例：

```
功能点：自然人唯一标识
  ├─ 解决什么问题：同一自然人在多系统中有多个账号，无法关联和审计（关联 P1/P2）
  ├─ 核心逻辑：系统生成 person_id (UUID)，通过复合匹配策略去重
  ├─ 涉及实体：Person、IdentityRecord、MainAccount
  ├─ 对外接口：向 PDP 提供 person_id 作为属性查询的主键
  └─ 设计约束：
      - 一个自然人终身只有一个 person_id
      - 可有多条身份记录（如内部员工+外包身份共存）
      - 匹配歧义时，人工确认最高优先级
```

### 路径模拟中发现的问题

模拟"离职后以外包身份回来"的场景时，Agent 发现一个潜在逻辑断裂：

> **发现**：如果系统只按飞书 user_id 匹配，外包人员没有飞书 user_id，会匹配不上已离职的内部员工 person_id。但该自然人实际是同一个人。
>
> **修正**：在复合匹配策略中增加"身份证号"作为跨身份类型的匹配桥梁。确认优先级链中，身份证号的优先级高于飞书 user_id。

## 阶段 3 实践：场景验证与案例补全

### 三层覆盖的实际分布

| 层级 | 场景数 | 代表性场景 |
|------|-------|-----------|
| L1 常规 | 5 | 入职、转岗、离职、外部用户接入、跨系统关联 |
| L2 边界 | 3 | 同步失败+定时对账兜底、同名同手机号、离职后以外包回来 |
| L3 极端 | 2 | 外部用户提供虚假信息、飞书 API 长时间不可用 |

### 正例编写示范

**L1 常规场景——入职**：

> **正例**：2026 年 4 月 1 日，产品经理赵敏入职，HR 在飞书 People 录入信息（姓名、工号 GQ-20260401、部门=产品部、直属上级=project owner）。统一账号平台在 10 分钟内自动创建主账号（person_id: uuid-xxx, main_account_id: MA-20260401-0001），并将身份信息同步至 CRM、BI、OA 三个已接入系统。赵敏当天即可使用飞书账号登录所有系统。

要素分析：
- 具体人物：产品经理赵敏
- 具体数据：工号 GQ-20260401、部门=产品部
- 完整流程：HR 录入 → 平台创建 → 下游同步 → 可登录
- 独立可理解：不需要读其他段落就能明白入职流程

### 反例编写示范

**设计决策反例——为什么用 M+N+E 而不是大宽表**：

> **反例（使用大宽表的代价）**：假设把所有属性放在一张表里——person 表有 100 个字段，其中 13 个是基础字段，20 个是 CRM 专属字段，15 个是财务专属字段，10 个是供应链专属字段。问题是：每接入一个新业务系统都要改表结构；80% 的字段对每个员工是空值；CRM 的 `region` 和供应链的 `region` 含义不同，命名冲突无法解决。

要素分析：
- 场景标签：使用方案 B 的代价
- 具体问题：改表结构、空值、命名冲突
- 代价量化：100 字段、80% 空值、20 个系统后维护失控

### 边界场景编写示范

| 边界场景 | 处理规则 | 理由 |
|---------|---------|------|
| 同一人从内部员工离职后以外包身份回来 | 不创建新 person_id，在原 person_id 下新增身份记录 | 同一自然人，需完整审计轨迹 |
| 外部用户提供虚假信息 | 平台不做真实性验证，记录信息来源和录入人，业务方承担审核责任 | 非实名认证平台，平台负责留痕 |

## 阶段 4 实践：文档生成与闭环

### MRD 最终结构

```
§1 项目背景与驱动力 .................... [留空，用户另行补充]
§2 目标与成功指标 ...................... 3 个目标（各含正反例） + 4 个量化指标
§3 用户与场景 ......................... 5 个角色 + 5 个核心场景
§4 解决方案概述
  §4.1 统一账号平台定位 ............... SSOT 定义 + 同步机制 + 架构图
  §4.2 账号来源与认证路径 ............. 4 种场景 × 详解 + 正反例
  §4.3 自然人唯一标识策略 ............. person_id + 匹配策略 + 边界场景表
  §4.4 主账号信息模型 ................. M+N+E 三层定义 + CRM/财务/供应链列名示例
  §4.5 生命周期管理机制 ............... 5 个事件 + 同步模式 + Session Revocation 说明
  §4.6 与 PDP 的衔接 .................. 属性→决策链路 + 端到端正例
§5 范围与边界 ......................... 9 项纳入 + 5 项排除 + 3 项预留
§6 风险与依赖 ......................... 5 个依赖 + 5 个风险
```

### 文档闭环操作

MRD 生成后，Agent 执行了以下闭环操作：

1. **讨论记录更新**：在 `discussion_record.md` 中新增"账号管理层深度讨论与 MRD 生成"章节，记录 8 轮对话摘要
2. **交接文档更新**：在 `agent_handoff.md` 中更新项目状态表（新增 MRD 完成状态）、目录结构（新增 `project_doc/`）、下一步重点（MRD 评审 → PRD）、文档关联关系
3. **一致性验证**：确认 MRD §4 中引用的赋权范式、组织架构模型定位等与 `important_conclusion.md` 的记录一致

## 关键经验总结

| # | 经验 | 说明 |
|---|------|------|
| 1 | 多源整合时以"优先级逻辑链"为锚 | 多份讨论记录可能包含重叠或矛盾的内容。用逻辑链判断哪些是核心、哪些是过程中被修正的旧方案 |
| 2 | 正例的人物要跨场景复用 | 入职场景用"赵敏"，转岗场景用"李明"——不要在同一个场景里堆太多人物，也不要全用"张三" |
| 3 | 反例比正例更有说服力 | 决策层最关心"为什么不能另一种做法"，而非"你选的方案有什么好处" |
| 4 | §5 范围与边界是 MRD 的"安全阀" | 写清楚"不做什么"能防止评审时被追加需求导致范围失控 |
| 5 | 文档闭环不能省 | MRD 生成后不更新交接文档，下一个 Agent 接手时会以为 MRD 还没做 |
| 6 | 留空章节好过胡编 | §1 背景如果用户还没准备好输入，标注"待补充"比 Agent 自行编造更安全 |
