## 识别方法论详解

### 1.1 双子任务结构

第一拍"识别"包含两个并列的子任务：**逻辑识别** + **范围识别**。两者不可省略其一。

#### 1.1.1 逻辑识别

**目的**：把现状资产中的"与本次改动相关的现行逻辑"提取出来，作为后续比对的对照基准。

**输入**：现状资产清单（多份文档）+ 用户对需求的描述

**输出**：一段或一组现状逻辑要点（typically bulleted list）

**执行步骤**：

1. **关键词提取**：从用户诉求中提取关键功能词（如本次 V5："乐享券"、"20%"、"档位"、"试算"、"冻结"、"退款"）
2. **跨文档搜索**：用关键词在每份现状文档中搜索相关段落
3. **去重 + 取最新**：多份文档涉及同一逻辑时按 [§现状融合规则细则](#现状融合规则细则) 处理
4. **裁剪**：删除与本次改动无关的段落，仅保留改动半径内的现行逻辑
5. **重组**：按逻辑层次（用户操作 → 系统计算 → 数据流转 → 边界场景）重新组织

**关键检查**：

- 逻辑识别完成后，问自己："如果新研发只读这一段，能不能理解现状是什么？"
- 如果需要再读 2 篇以上文档才能理解 → 说明你的逻辑识别没做完整
- 如果某条逻辑读者会问"为什么写这个"（即与本次改动无关）→ 说明你没裁剪干净

#### 1.1.2 范围识别

**目的**：明确改动的影响半径，让下游研发知道"哪些功能改了 / 哪些功能没改"。

**输入**：用户对需求的描述（关键！）

**输出**：两个清单 — **识别范围**（in scope）+ **识别边界**（out of scope）

**反直觉点**：很多人会先列影响半径，再去匹配用户描述。**这是错的**。正确的方向是反过来：

```
用户诉求描述 → 反推影响半径 → 显式标注 in/out of scope
```

理由：用户描述本身已经隐含了改动半径。我们的任务是把"隐含"变成"显式"，而不是凭空想象一个半径。

**典型工作流**：

```
Step 1：解析用户描述，逐句提取动作动词（"改成"、"新增"、"取消"、"沿用"等）
Step 2：每个动作动词背后是一个功能点 → 加入 in scope 列表
Step 3：扫描用户描述未明示但**有可能被波及**的相邻功能 → 加入候选 out of scope 列表
Step 4：候选 out of scope 列表中，凡是用户**明示要沿用**的 → 移入"沿用现状"声明
Step 5：候选 out of scope 列表中剩余的项 → 主动向用户确认是 in 还是 out
```

**输出格式建议**：

```markdown
**识别范围**：本期改动影响 <一句话概括的总半径>。具体半径覆盖：
① <子半径 1>；
② <子半径 2>；
...

**识别边界**（不在本期范围）：<功能 A> / <功能 B> / ... —— 这些功能本身**不改动**，
<必要时补充说明：如"仅其中 X 部分按本期新算法套入"等>。
```

### 1.2 识别完成的判定标准

| 判定 | 通过标准 |
|------|---------|
| 逻辑识别完成 | 与本次改动相关的现行逻辑均已提取，且能独立理解（不依赖外部文档） |
| 范围识别完成 | in scope 与 out of scope 互不重叠、合起来覆盖用户描述中所有动作动词背后的功能点 |
| 边界明确 | 没有"灰色地带"功能（要么 in，要么 out，明确沿用 vs 改动）|

### 1.3 反例

#### 反例 1 — 现状描述写得过细，包含改动半径外内容

```markdown
❌ 错误
**现状逻辑**：
- 货款余额不允许扣负
- 信用账本支持透支（可透支金额 = 临时额度 + 固定额度）
- 货补/返利账本默认 30% 上限...
- 账扣账本允许整单 100% 支付
- 赠货账本走"其他出库"
- 优惠券支付不支持调拨订单
- ...
```

问题：本次改动只涉及乐享券 + 货补/返利 + 现金；信用账本透支机制、账扣、赠货、优惠券都与本次无关。

```markdown
✅ 正确
**现状逻辑**（截至 2026-05-18 线上生产口径，仅列与本次改动相关的部分）：
- 货款余额不允许扣负；最终若货款 < 0 则全单回滚，返回支付失败
- 货补/返利档位默认 30%，可通过 OA 申请提升至 50% 或 70%（仅 30/50/70 三档）
- 单 SKU 乐享券上限 = rounddown(SKU 数量 × 30%)；用户在 [0, 上限] 自主录入
- ...
```

#### 反例 2 — 范围识别缺失边界声明

```markdown
❌ 错误
**识别范围**：本期改动影响订单支付成功时点的各账本计费计算。
```

问题：只说改了什么，没说没改什么。下游会困惑"那退款流程是不是也改了？发货呢？"

```markdown
✅ 正确
**识别范围**：本期改动影响订单支付成功时点的各账本计费计算。具体半径覆盖：
① 良品下单/支付页的支付方式选项；
② 账款接收下单请求后的乐享券计算逻辑；
③ 账款的试算/冻结执行链路；
④ 退款/少发出库/订单关闭场景中的乐享券处理。

**识别边界**（不在本期范围）：发货/退货/少发/订单关闭的业务流程主干、状态机、
账本类型表、客户闭户兜底、OA 货补档位申请流程 —— 这些功能本身不改动，
仅其中"乐享券部分"按本期新算法套入。
```

## 比对表模板

### 2.1 标准模板

```markdown
#### 5.x.2 需求改动前后对比

| 维度 | 现状（改动前） | 改动后 |
|------|--------------|-------|
| <维度 1> | <现状描述> | <改动后描述，或"**不变**"> |
| <维度 2> | <现状描述> | <改动后描述> |
| ... | ... | ... |
```

### 2.2 维度选取原则

**Do**：

- 每行一个**原子功能点 / 字段 / 行为**（不要把多个功能放一行）
- 优先选取**用户/研发**容易混淆的维度（"是不是变了？"）
- 把"声明性不变"也写入（如"状态机 - 不变"），减少下游误解
- 把**数量性质 vs 数值**分开列（如本次 V5：单 SKU 乐享券数量的"性质"是"上限 → 强制等值"，"数值"是"30% → 20%"，两行分列）

**Don't**：

- 不要写复合维度（如"乐享券和货补的计算规则" → 拆成两行）
- 不要把"过程"放进比对表（过程留给 §5.x.3）
- 不要在比对表中加注释 / 引用块（保持表的纯净度）

### 2.3 现状列的处理

| 现状情况 | 现状列写法 |
|---------|----------|
| 现状有明确规则 | 直接抄现状描述 |
| 现状无明确规则 | "无显式策略" 或 "现状未涉及" |
| 现状中存在但本期不动 | 改动后列写"**不变**" |
| 多份文档冲突 | 按现状融合规则取的"权威口径" |

### 2.4 行数控制

- **8 行以下**：维度选取过粗，可能漏维度。检查清单：声明性"不变"项是否漏了？数量性质/数值是否分行？接口/字段/流程/状态机/业务主干是否各占一行？
- **8-20 行**：典型范围，建议默认采用
- **20 行以上**：维度选取过细 / 改动范围超出本 Skill 适用范围。考虑：
  - 是否把多个细节合并成一个"原则性维度"？
  - 是否本次改动点其实是多个改动点的捆绑？（考虑拆为 5.1 / 5.2 / ...）

### 2.5 V5 实战样例（14 行）

| 维度（V5 实例）| 行性质 |
|---------------|-------|
| 用户在良品支付页的支付方式选项 | 实质改动 |
| 是否使用乐享券的决策方 | 实质改动 |
| 单 SKU 乐享券数量的性质 | 实质改动（性质行）|
| 券支付比例 | 实质改动（数值行）|
| 比例性质 | 实质改动（解释性维度）|
| 货补档位与乐享券比例联动 | 实质改动（含特殊概念区分）|
| 余量不足时的处理 | 实质改动 |
| 下单试算 T1→实际冻结 T2 余量变化的处理 | 实质改动（新增的非对称策略）|
| 良品支付页初始化所需的接口 | 实质改动（新增接口）|
| 行间优先级 | **不变**（声明性）|
| 单行内扣款顺序 | **不变**（声明性）|
| 状态机 / 业务主干 / 客户闭户兜底 / OA 流程 | **不变**（声明性聚合）|
| 退款时账款是否实际向营销中台释放/发券 | **不变**（声明性）|

**关键观察**：13 行中有 4 行"不变"（占 30%）。这些"不变"行是 PRD 价值最高的部分之一 —— 它们告诉研发"不要碰这些功能"，避免误改。

## 动作的子节聚合骨架

### 3.1 标准聚合模板

```markdown
#### 5.x.3 具体迭代方案

##### 5.x.3.1 <核心规则/算法>
<具体规则定义，含公式 / 表 / 决策树>

> <扩展说明：背景理由、辅助证明、风险提示等，用引用块嵌入，不拆独立标题>

##### 5.x.3.2 <补充规则 / 联动表 / 边界条件>
<具体定义>

##### 5.x.3.3 <时点 / 流程模型>（如需）
<时点定义 + 触发条件 + 动作清单>

##### 5.x.3.4 <新交付接口规格>（如需）
<提供方 / 调用方 / 入参 / 出参 / 取值规则>

##### 5.x.3.5 受影响功能与沿用范围
<一张表：现有功能 / 现状 / 本期是否改动>

##### 5.x.3.6 回归测试要点
<一张表：编号 / 回归场景 / 预期>
```

### 3.2 子节性质分类

| 子节类型 | 必备性 | 内容性质 |
|---------|-------|---------|
| 核心规则 / 算法 | **必备** | 改动点的核心逻辑，typically 1-2 个子节 |
| 补充规则 / 联动表 | 按需 | 当核心规则涉及多个参数联动时（如 V5 货补档位 × 乐享券比例联动）|
| 时点 / 流程模型 | 按需 | 涉及时点 / 状态 / 异步流程的改动（如 V5 T1/T2 两时点）|
| 新交付接口规格 | 按需 | 本期新引入接口时（如 V5 minCoupon 接口）|
| 受影响功能与沿用范围 | **必备** | 所有迭代型 PRD 都必须有 |
| 回归测试要点 | **必备** | 所有迭代型 PRD 都必须有 |

### 3.3 何时用 `>` 引用块而非独立子节

**判断标准**：这段内容如果删除，读者能不能理解上一段的核心规则？

- 能 → 用 `>` 引用块（说明它是辅助/解释性的）
- 不能 → 升为独立子节（说明它本身就是核心规则的一部分）

**适合用引用块的内容类型**：

- 算法的**为什么**（背景理由 / 设计动机）
- 边界情况的**风险提示**
- 与其他规则的**等价说明**（如本次 V5 退款"计算不执行"的路径 A/B 说明）
- 实现层面的**注意事项**

**适合升为独立子节的内容类型**：

- 算法本体 / 公式定义
- 新接口的入参/出参规格
- 一张完整的联动表 / 决策表
- 时点模型的状态转移

### 3.4 V5 实战拆解

V5 §5.1.3 最终采用的 6 个子节及其性质：

| V5 子节 | 性质 | 内容 |
|---------|------|------|
| 5.1.3.1 乐享券单行算法 | 核心规则 | 金额→数量→金额回算的算法定义 + 行级判定表 |
| 5.1.3.2 货补档位 × 乐享券比例联动 | 补充规则（联动表）| 30/50/70 三档与乐享券比例的联动 |
| 5.1.3.3 两时点模型与时间差非对称 | 时点 / 流程模型 | T1/T2 触发条件 + 时间差处理策略 |
| 5.1.3.4 minCoupon 接口（账款本期新交付）| 新交付接口规格 | 提供方/调用方/入参/出参/取值规则 |
| 5.1.3.5 受影响功能与沿用范围 | 必备 | 发货/退款/少发/订单关闭/状态机/客户闭户/OA 7 行 |
| 5.1.3.6 回归测试要点 | 必备 | 16 条 RT 用例覆盖正向/异常/兼容 |

**V5 第一稿的教训**：原本拆了 9 个子节（含"对某行是否计算 20% 的判定"、"多券选择规则"、"金额→数量→金额回算的原因"、"与现存营销中台交互链路的关系"等独立子节），结构臃肿。最终聚合：

- "对某行是否计算 20% 的判定" → 合并进 5.1.3.1 作为内嵌的判定表
- "多券选择规则" → 合并进 5.1.3.1 作为 `>` 引用块
- "金额→数量→金额回算的原因" → 合并进 5.1.3.1 作为 `>` 引用块
- "与现存营销中台交互链路的关系" → 合并进 5.1.3.5

聚合后从 9 节 → 6 节，可读性显著提升。

## 现状融合规则细则

### 4.1 多版本现状的层次模型

典型项目的现状资产会形成 3 层：

```
Layer 1: 早期现状（更早的版本/约定）
    ↓ 被部分覆盖
Layer 2: 当前生产口径（最新已上线的版本）
    ↓ 触发改动
Layer 3: 外部触发源（本次改动的需求来源，如上游 PM 方案）
```

**规则**：

- 三层中都覆盖的内容 → 取 Layer 2
- 仅 Layer 1 提到、Layer 2 重写过的 → 不引用 Layer 1
- 仅 Layer 1 提到、Layer 2 未涉及的（基础设施性内容）→ 保留 Layer 1
- Layer 3 不直接作为现状 → 放在 §2.2 诉求来源 + §九 参考资料

### 4.2 文档与线上不一致的处理决策树

```
现状文档 X 写的逻辑 vs 实际线上 Y
    ↓
两者是否一致？
    ├─ 是 → 按 X / Y 描述（一致即可）
    └─ 否 → 主动向用户追问"以哪份为准"
              ↓
            用户回答 → 按用户确认的口径写
              ↓
            是否在 PRD 中说明文档勘误？
              ↓
            否（默认）→ PRD 保持干净
            是（特殊请求）→ 加 footnote 但不展开
              ↓
            在 discussion_record 或会话中记录差异
```

### 4.3 V5 实战：多版本融合的具体处理

V5 PRD 涉及的 3 层资料：

| Layer | 文件 | 处理方式 |
|-------|------|---------|
| Layer 1 | `reference/old_rules.docx`（账款上一版，2025-03 前）| 保留账本类型表、搭赠/退款基础规则等"基础设施"；不引用已被 Layer 2 覆盖的内容 |
| Layer 2 | `reference/present_rules_cauculation.docx`（一物一码 V1.0，2025-03 上线）| 主要现状口径来源 |
| Layer 3 | `reference/乐享券最低使用量改造.docx`（良品 PM 本期方案）| 仅在 §2.2 + §九 引用 |

**典型决策**：

- 扣款顺序：Layer 2 文档原文写"权益账本 > 兑换券 > 货款"，但 project owner 确认线上实际是"乐享券 > 货补/返利 > 现金"。
  - PRD 按线上口径写"乐享券 → 货补/返利 → 现金"
  - 不加文档勘误注释
  - 在 discussion_record 记录差异

### 4.4 "范围外" vs "未提及" 的区分

| 类型 | 含义 | 处理 |
|------|------|------|
| 范围外（out of scope） | 用户描述明示或追问后确认本期不改的功能 | 在 §5.x.1 识别边界中显式列出"沿用现状" |
| 未提及（not mentioned） | 用户描述未涉及、本 Skill 也未明确判定的功能 | 不写入 PRD（不主动列举无关内容）|

**关键差异**：范围外是**显式声明的边界**，未提及是**默认的沉默**。

## 改动点边界判定

### 5.1 单点 vs 多点

**判定标准**（满足任一即为"单点"）：

- 改动只涉及 1 个核心功能（如本次 V5 的"乐享券计算逻辑"）
- 改动跨越的章节 ≤ 1 章（如本次 V5 仅 §5.1）
- 改动总规模 ≤ 500 行 PRD 描述

**多点情况**：

- 跨章节改动 ≥ 2 章 → 仍可用本 Skill，但 §5 下开多个 §5.x 节
- 跨章节改动 ≥ 5 章 → 改用 prd-write rewrite 模式
- 多个改动点强耦合（必须同时实现，且互相依赖逻辑）→ 仍可用本 Skill，聚合为同一 §5.x 节

### 5.2 何时改用 prd-write

| 场景 | 改用 |
|------|------|
| 现状资产严重缺失（无法做"识别"步骤）| `prd-write` new 模式 |
| 改动范围 > 30% 现状 PRD | `prd-write` rewrite 模式 |
| 由评审会议 B 表驱动 | `prd-update-from-meeting` + `prd-write` incremental |
| 需要分簇执行 + 派生位置扫描 | `prd-write` incremental 模式 |
| 需要完整 9 章原型/线框图 | `prd-write` new 模式 |

### 5.3 边界场景

| 边界场景 | 处理 |
|---------|------|
| 改动点本来是 1 个，但实现时发现要联动改 2-3 处 | 仍用本 Skill；§5.x.3 受影响功能节中显式列出联动改动 |
| 改动点本来是 3 个，但其中 1 个改完发现要新建模型 | 该子项升级到独立 §5.x 节；新模型在 §5.x.3 显式声明 |
| 改动点边界一开始不清楚 | 在启动检测阶段就向用户追问；不要等动笔后才发现范围错 |
| 改动后发现要补充很多兜底/异常场景 | 兜底场景作为 §5.x.3 的子节或回归测试用例，不必升级 PRD 类型 |

## V5 PRD 实战样例

本节用 V5 PRD §5.1（"乐享券强制单行计算改造"）作为完整样例，逐节拆解三拍如何落地。

### 6.1 §5.1.1 现状描述 — 实战拆解

**结构**：

```markdown
#### 5.1.1 现状描述

**识别范围**：本期改动影响订单支付成功时点的各账本计费计算。具体半径覆盖：
① 良品下单 / 支付页的支付方式选项；
② 账款接收下单请求后的乐享券计算逻辑；
③ 账款的试算 / 冻结执行链路（实际扣款发生在发货时，本期不改动）；
④ 退款 / 少发出库 / 订单关闭场景中的乐享券处理。

**识别边界**（不在本期范围）：发货 / 退货 / 少发 / 订单关闭的业务流程主干、
状态机、账本类型表、客户闭户兜底、OA 货补档位申请流程 —— 这些功能本身不改动，
仅其中"乐享券部分"按本期新算法套入。

**现状逻辑**（截至 2026-05-18 线上生产口径）：

- 良品支付页：客户自主选择支付组合，可选 6 类：...
- 单 SKU 乐享券上限 = rounddown(SKU 数量 × 30%)；用户在 [0, 上限] 自主录入
- 货补/返利档位默认 30%，可通过 OA 申请提升至 50% 或 70%（仅 30/50/70 三档）
- 行间优先级：SKU 单价降序；相同单价按自然序号升序
- 单行内计算顺序：乐享券 → 货补/返利 → 现金
- 货款余额不允许扣负；最终若货款 < 0 则全单回滚，返回支付失败
- 计算路径：金蝶约束单 SKU 最小计量单位不可小数，所有金额计算最终须回到整数数量
- 退款 / 发货 / 少发 / 订单关闭场景的乐享券部分由账款随同其他账本一并扣减/回退
```

**关键设计**：

- 识别范围用 ①②③④ 编号子半径，让下游一眼看清半径覆盖
- 识别边界明确"功能本身不改动 + 仅 X 部分按新规套入"双重声明，避免歧义
- 现状逻辑仅 8 条 bullet 覆盖核心规则，不展开非相关内容

### 6.2 §5.1.2 需求改动前后对比 — 实战拆解

13 行对比表（见 [§比对表模板 §2.5](#25-v5-实战样例14-行)），其中包含：

- **9 行实质改动**（性质改变 / 数值变化 / 新增）
- **4 行声明性不变**（状态机 / 业务主干 / 行间顺序 / 单行内顺序）

**特殊设计**：

- 货补档位 × 乐享券比例联动**单独成行**（不与"比例"行合并），因为这是涉及多档位联动 + "档位 vs 实际占用"特殊概念区分的高密度信息
- "现状列"与"改动后列"都使用**相同的描述粒度**（不能现状写得很粗、改动后写得很细）

### 6.3 §5.1.3 具体迭代方案 — 实战拆解

6 个子节（见 [§动作的子节聚合骨架 §3.4](#34-v5-实战拆解)）：

#### 6.3.1 §5.1.3.1 算法

```markdown
##### 5.1.3.1 乐享券单行算法

**单行算法**（每个 SKU 独立执行，按 SKU 单价降序 / 相同序号升序的顺序处理）：

```
步骤 1：应付乐享券金额 = SKU 金额 × 乐享券比例
       其中：SKU 金额 = SKU 数量 × SKU 单价
            乐享券比例见 §5.1.3.2 联动表
步骤 2：应付乐享券数量 = rounddown(应付乐享券金额 ÷ SKU 单价)
步骤 3：实际乐享券抵扣金额 = 应付乐享券数量 × SKU 单价
```

> **金额→数量→金额回算的原因**：金蝶要求下游单 SKU 数量不可出现小数；
> 步骤 1 算出的金额本身可能非整除单价，必须经步骤 2 向下取整为数量后，
> 再用步骤 3 回算最终抵扣金额。

**对某行是否计算 20% 的判定**：

| 上游 coupons[] 中本 SKU 的情况 | 经销商货补档位 | 账款动作 |
|----------------------------|--------------|---------|
| 无任何券信息 | 任意档位 | 该行乐享券数量 = 0 |
| 有券信息 | 30% / 50% / 70% | 按本节算法算出"应付乐享券数量" |

> **多券由上游决定，账款只决定数量**：本次架构变化是良品已直接对接营销中台
> 查询券信息并选择券种，账款不再代理。但账款最终采用的数量以自己按本算法
> 算出的值为准，覆盖良品传入的数量值。理由：从良品下单到账款冻结之间
> 存在时间差（业务侧反馈最长可达 7 天），余额 / 券量 / 档位都可能变化。
```

**关键设计**：

- 算法本体用代码块（fenced code）展示，方便研发直接拷贝
- "为什么先算金额再算数量"用引用块嵌入，不拆独立子节
- 行级判定表内嵌，不升级为独立子节（V5 第一稿曾拆，聚合后效果更好）

#### 6.3.2 §5.1.3.2 联动表

简洁的 3 行表 + 1 段引用块说明。**不展开 OA 申请流程细节**（属于现状沿用，不在本期范围）。

#### 6.3.3 §5.1.3.3 时点模型

```markdown
| 时点 | 触发 | 账款动作 |
|------|------|---------|
| T1 试算 | 良品在下单前调用账款试算接口 | ① 完整跑算法... ② 查余量... ③ 余量够→返回试算结果；不够→返回乐享券数量=0 |
| T2 冻结 | 良品在下单支付时调用账款冻结接口 | ① 以 T1 试算结果为输入；② 再次查余量；③ 够→真正冻结；不够→阻断 |
```

**关键设计**：

- 触发条件 + 动作清单分两列，避免文字纠缠
- 引用块补充"广义口径"等扩展说明

#### 6.3.4 §5.1.3.4 接口规格

标准接口表（提供方/调用方/入参/出参）+ 取值规则代码块。引用块补充"接口字段、错误码、SLA 在联调阶段对齐"——这是迭代型 PRD 的常见处理：**不在 PRD 中锁死实现细节**。

#### 6.3.5 §5.1.3.5 受影响功能与沿用范围

7 行表（发货/退款代配送/退款非代配送/少发/订单关闭/客户闭户/状态机/OA），列出"现状 + 本期是否改动"。

**关键设计**：

- "本期是否改动"列**默认都写"主干不变"**，仅说明乐享券部分如何套入
- 完全不改动的功能（如客户闭户、状态机、OA）直接写"不改动，本 PRD 不展开"

#### 6.3.6 §5.1.3.6 回归测试要点

16 条 RT 用例。**覆盖维度**：

- 各档位（30/50/70）+ 有券/无券组合 → 5 条
- T1/T2 时间差非对称 → 2 条
- SKU 顺序 → 1 条
- 数量覆盖（上游传入 vs 账款算）→ 1 条
- 接口调用 → 1 条
- 发货/退货/少发/订单关闭 → 5 条
- 客户闭户 / 档位变更 → 2 条

## 与 prd-write incremental 模式的差异化定位

### 7.1 双层判定

**第一层**：本次任务是否适合用本 Skill？

```
是否有完整的现状资产？
    ├─ 否 → prd-write new 模式
    └─ 是 →
        改动规模 > 30% 现状 PRD？
            ├─ 是 → prd-write rewrite 模式
            └─ 否 →
                是否由评审会议 B 表驱动？
                    ├─ 是 → prd-update-from-meeting + prd-write incremental
                    └─ 否 →
                        是单点迭代场景吗？
                            ├─ 是 → 本 Skill ✓
                            └─ 否 → prd-write incremental（多点跨章节）
```

**第二层**：本 Skill 与 prd-write incremental 的本质差异

| 维度 | prd-write incremental | prd-incremental-on-asis |
|------|----------------------|------------------------|
| 输入 | 评审 B 表 / 修订意见清单 | 现状资产 + 用户口述/书面单点诉求 |
| 思路 | 已有 PRD 作为基线，按差异分簇改 | **现状（生产逻辑）**作为基线，单点切入 |
| 执行机制 | 分簇 + 簇间 reset + 派生位置扫描 | 三拍线性 + 现状融合 |
| 5.x 节内部结构 | 现状/业务流/类型节/案例/边界/逆向流程 | 现状描述/改动前后对比/具体迭代方案 |
| 模型重建倾向 | 中性（依 B 表） | 复用优先（非强制反对新建）|
| 质量自检 | changelog 同步、派生 8 类位置 | 复用查找证明、影响面声明、范围识别证明 |
| 典型规模 | 中-大（10-30+ 改动点）| 小（1-3 个改动点）|

### 7.2 协作可能性

虽然两个 Skill 独立并存，但实际项目中可能交替使用：

- 项目首版迭代 → 本 Skill 产出 V5
- V5 后续评审会议 → `prd-update-from-meeting` 出 B 表 → `prd-write` incremental 改 V5
- V5 + V5.1 + V5.2 累积到一定规模 → 整合为 V6（用 prd-write rewrite）

这种交替不需要 Skill 间显式衔接 —— 每个 Skill 输入只看现状资产 + 当前任务，互不依赖。

## 常见反模式与修正

### 反模式 1 — 把 5.x.3 拆得过细

**症状**：5.x.3 下有 7-9+ 个子节，每个子节内容只有几行。

**根因**：把"扩展说明" / "辅助证明" / "为什么这么设计"等内容都升为独立子节。

**修正**：

- 用 [§动作的子节聚合骨架 §3.3](#33-何时用--引用块而非独立子节) 的判定标准重新审视
- 把扩展说明用 `>` 引用块嵌入
- 聚合相关性强的子节（V5 第一稿从 9 节聚合到 6 节）

### 反模式 2 — 现状描述写成上一版 PRD 摘录

**症状**：5.x.1 把上一版 PRD 大段拷贝过来，包含本次改动半径外的内容。

**根因**：现状识别没做范围裁剪。

**修正**：

- 用关键词从上一版 PRD 中提取相关段落
- 删除与本次改动无关的内容
- 重新组织，按"用户操作→系统计算→数据流转→边界"顺序

### 反模式 3 — 对比表"现状列"留空

**症状**：5.x.2 对比表中"现状（改动前）"列写"—"或者空白。

**根因**：作者认为该维度"现状没有规则"。

**修正**：

- "现状无规则"也是现状的一种状态，应显式写"无显式策略"或"现状未涉及"
- 不允许留空 —— 留空会让读者困惑"是没有还是漏了"

### 反模式 4 — 影响面节遗漏功能

**症状**：5.x.3.5 受影响功能节中没列出某个其实被波及的功能，下游研发联调时发现。

**根因**：范围识别阶段没扫全。

**修正**：

- 在范围识别阶段就要把改动半径内的所有功能扫一遍
- 用现状资产中的功能清单做交叉验证（"上一版 PRD 的目录里这个功能改了吗？"）
- 影响面节宁可多列"不变"行，也不要漏

### 反模式 5 — 新引入模型未显式声明

**症状**：5.x.3 某段中出现"... 接口"、"... 字段"、"... 流程" 但未交代是新增还是复用。

**根因**：没遵守复用优先原则的反向声明义务。

**修正**：

- 凡是新引入的接口/字段/流程，在子节标题或开头**显式标注**"本期新引入 X"
- 凡是承接现存的接口/字段/流程，在描述中**显式标注**"沿用现存"
- 不允许中性表述（既没说新、也没说旧）

### 反模式 6 — OPEN 项过多

**症状**：8.3 OPEN 项有 10+ 条，各种"待澄清"、"待评估"。

**根因**：作者把所有不确定都丢进 OPEN 节，回避决策。

**修正**：

- OPEN 项仅列**研发评审 / 联调阶段的真实开放项**（如本次 V5 的"退款路径 A/B"、"minCoupon SLA 联调时对齐"）
- 业务层面的不确定 → 在本 PRD 起草阶段就向用户追问，不要留到 OPEN
- OPEN 项控制在 ≤ 5 条

### 反模式 7 — 重复 prd-write 的 5.x 节结构

**症状**：5.x 节按 prd-write 的"页面原型 / 业务流 / 类型专属节 / 正向案例 / 边界场景 / 逆向流程"结构展开，每个改动点都套这一整套。

**根因**：套用了不适合迭代型 PRD 的子节结构。

**修正**：

- 迭代型 PRD 的 5.x 节固定为**现状描述 / 改动前后对比 / 具体迭代方案**三拍
- 不需要"页面原型"（迭代型 PRD 通常不重画前端）
- 不需要"业务流"（业务流在现状描述节中说明）
- 不需要单独的"正向 / 边界 / 逆向案例"（这些已合并到回归测试要点中）

### 反模式 8 — 不写"声明性不变"行

**症状**：对比表只列"实质改动"行，不写"状态机 - 不变"这类声明性行。

**根因**：作者认为"不变"行没价值。

**修正**：

- "不变"行是 PRD 价值最高的部分之一 —— 它们告诉研发"不要碰这些功能"，避免误改
- 至少包含：状态机不变 / 业务主干不变 / 行间顺序不变 / 单行内顺序不变（如适用）
- 每个迭代型 PRD 的对比表中"不变"行应占 20-40%
