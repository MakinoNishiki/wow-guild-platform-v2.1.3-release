## ⚑ 路由自检（启动前必读）

本 Skill 与 `prd-write` 按 **PRD 类型** 分工，启动前先确认类型：
- **现状上下文充分、单点或小改动的迭代**（识别-比对-动作）→ 用本 Skill（prd-incremental-on-asis）
- **大型 / 从 0→1 建模 / 完整闭环 / 多改动点跨章节** → 移交 `prd-write`

用户已声明 PRD 类型则按声明路由；**未声明且无法从上下文明确判断时，主动提问确认类型后再开工**，不要默认。路由规则登记见 `the project governance entry`「project owner 的工作流」节。

## 快速开始

**何时使用本 Skill**：

- 项目已有线上生产系统在跑，存在大量可参照的现状逻辑、字段、流程、接口、配置
- 本次需求是**小规模 / 单点 / 增量诉求**（典型 1-3 个原子改动点）
- 改造性质是**功能微调 / 单点新增**，不需要重新建模、不需要重画完整闭环
- 用户明确表达"基于现状改"、"不要重做"、"复用优先"、"对现有功能做调整"

**何时改用其他 Skill**：

| 场景 | 改用 |
|------|------|
| 0→1 新建系统 / 新建模块 | `prd-write` new 模式 |
| 完整重写既有 PRD（>30% 改动） | `prd-write` rewrite 模式 |
| 评审会议纪要驱动的 PRD 增量改写 | `prd-update-from-meeting` → `prd-write` incremental |
| 改动点跨 5+ 章节、需大量分簇执行 | `prd-write` rewrite 或 incremental 模式 |
| 仅需 MRD 阶段产出 | `mrd-generation` |

**输入三件套**（启动必备，详见 [§启动检测](#启动检测)）：

1. **现状资产清单**：线上 PRD / 接口文档 / 数据库表结构 / 配置 / 历史会议纪要中的任一组合
2. **单点诉求列表**：每条带"来源 + 期望 + 约束"
3. **基线 PRD 路径**（可选）：项目若已有上一版 PRD 可作为 base 引用

**核心产物**：一份完整的、可独立交付的迭代型 PRD（`.md` 文件），9 章结构 + 5.x 节固定子结构（5.x.1 现状描述 / 5.x.2 改动前后对比 / 5.x.3 具体迭代方案）。

## Skill 定位

### 与 prd-write v3.0 的关系

**独立并存，非姊妹**。两者无串联依赖、无优先级关系，由用户根据需求规模和适用模型自选。

| 维度 | prd-write v3.0 incremental 模式 | prd-incremental-on-asis |
|------|------------------------------|------------------------|
| 输入主体 | 评审会议 B 表（PM 决策驱动）/ 已有 PRD 修订意见 | 现状资产 + 单点新诉求 |
| 思路前置 | 已有 PRD 作为基线 → 按差异分簇改 | **现状（生产逻辑）**作为基线 → 单点切入 |
| 改动半径 | 多改动点跨章节，需分簇执行（每簇 3-7 项） | 单点 / 少量改动点（典型 1-3 个）|
| 模型重建倾向 | 中性（依 B 表） | **复用优先**（不强制反对新建，倾向最小侵入） |
| 产物形态 | 完整改写后的 PRD（全 9 章） | 完整迭代型 PRD（全 9 章，但 §5 只写改动点）|
| 5.x 节内部结构 | 现状 / 业务流 / 类型节 / 案例 / 边界 / 逆向流程 | **现状描述 / 改动前后对比 / 具体迭代方案**（三拍固定结构） |
| 质量自检 | 含 changelog 同步、派生 8 类位置扫描 | 含复用查找证明、影响面声明、范围识别证明 |
| 执行机制 | 分簇 + 簇间 reset + 派生位置扫描 | 三拍线性 + 现状融合 |

### 本 Skill 的灵魂

1. **现状即基线**：不是"用户描述什么我写什么"，而是"先看现状是什么，再看用户描述对现状做什么调整"。
2. **复用优先**：默认查找现状是否已有可承接的字段/流程/状态/接口；找不到才考虑新增。**不强制反对新建模型**（含业务模型/数据流模型/流程），仅作为使用倾向 —— 有些需求的解决必须构建新模型，本 Skill 允许这种情况。
3. **范围识别先于动作**：在写"做什么"之前，先写清"改动影响哪些功能 / 不影响哪些功能"，避免范围漂移。
4. **比对显式化**：原方案是什么 / 现在改成什么，必须显式列在对比表中，不允许只写"改动后"而不交代"改动前"。
5. **最小侵入**：每个改动点优先选择对现状破坏最小的实现路径。

## 启动检测

新 Agent 接到"用本 Skill 写迭代型 PRD"任务时，**在动手前必须完成下列检测**。任一项缺失则向用户主动追问，不要凭空构造。

### 检测项 1 — 现状资产清单

**必备**。至少有 1 项明确的现状文档路径。常见形态：

| 现状形态 | 典型文件 / 来源 |
|---------|---------------|
| 线上 PRD | `reference/<上一版>.docx`、`docs/<上一版>.md` |
| 接口文档 | `reference/<接口契约>.md` / 内部知识库链接 |
| 数据库表结构 | DBA 维护的 ER 图 / DDL |
| 系统配置 | 配置中心截图、配置项清单 |
| 历史会议纪要 | `reference/meetingRecord/<日期>.docx` |
| 业务说明文档 | 业务方手写的 SOP / 说明文档 |
| 早期版本 PRD | 已归档的更早版本 |

**关键检查**：

- 若存在**多份现状文档版本不一致**，问用户"哪份是当前生产口径权威？"
- 若现状文档**与实际线上逻辑有出入**（如本次 V5 中 present_rules 文档把扣款顺序写反），询问用户以哪份为准
- 若**完全没有现状文档**，则本 Skill 不适用，建议改用 `prd-write` new 模式

### 检测项 2 — 单点诉求列表

**必备**。每条诉求至少包含三要素：

| 要素 | 说明 |
|------|------|
| 来源 | 上游 PM / 用户反馈 / 业务方需求 / 合规要求 / 数据问题等 |
| 期望 | 解决什么问题 / 支持什么新场景 |
| 约束 | 时间窗口 / 不能动什么 / 必须沿用什么 / 上下游约束 |

**关键检查**：

- 诉求**数量 > 5 个**或**改动跨 5+ 章节**时，提示用户考虑改用 `prd-write` rewrite 模式
- 诉求描述含糊（"优化下"、"调整一下"）→ 主动追问具体期望
- 多个诉求间存在**强耦合**（必须同时实现）→ 在 PRD 中聚合为同一 §5.x 节，不要拆分

### 检测项 3 — 基线 PRD 路径（可选）

**非必备**，但若存在，强烈建议明确：

- 上一版 PRD 文件位置
- 该 PRD 的封版状态（是否冻结？）
- 本次 V5 与上一版 PRD 的版本关系（继续追加 vs 独立新版本？）

### 检测完成后，向用户输出确认

格式建议：

```
## 启动检测确认

| 项 | 状态 |
|---|------|
| 现状资产 | <列出文档路径与角色> |
| 现状权威口径 | <用户确认的口径> |
| 单点诉求 | <清单+三要素> |
| 基线 PRD | <路径 / 或"无"> |
| 改动点预估数量 | <N 个，建议在 1-3 内> |
| 文件输出位置 | <docs/PRD_xxx_v5.md> |

请用户确认后开始。
```

## 三拍工作流（识别-比对-动作）

本 Skill 的核心方法论。每个改动点都按"识别 → 比对 → 动作"顺序产出。

### 第一拍 — 识别（Identification）

**输出位置**：§5.x.1 现状描述

**两个子任务**：

1. **逻辑识别**（What is the current logic?）
   - 从现状资产中提取与本次改动相关的现行逻辑
   - 多份资料冲突时按 [§现状融合规则](#现状融合规则) 处理
   - 描述粒度：覆盖本次改动半径内的所有现行规则，不主动列举范围外内容

2. **范围识别**（What's in scope, what's not?）
   - **识别范围**：本次改动**会影响**的功能 / 链路 / 接口 / 字段
   - **识别边界**：本次改动**不影响**的功能（明确声明"沿用现状"，避免下游研发误解为本期改动）

**关键规则**：

- 范围识别的**输入**是用户对需求的描述。要从用户描述中反推出影响半径，而不是先列影响半径再去匹配描述。
- 若识别到"用户描述中未提及但实际会被波及"的功能，必须显式写入范围识别，并向用户标注；不要装作没看到。

**示例**（来自 V5 §5.1.1）：

```markdown
**识别范围**：本期改动影响订单支付成功时点的各账本计费计算。具体半径覆盖：
① 良品下单/支付页的支付方式选项；
② 账款接收下单请求后的乐享券计算逻辑；
③ 账款的试算/冻结执行链路；
④ 退款/少发出库/订单关闭场景中的乐享券处理。

**识别边界**（不在本期范围）：发货/退货/少发/订单关闭的业务流程主干、
状态机、账本类型表、客户闭户兜底、OA 货补档位申请流程 —— 这些功能本身不改动，
仅其中"乐享券部分"按本期新算法套入。
```

### 第二拍 — 比对（Comparison）

**输出位置**：§5.x.2 需求改动前后对比

**核心要求**：用**一张对比表**显式列出每个维度上"现状（改动前）"与"改动后"的差异。

| 表格列 | 必备 | 内容 |
|--------|------|------|
| 维度 | ✓ | 一个原子功能点 / 字段 / 行为 |
| 现状（改动前） | ✓ | 当前生产口径下该维度的状态 |
| 改动后 | ✓ | 本次需求实现后该维度的状态 |

**关键规则**：

- **现状列不能为空**。如果某维度在现状中"无明确定义"，写"无显式策略"而不是留空
- **改动后列出现"不变"的行也保留**。这些"不变"项是声明性的，告诉研发"虽然在改动半径内但本期不动"
- 对比表行数控制在 **8-20 行**之间。少于 8 行可能漏维度，多于 20 行说明改动范围超出本 Skill 适用范围
- 比对**不写过程**，只写"前后状态"。过程留给第三拍

**示例**（来自 V5 §5.1.2，节选）：

| 维度 | 现状（改动前） | 改动后 |
|------|--------------|-------|
| 用户支付方式选项 | 6 类，含乐享券组合，可选 | 3 类，乐享券非用户选项 |
| 是否使用乐享券的决策方 | 用户主动勾选 | 系统强制判定 |
| 单 SKU 乐享券数量的性质 | 上限 = rounddown(数量 × 30%) | 强制等值 = 按金额 20% 算 |
| 行间优先级 | SKU 单价降序 | **不变** |
| 状态机 | 现行订单支付状态机 | **不变** |

### 第三拍 — 动作（Action）

**输出位置**：§5.x.3 具体迭代方案

**核心要求**：把"改动后"列的内容转化为可实现的动作描述。

**结构建议**（不强制，但 V5 实战验证有效）：

```
5.x.3 具体迭代方案
├ 5.x.3.1 <核心改动 1>（如算法/接口/规则的具体定义）
├ 5.x.3.2 <核心改动 2>
├ 5.x.3.3 <时点/流程模型>（如需）
├ 5.x.3.4 <新交付接口规格>（如需）
├ 5.x.3.5 受影响功能与沿用范围（影响面声明）
└ 5.x.3.6 回归测试要点
```

**关键规则**：

- **子节数量控制在 3-6 个**。**>6 个**说明改动点拆得太细，应聚合（参考 V5 第一稿教训：原 9 个子节聚合为 6 个后可读性显著提升）
- 扩展性说明（背景理由、辅助证明、风险提示）用 `>` 引用块嵌入相邻段落，**不拆独立标题**
- "影响面/沿用范围"节是 §5.x.3 的必备子节，把所有"业务主干不变 / 仅 X 部分按新规套入"的功能显式列出
- "回归测试要点"节是 §5.x.3 的必备子节，至少 10 条覆盖正向 + 异常 + 兼容场景

**为什么不直接用四段式（现状-诉求-改动-影响）？**

早期方案曾用过四段式：现状引用 / 诉求陈述 / 改动方案 / 影响面回归点。V5 第一稿验证后发现：

- 现状引用 + 影响面经常重叠（影响面里也要引现状）
- 诉求陈述与对比表"现状列"信息冗余
- 影响面单列为节会与改动方案脱节

**三拍范式**（识别-比对-动作）是四段式的进化版，把"诉求"内化到比对表中（用"现状 vs 改动后"两列直接显化诉求），把"影响面"作为"动作"节的子节（保证与改动方案同步演进），把"现状引用"升级为"现状描述 + 范围识别"（不只是引用，还要划边界）。

## 现状融合规则

当现状资产存在多份文档时，按以下规则融合：

### 规则 1 — 取重叠部分的最新版本

**场景**：早期 PRD（如 `old_rules.docx`）+ 当前生产 PRD（如 `present_rules.docx`）+ 良品方案（如本次 `乐享券最低使用量改造.docx`）三层共存。

**处理**：

- 三份资料中**都覆盖**的内容 → 取**最新版本**（通常是当前生产 PRD）的描述
- 仅在早期文档中提到、被后续版本**重写**过的内容 → **不引用早期描述**
- 仅在早期文档中提到、后续版本**未涉及**的内容（如基础账本表、退款分摊规则等基础设施）→ 保留早期描述

### 规则 2 — 文档与线上不一致时以线上为准

**场景**：现状 PRD 文档写的逻辑与实际线上系统实现不一致（V5 中遇到的真实情况：present_rules 把扣款顺序写成"权益账本 > 兑换券 > 货款"，但线上实际是"乐享券 > 货补返利 > 现金"）。

**处理**：

- 主动向用户确认权威口径
- PRD 中按用户确认的线上口径表述
- **不在 PRD 中加文档勘误注释**（避免冗余，让 PRD 干净）
- 在 `discussion_record.md` 或会话上下文中记录文档与线上的差异，供未来回溯

### 规则 3 — 不主动列举范围外内容

现状描述节**只描述与本次改动半径相关的现行逻辑**。不要为了"显得全面"而把现状资产里所有内容都搬进来。

**判断标准**：某条现状规则若被删除会不会影响读者理解本次改动？

- 会 → 保留
- 不会 → 删除

### 规则 4 — 良品/上游方案的引用方式

外部触发型文档（如本次良品 PM 出具的方案）不直接作为现状（它本身就是本次改动的诉求来源），而是：

- 在 §2.2 诉求来源节引用
- 在 §5.x.1 现状描述节中**仅引用与本期 PRD 强相关的部分**（不要把上游全文搬过来）
- 在 §九 参考资料中列出完整路径

## 复用优先原则

本 Skill 的核心使用倾向。**不是强制审查项**，但在写"动作"节时应优先按此原则选择实现路径。

### 复用查找清单

写每个改动点的"动作"前，按下列顺序问自己：

1. **现状是否已有可承接的字段**？（如本次 V5 的 minCoupon 接口出参 minCoupon 字段，沿用良品方案中已定义的字段命名）
2. **现状是否已有可承接的流程**？（如本次 V5 发货/退款/少发的业务主干完全沿用现状，仅"乐享券部分"套入新算法）
3. **现状是否已有可承接的状态机**？（如本次 V5 不引入新状态机，沿用账款现行订单支付状态机）
4. **现状是否已有可承接的接口**？（如本次 V5 账款 → 良品 → 营销中台的回写链路完全沿用，账款不直接对接营销中台）
5. **现状是否已有可承接的配置项**？（如本次 V5 经销商货补档位识别沿用现存配置，OA 申请流程沿用现存）

只有上述 5 项都答"否"，才考虑新建。

### 新建判定标准

允许新建的典型情况（不强制反对）：

- 现状确实无承接物，且承接物的引入对其他功能影响极小（如本次 V5 的 minCoupon 接口 —— 这是账款本期新交付的唯一接口）
- 现状承接物存在但语义不匹配，硬复用会引发更大的语义混乱
- 上游已经决定要新建（如良品 PM 方案中已明确需要新接口）

**警示**：新建模型 / 状态机 / 数据流时，必须在 §5.x.3 中**显式声明"本期新引入 X"**，并在 §5.x.3 受影响功能节中说明对现存功能的影响。

### 反例（V5 中显式避免的）

| 反例 | V5 中的实际处理 |
|------|---------------|
| 引入新状态机 | 显式声明"不引入新状态机，沿用账款现行订单支付状态机" |
| 引入新事件路由 | 显式声明"不沿用 phase1 事件路由设计" |
| 引入新账本类型 | 不引入；沿用现有 5 大账本（货款/账扣/货补/返利/乐享券） |
| 改动业务主干（发货/退货流程） | 业务主干不变；仅"乐享券部分"按新单行逻辑套入 |

## 9 章 PRD 结构 + 5.x 节固定子结构

### 9 章总览

| 章节 | 是否必填 | 内容要点 | 与 prd-write 的差异 |
|------|---------|---------|-------------------|
| 一、文档概要 | 必填 | 1.1 版本记录 / 1.2 功能范围 / 1.3 名词解释 | header 必含"PRD 类型: 迭代型"标注 + 基线引用层次说明 |
| 二、背景及目标 | 必填 | 2.1 现状 / 2.2 诉求来源 / 2.3 目标 / 2.4 不在本期目标 | 2.1 现状是全局粗粒度描述（与 §5.x.1 的细粒度互补）|
| 三、竞品分析 | 可省 | 单点迭代通常沿用上版 / 留白 | 多数情况下写"沿用上版，不重复展开" |
| 四、主逻辑 | 简写 | 一句话指向 §5（如"详见 §5.1"）| 不展开整体业务逻辑（已由现状 PRD 承接） |
| 五、方案详情 | **核心** | 每个改动点一个 §5.x 节（5.1 / 5.2 ...）| **§5.x 内部固定为三拍结构**，见下 |
| 六、迭代计划 | 必填 | 说明本 PRD 是迭代型，本期承载哪些改动点 | 标明本文件追加 5.x 的累积承载规则 |
| 七、运营计划 | 必填 | 7.1 权限 / 7.2 埋点 / 7.3 数仓（按需） | 单点迭代通常无新权限 |
| 八、沟通记录 | 必填 | 8.1 时间倒序 / 8.2 外部依赖 / 8.3 待澄清事项（OPEN）| 8.3 OPEN 项是迭代型 PRD 特色（多数研发细节留到联调） |
| 九、参考资料 | 必填 | 现状资产路径 + 上游触发源 + 不引用文档 | 显式列出"不引用"项（如本次的 v4.3-phase1）避免下游误用 |

### §5.x 节固定子结构（**本 Skill 的核心约束**）

每个改动点的 §5.x 节严格按以下三个子节结构：

```
### 5.x <改动点名称>

#### 5.x.1 现状描述
- 识别范围（覆盖什么）
- 识别边界（不覆盖什么）
- 现状逻辑（按现状融合规则提取的当前生产口径）

#### 5.x.2 需求改动前后对比
- 一张对比表（维度 / 现状 / 改动后），8-20 行

#### 5.x.3 具体迭代方案
- 5.x.3.1 ~ 5.x.3.6（3-6 个子节，按改动点性质聚合）
- 必含：受影响功能与沿用范围 + 回归测试要点
- 扩展说明用 > 引用块，不拆独立标题
```

**子标题名称强制锁定**：

- 5.x.1 **现状描述**（不可改写为"现状引用"、"识别"等其他名称）
- 5.x.2 **需求改动前后对比**（不可改写为"比对"、"差异"等）
- 5.x.3 **具体迭代方案**（不可改写为"动作"、"改动方案"等）

理由：迭代型 PRD 通常会被多个研发同事打开，子标题命名固定有助于建立"看见 5.x.1 就知道在讲现状"的肌肉记忆，降低阅读成本。

### 5.x 内 5.x.3 的子节数量控制

- **2-3 个子节**：单点改动且无新接口、无新流程模型 —— 风险：过简，可能漏影响面
- **3-6 个子节**：典型情况，建议默认采用 —— V5 §5.1.3 是 6 个子节
- **>6 个子节**：警示信号，需聚合（V5 第一稿曾拆到 9 个，聚合至 6 个后可读性显著提升）

## 质量自检清单

PRD 起草完成后，按下列清单逐项自检。任一项不达标则回到对应章节修订。

### 必查项

| # | 自检项 | 通过标准 |
|---|--------|---------|
| Q1 | header 五字段是否完整 | 更新日期、用途、owner、内容概述、目录索引全有 |
| Q2 | header 是否标注"PRD 类型: 迭代型" | 显式标注，便于下游识别 |
| Q3 | header 是否列出基线引用层次 | 列出现状资产 + 显式声明"不引用"哪些文档 |
| Q4 | tail 导航尾部是否完整 | 至少 5 条"如果你需要了解…→查阅→定位"|
| Q5 | §2.1 现状描述与 §5.x.1 是否一致 | 不冲突；§2.1 是粗粒度，§5.x.1 是细粒度 |
| Q6 | §5.x.1 是否同时包含识别范围 + 识别边界 | 两段都必须有 |
| Q7 | §5.x.2 对比表是否覆盖 8-20 行 | 不足说明漏维度，过多说明超出适用范围 |
| Q8 | §5.x.2 对比表"现状列"是否都填了 | 不可留空；空白维度用"无显式策略"或"现状未定义" |
| Q9 | §5.x.2 对比表是否包含"不变"行 | 把声明性的"业务主干不变"等显式列出 |
| Q10 | §5.x.3 子节数量是否在 3-6 之间 | 不在范围内需聚合或拆分 |
| Q11 | §5.x.3 是否含"受影响功能与沿用范围"节 | 必备 |
| Q12 | §5.x.3 是否含"回归测试要点"节 | 必备，至少 10 条 |
| Q13 | 扩展说明是否用 `>` 引用块而非独立标题 | 子节数量失控的常见原因是把扩展说明拆成节 |
| Q14 | §九 参考资料是否列出"不引用"项 | 避免下游误用历史文档 |
| Q15 | §8.3 OPEN 项是否合理 | 不要把所有不确定都丢进 OPEN，仅列研发评审/联调阶段的真实开放项 |

### 复用查找证明项（本 Skill 特色）

| # | 自检项 | 通过标准 |
|---|--------|---------|
| R1 | 是否在 §5.x.3 显式声明"不引入新状态机"（或必要时声明新引入）| 涉及状态变化的改动必须有此声明 |
| R2 | 是否在 §5.x.3 显式声明业务主干"不变"（或必要时说明改动）| 涉及发货/退款/订单关闭等主干流程的改动必须有此声明 |
| R3 | 现状已有字段/流程/接口的承接关系是否明确 | 不能出现"账款侧 ... 接口"而不指明是新接口还是承接现存的 |
| R4 | 新引入的模型/接口/字段是否都在 §5.x.3 显式列出 | 不允许"暗藏"新增 |

### 自检不通过的常见原因

1. **5.x.3 子节过多** → 把"接口规格"、"算法详细"、"时点模型"等拆成独立节。**修正**：聚合并把扩展说明改为 `>` 引用块
2. **现状描述写成了"上一版 PRD 摘录"** → 把上一版的内容大段拷贝过来。**修正**：只保留与本期改动半径相关的内容，删除范围外内容
3. **对比表只有"改动后"列填了**，现状列写"无"。**修正**：现状即使是空白也要写"无显式策略"或"现状未涉及"
4. **影响面节遗漏了某个功能**，下游研发联调时发现。**修正**：在范围识别阶段就要把改动半径内的所有功能扫一遍
5. **新引入模型未在 §5.x.3 显式声明** → 仅在某段中提及。**修正**：必须在子节标题或开头明示"本期新引入 X"

## 文件命名规范 + 上下游衔接

### 文件命名

| 形态 | 命名 |
|------|------|
| 项目首版 V5 | `docs/PRD_<system>_v5.md`（沿用项目已有命名规范，N 跟项目历史版本号）|
| 单点迭代追加（同一文件）| 在现有 V5 文件追加 §5.2 / §5.3 ... |
| 单点迭代拆分（独立 PRD）| `docs/PRD_<feature>_v1.md` 或 `docs/PRD_<system>_v{N+1}.md` |
| 评审差异文件 | `docs/prd/meeting_diff_PRD_v{X.Y}_{YYYYMMDD}.md`（由 `prd-update-from-meeting` Skill 产出，非本 Skill）|

### 上下游衔接

#### 上游

本 Skill 没有强制上游 Skill。常见上游输入形态：

- 用户口述需求（直接转化为本 Skill 的"单点诉求列表"输入）
- 上游 PM 出具的方案文档（如本次良品方案）
- 业务方反馈的优化点
- 数据问题排查结论
- 合规要求文件

**不要求**先做 brainstorming / project-scope-breakdown / mrd-generation / prd-prep —— 单点迭代场景下，这些前置 Skill 通常已经被现状资产覆盖。

#### 下游

本 Skill 产物 = 完整可独立交付的 PRD 文件。可直接进入：

- 研发评审 / 联调阶段
- 测试用例编写（基于 §5.x.3 回归测试要点）
- 上线计划制定

**不强制**走 prd-review / prd-split / TRD 等下游 Skill。单点迭代规模通常不需要这些重型流程。

### 与项目级文档的同步要求

本 Skill 产出 PRD 时，**必须同步更新**项目级文档（沿用元指令 #1 / #9 / #13）：

1. **`important_conclusion.md`**：如本次会话沉淀了新的关键概念区分（如"货补档位 vs 实际占用"），新增对应条目作为后续 PRD 沿用基线
2. **`agent_quickstart.md`**："当前状态"反映 V5 进度；"PRD 版本对照"增加 V5 行
3. **`agent_handoff.md`** §7：归档本次会话的关键前置知识
4. **`discussion_record.md`**：按元指令 #1 的索引制格式记录本次会话
