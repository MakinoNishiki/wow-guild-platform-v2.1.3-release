# MRD 文档整合 (MRD Integration)

> Version: 1.0 | Language: 简体中文 | License: Authorized portable distribution

## 快速开始

本 Skill 引导 Agent 将**多份模块级 MRD** 整合为一份统一的 MRD 文档，关键增量价值在于生成跨模块的概述章节（含核心模型设计、端到端链路），为决策层提供项目全貌。

**输入**：2+ 份已完成的模块级 MRD 文档 + 项目上下文文档（agent_handoff、important_conclusion 等）
**输出**：整合版 MRD（新文件）+ 关联文档更新。原始 MRD 文件保留不动。

```
上游 Skill（mrd-generation）              本 Skill（mrd-integration）
  设计共识 → 模块级 MRD ×N      →      结构分析 → 整合设计 → 概述生成 → 合并输出
```

整合文档结构模板见 [reference.md](reference.md)。

## 适用场景

- 项目包含多个模块，各模块已分别生成 MRD，需要统一视图
- 立项评审或高层汇报前需要展示项目全貌
- 需要跨模块的端到端场景演示

**前提**：至少 2 份模块级 MRD 已通过用户审核。如果 MRD 尚未生成，应先使用 `mrd-generation` Skill。

## 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **原文不动** | 源 MRD 文件保留不做任何改动，整合版是独立的新文件 |
| 2 | **概述即全貌** | §1 是整合版的核心增量价值——展示核心模型架构、端到端链路、分期策略、模块间数据流，这些是模块级 MRD 无法单独呈现的 |
| 3 | **重叠合并、独立保留** | 目标/用户/范围/风险等重叠章节合并去重；各模块的解决方案详述保留为独立章节 |
| 4 | **端到端串联** | 场景设计必须展示跨模块的完整链路（如：身份创建 → 属性同步 → 用户组匹配 → 角色分配 → 鉴权生效） |
| 5 | **术语统一** | 跨模块合并时，同一概念必须使用统一术语（发现不一致时标记并统一） |
| 6 | **溯源可查** | 整合版中的每个解决方案章节应标注内容来源（哪份源 MRD 的哪个章节） |

## 三阶段工作流

```
阶段 1              阶段 2              阶段 3
结构分析与整合设计  →  内容整合与概述生成  →  验证与文档闭环
      ↓                    ↓                    ↓
 源文件分析           §1概述 + 合并章节      质量自检 + 关联更新
 重叠/独立识别        端到端场景串联
 结构蓝图确认         解决方案章节组装
```

---

### 阶段 1：结构分析与整合设计

**目标**：分析所有源 MRD 的结构，识别重叠与独立内容，设计整合文档的章节蓝图。

**操作**：

**第 1 步：源文件全量阅读**

逐份阅读所有源 MRD，提取以下信息：

| 提取维度 | 说明 |
|---------|------|
| 章节结构 | 每份 MRD 的章节编号和标题 |
| 目标与指标 | 定性目标 + 量化指标的清单 |
| 用户角色 | 各模块定义的用户角色（注意同名不同义、异名同义） |
| 核心场景 | 场景清单（标注是否涉及跨模块交互） |
| 解决方案详述 | 各模块的核心设计点清单 |
| 范围与边界 | 纳入/排除/预留项 |
| 风险与依赖 | 依赖项和风险项 |

**第 2 步：重叠与独立分类**

将提取的内容分为两类：

| 类型 | 判定标准 | 整合策略 |
|------|---------|---------|
| **重叠内容** | 多份 MRD 中出现相同或高度相似的内容（如：同一个用户角色、同一个痛点、同一个依赖项） | 合并去重，保留最完整的描述 |
| **独立内容** | 仅属于某个模块的专属设计（如：某模块的解决方案详述、特有的技术选型） | 保留为独立章节，标注来源 |

注意事项：
- 用户角色合并时特别注意"角色名不同但实际指向同一类人"的情况（如"系统管理员"和"权限管理员"）
- 痛点合并时要区分"同一个痛点在不同层面的表现"和"完全不同的痛点"
- 场景合并时识别可以串联的跨模块场景（如"入职"在账号管理是创建主账号，在功能权限是默认授权——应合并为端到端入职全流程）

**第 3 步：结构蓝图设计**

基于分析结果，设计整合文档的章节结构（参考 [reference.md](reference.md) 模板）。关键决策点：

- §1 概述章节应包含哪些内容？（通常：业务现状、驱动力、核心模型架构、端到端链路、分期策略、结构导读）
- 解决方案章节如何组织？（通常：按模块分独立章节，如 §4 模块A、§5 模块B）
- 场景章节是否需要跨模块串联？（如果模块间有数据流关系，强烈建议串联）

**第 4 步：向用户确认结构蓝图**

将蓝图展示给用户，确认：
- [ ] 章节划分是否合理
- [ ] 是否有遗漏的跨模块关系
- [ ] §1 概述的覆盖范围是否符合预期

**自检**：
- 是否遗漏了某份源 MRD 的关键内容？
- 跨模块的数据流关系是否已完整识别？
- 术语是否统一？

**完成标志**：用户确认结构蓝图

---

### 阶段 2：内容整合与概述生成

**目标**：按蓝图生成整合版 MRD，重点产出 §1 概述章节。

**操作**：

**第 1 步：生成 §1 项目概述与核心模型设计（关键增量）**

§1 是整合版的核心增量价值。模块级 MRD 各自聚焦单一模块，无法呈现跨模块的全貌。§1 的目标是让决策层在阅读详细方案之前，先建立对整个系统的宏观理解。

§1 通常包含以下子章节：

| 子章节 | 内容 | 写作要点 |
|-------|------|---------|
| **业务现状与痛点** | 统一呈现所有模块面对的痛点 | 用表格对比"同一痛点在不同层面的表现"，而非按模块分别列举 |
| **驱动力与战略定位** | 项目的战略驱动力和定位 | 说明多个驱动力之间的张力和平衡策略 |
| **核心模型设计** | 整个系统的架构框架 | 用 ASCII 架构图展示模型全貌；标注每个模型对应文档的哪个章节；重点说明模型之间的数据流关系 |
| **端到端数据流** | 从输入到输出的完整链路 | 用一个具体正例（端到端场景）演示数据如何在模块间流转 |
| **分期策略** | 各期覆盖内容的全局视图 | 表格形式，标注"本文档覆盖"的范围 |
| **结构导读** | 指引读者如何阅读本文档 | 表格形式，每个章节一行（章节号、内容、读者关切） |

核心模型设计部分的写作规范：

```
核心模型设计的表达结构：

1. 框架总览图（ASCII）
   - 展示所有模型/模块及其层级关系
   - 标注数据流方向（用箭头）
   - 标注每个模型对应的文档章节

2. 模型与文档的对应关系（表格）
   | 模型 | 覆盖情况 | 对应章节 |

3. 端到端数据流图（ASCII）
   - 展示从上游系统到最终业务系统的完整数据流
   - 标注每个环节发生在哪个模块

4. 端到端正例（引用块）
   - 用一个具体场景（如"新人入职"）
   - 按时间顺序走完从身份创建到权限生效的全流程
   - 每个步骤标注发生在哪个章节
```

**第 2 步：合并重叠章节**

对每个重叠章节执行：

| 章节类型 | 合并策略 |
|---------|---------|
| **目标** | 按模块分组呈现，每个目标保留正反例。合并时检查是否有跨模块的目标（如"权限变更全程可追溯"可能同时涉及账号变更和角色变更） |
| **成功指标** | 用表格统一呈现，增加"模块"列标注指标所属模块 |
| **用户角色** | 合并同义角色（保留描述最完整的版本），合并后确保每个角色的"与系统的关系"覆盖所有模块 |
| **场景** | 识别可串联的跨模块场景（如入职=账号创建+权限分配），合并为端到端场景。模块专属场景保留但按旅程归组 |
| **范围边界** | 按模块分组，合并共有的排除项和预留项 |
| **风险依赖** | 去重后按风险等级排序。特别注意跨模块依赖（如"功能权限依赖统一账号平台的属性输出"） |

场景合并的判定规则：

```
判定是否合并场景：

Q1: 这两个场景描述的是同一个用户旅程的不同环节吗？
  → 是 → 合并为端到端场景，按时间顺序串联
  → 否 → 保留为独立场景

Q2: 合并后的场景是否比两个独立场景更有说服力？
  → 是 → 合并（例：入职=创建账号+分配权限 > 分开讲更完整）
  → 否 → 保留独立（例：密码重置 和 角色互斥 无关联，不合并）
```

**第 3 步：组装解决方案章节**

各模块的解决方案保留为独立章节（如 §4、§5）。操作要点：

- 保留源 MRD 中的完整内容（架构图、正反例、设计决策表格等）
- 章节开头标注内容来源（如："本章节完整内容源自 `MRD_xxx.md` §4"）
- 检查跨模块引用的准确性（如：功能权限引用了统一账号平台的属性输出，需确认引用的属性名、层级与 §4 一致）
- 根据整合文档的章节重新编号（源 MRD 中的 §4 可能变为整合版的 §5）

**第 4 步：生成文档头部和尾部**

- Header：包含整合说明（列出源文件清单、说明"原始文件保留不动"）
- Tail：文档关联关系表（包含所有源 MRD + 项目文档 + 上下游文档）

**完成标志**：整合版 MRD 全文生成完成

---

### 阶段 3：验证与文档闭环

**目标**：验证整合质量，更新关联文档。

**操作**：

**第 1 步：内容完整性检查**

| 检查项 | 操作 |
|-------|------|
| 源 MRD 内容覆盖 | 逐份源 MRD 检查，确认其核心内容（目标、解决方案、范围）均已在整合版中体现 |
| 概述章节质量 | §1 是否包含核心模型架构图、端到端数据流、分期策略、结构导读 |
| 端到端场景 | 是否有至少 1 个跨越所有模块的端到端正例 |
| 术语一致性 | 跨模块合并的内容中，同一概念是否使用相同术语 |
| 交叉引用准确性 | 章节间的交叉引用（如"详见 §4.3"）是否指向正确位置 |

**第 2 步：质量自检清单**

- [ ] §1 概述能让决策层在不阅读后续章节的情况下理解项目全貌
- [ ] 核心模型架构图清晰展示了模块间关系
- [ ] 端到端数据流有具体正例演示
- [ ] 目标章节的正反例完整、无遗漏
- [ ] 用户角色定义无重复、无遗漏
- [ ] 场景章节展示了跨模块的端到端旅程
- [ ] 解决方案章节标注了内容来源
- [ ] 范围与边界无遗漏（与各源 MRD 逐项比对）
- [ ] 风险与依赖无遗漏，且跨模块依赖已显式标注
- [ ] 文档关联关系表包含所有源文件

**第 3 步：关联文档更新**

| 文档 | 更新内容 |
|------|---------|
| `agent_handoff.md` | 更新目录结构、项目状态、文档关联关系 |
| `discussion_record.md` | 记录本轮整合过程的摘要 |
| 其他项目文档 | 按项目规则检查是否需要更新 |

**完成标志**：质量自检通过 + 关联文档全部更新

## 与上下游 Skill 的衔接

```
project-scope-breakdown          mrd-generation            mrd-integration
┌────────────────────┐     ┌──────────────────────┐    ┌───────────────────┐
│ 模糊需求 → 设计共识 │ ──→ │ 共识 → 模块级 MRD ×N │ ──→│ MRD ×N → 整合版 MRD│
└────────────────────┘     └──────────────────────┘    └───────────────────┘
                               重复 N 次（每模块一次）       整合一次
```

- **上游**：`mrd-generation` 的产出（2+ 份模块级 MRD）作为本 Skill 的输入
- **下游**：整合版 MRD 作为立项评审的统一输入，也是 PRD 阶段的上游文档
