# PRD 评审规则

> **适用范围**：公司全部业务线、全部需求类型的 PRD 文档评审
> **文档版本**：V3.0 | **创建日期**：2026-04-16 | **更新日期**：2026-04-22
> **目标**：通过标准化评审，确保 PRD 能直接支撑 TRD 编写、任务拆解、排期开发、测试用例设计和跨团队协作，不靠口头补充和线下对齐

## 二、评审说明

本规则供 AI 辅助评审使用，输出结果为草稿意见，须经人工复核后方可作为正式评审结论。

**评审步骤**：读取 PRD → 按第五章各维度逐项打分 → 检查第三章独立阻断项 → 计算综合分 → 判定结论 → 输出报告。

**需要重新评审的情况**：

- 核心流程主干路径发生变化
- 新增跨系统联动字段、状态或依赖
- 验收标准或上线范围发生实质性调整
- 评审通过后超过 30 天仍未开始排期

**可简化评审的情况**（仍须覆盖业务背景、范围与边界、验收标准三个维度）：

- 文案修改，无交互逻辑变化
- 已有字段展示调整，无新增规则
- 缺陷修复，无新增接口、状态、依赖

**不可简化评审的情况**：

- 跨系统联动
- 新增状态流转
- 新增核心字段或数据迁移
- 涉及合规、安全、权限、审计

## 三、独立阻断项

> 以下问题无论综合分多少，均不得判定为"通过"或"有条件通过"。

- 核心业务目标不清，无法判断需求价值
- 范围和边界缺失，无法确认影响面
- 核心流程主路径缺失，无法推导系统行为
- 关键规则/数据口径未定义，开发实现会产生歧义
- 验收标准缺失，测试无法定义通过条件
- 涉及跨系统同步，但失败补偿/责任归属未说明
- 涉及存量数据迁移，但未说明清洗规则、回滚方案或执行窗口
- 涉及权限、合规、审计、安全，但未说明控制措施
- 涉及性能/时效承诺，但无任何量化要求

---

## 四、评审维度与评分标准

每个维度满分 10 分，加权后得综合分。

| 维度 | 权重 | 核心问题 |
|------|:---:|----------|
| 业务背景与目标 | 10% | 为什么做，解决什么问题，成功标准是什么 |
| 范围与边界 | 10% | 做什么，不做什么，影响哪些系统/角色 |
| 页面/模块说明 | 10% | 在哪里改，页面路径、区域划分、字段归属是否明确 |
| 核心流程 | 15% | 主流程、分支流程、系统间数据流是否完整 |
| 关键字段与规则定义 | 15% | 字段字典、校验规则、联动逻辑是否完整可执行 |
| 异常与边界场景 | 10% | 失败路径、并发、驳回、幂等是否覆盖 |
| 状态流转规则 | 10% | 状态枚举、流转条件、终态、非法流转是否完整 |
| 验收标准 | 10% | 完成标准是否可验证、可测试 |
| 非功能与依赖风险 | 10% | 性能、时效、安全、外部依赖、数据迁移是否明确 |

> 若需求不涉及页面（如接口型、数据任务型），可将"页面/模块说明"理解为"接口契约/任务说明"。
> 非功能与依赖风险不单独影响主评分，但命中独立阻断项时直接判定不通过。

### 结论判定矩阵

| 条件 | 结论 |
|------|------|
| 综合分 ≥ 8，且无独立阻断项，且无高风险缺口 | **通过** |
| 综合分 6-7.9，且高风险缺口 ≤ 2，且无独立阻断项 | **有条件通过** |
| 综合分 < 6，或高风险缺口 > 2，或存在独立阻断项 | **不通过** |

## 五、各维度评审细则

### 5.1 业务背景与目标

**目的**：确保需求不是拍脑袋，开发和测试能理解"为什么要做这件事"。

**必须包含**：

- [ ] 现状描述：当前系统/流程存在什么问题
- [ ] 影响说明：不做或做错会带来什么后果（业务、数据、合规层面）
- [ ] 需求来源：业务提出方、触发事件、优先级依据
- [ ] 成功标准：做完之后怎么算成功（可衡量）

**评分参考**：

| 分数 | 标准 |
|------|------|
| 9-10 | 现状、影响、来源、成功标准均有明确说明，数据或案例佐证充分 |
| 7-8 | 四项均有，但部分描述较模糊 |
| 5-6 | 只有需求结论，缺少背景和影响说明 |
| < 5 | 没有任何背景，无法判断需求合理性 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 影响说明 | "影响业务流程" | "仓库字段缺失导致金蝶对账失败，每月人工核对耗时约 8 小时，存在漏账风险" |
| 成功标准 | "上线后效果更好" | "上线后仓库地址真实性核查通过率 ≥ 95%，法务纠纷中地址证明材料缺失问题归零" |

---

### 5.2 范围与边界

**目的**：明确"做什么"和"不做什么"，防止需求蔓延和影响面误判。

**必须包含**：

- [ ] 本次要做什么（功能范围）
- [ ] 本次明确不做什么（排除项）
- [ ] 影响系统、角色、业务范围
- [ ] 上下游依赖已标注

**常见问题**：

| 问题 | 说明 |
|------|------|
| 只说"新增功能X"，未说是否影响已有功能 | 高风险 |
| 改动涉及多系统，但未说明哪些系统本次不改 | 高风险 |
| 未说明依赖哪些上游数据或下游消费方 | 中风险 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 排除项 | （无） | "本次不改造金蝶档案结构，仅新增字段透传；不涉及历史数据的地址证明补录，存量仓库不要求补传" |
| 依赖标注 | "需要和其他系统联动" | "上游：OA 审批系统提供审批结果回调；下游：仓库主数据服务、金蝶、下游一张表（4h 定时同步）" |

---

### 5.3 页面/模块说明

**目的**：开发和测试能直接定位到具体位置，而不需要反复确认"在哪个页面"。

> 接口型、数据任务型需求：本维度理解为"接口契约/任务入口说明"，检查接口路径、调用方、入参出参结构。

**必须包含**：

- [ ] 页面路径或菜单位置（如：系统-模块-列表-详情）
- [ ] 页面区域划分（查询区、列表区、详情区、弹窗等）
- [ ] 每个区域的字段列表与展示规则
- [ ] 新增/变更/隐藏字段需分类说明，不得混写
- [ ] 涉及多端时，各端改造点需分别说明

**常见问题**：

| 问题 | 说明 |
|------|------|
| 只说"增加字段X"，未说在哪个页面的哪个区域 | 阻断 |
| 原型与文字规则不一致，没有说明以哪个为准 | 阻断 |
| 字段说明只写名称，未写类型、格式、展示规则 | 高风险 |
| 多系统改造点混写，无法分系统拆解 | 高风险 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 页面定位 | "在仓库管理页面增加字段" | "OP-主数据-仓库管理-仓库列表-详情页-基本信息区，新增「地址证明」字段" |
| 多端说明 | "OA 和 OP 都要改" | "OA 申请表：新增「地址证明」附件上传组件；OP 详情页：只读展示，不可编辑" |

---

### 5.4 核心流程

**目的**：明确业务主干路径和系统间数据流向，保障开发和测试的流程用例可以对齐。

**必须包含**：

- [ ] 业务流程图（泳道图或步骤描述均可）：谁发起 → 谁审批 → 谁接收 → 结果是什么
- [ ] 系统流程图/数据流向：数据在哪个系统产生 → 经过什么中间服务 → 最终落在哪里
- [ ] 主流程的成功路径（Happy Path）完整可追踪
- [ ] 关键分支路径（如不同申请类型对应不同字段规则）
- [ ] 跨系统联动触发条件（如审批通过后，哪些系统需要同步，顺序是什么）

**评分参考**：

| 分数 | 标准 |
|------|------|
| 9-10 | 主流程 + 分支 + 系统流均有，跨系统触发条件清晰 |
| 7-8 | 主流程完整，分支或系统流有缺失 |
| 5-6 | 只有文字描述，无流程图，分支路径不清 |
| < 5 | 流程说明严重缺失，无法推导数据流向 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 跨系统触发 | "审批通过后同步数据" | "OA 审批全部节点通过后，主数据服务同步推送，顺序：① 仓库服务（主记录写入）→ ② 金蝶（科目档案创建），仓库服务失败时阻断，不推送金蝶" |
| 分支路径 | "不同类型处理不同" | "仓库类型=自有仓：必须上传「房产证明」；仓库类型=租赁仓：必须上传「租赁合同」；两种类型附件存储路径不同" |

**流程图推荐格式**：建议使用 Mermaid `flowchart`、`sequenceDiagram`，可直接在文档中维护，避免图片不可读。

---

### 5.5 关键字段与规则定义

**目的**：字段和规则是需求落地的最小单元，定义不完整会导致前后端、接口层各自理解。

**字段字典必须包含**（新增或变更字段均需）：

| 属性 | 说明 |
|------|------|
| 字段名称 | 前端展示名称 |
| 字段编码 | 接口/数据库字段名（如 `whAddProof`） |
| 数据类型 | 文本 / 数值 / 附件 / 枚举 / 日期 等 |
| 是否必填 | 必填 / 非必填 / 条件必填（需说明条件） |
| 默认值 | 有则说明，无则写"无" |
| 长度/精度 | 字符串最大长度、数值精度（如两位小数） |
| 枚举值 | 枚举类型需列出所有值及含义 |
| 编辑权限 | 可编辑 / 只读 / 禁用（需说明各场景） |
| 显隐规则 | 在哪些条件下显示 / 隐藏 |
| 适用系统 | 适用的前端系统（如 OA / OP / 移动端） |
| 同步逻辑 | 字段在各系统间的同步方向和时机 |

**附件类字段额外必须说明**：

- [ ] 存储位置（如 OSS Bucket 路径）
- [ ] 接口传输结构（URL 数组 / 文件 ID 列表）
- [ ] 历史版本保留策略（只存最新 / 保留所有版本）
- [ ] 权限控制（谁可以上传 / 下载 / 删除）

**校验规则必须包含**：

- [ ] 字段级校验：必填、长度、格式、类型（每个字段逐一定义）
- [ ] 业务规则校验：跨字段联动、唯一性约束、状态前提条件
- [ ] 联动清空规则：A 字段变更后，哪些字段需要清空 / 重置，清空后是否阻断提交
- [ ] 提交时机校验：点击提交时触发 / 实时触发（onChange）
- [ ] 校验失败提示文案：前端提示文字（不得只写"提示错误"）

**评分参考**：

| 分数 | 标准 |
|------|------|
| 9-10 | 所有字段有完整字典表，校验规则无歧义，附件类有存储和权限说明 |
| 7-8 | 大部分字段完整，个别字段缺枚举或编辑权限；校验规则主干清晰 |
| 5-6 | 字段列表存在，但类型、必填、枚举等普遍缺失；校验规则不完整 |
| < 5 | 字段说明散落正文，无字典表，无法直接落库或写接口 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 枚举值 | "仓库类型：自有/租赁" | "仓库类型（whType）：枚举，1=自有仓，2=租赁仓，3=联营仓；适用系统：OA/OP；同步逻辑：OA 写入后实时同步至仓库服务，只读" |
| 条件必填+联动 | "地址证明条件必填，地址变更后清空" | "仓库类型=自有仓时必填；仓库地址发生变更时自动清空，清空后阻断提交，提示：「地址已变更，请重新上传地址证明」" |

### 5.6 异常与边界场景

**目的**：异常场景不写进需求，开发通常不会主动实现，导致测试阶段才发现大量缺陷。

**必须覆盖**：

- [ ] 接口调用失败：下游系统不可用时如何处理（报错提示 / 重试 / 降级）
- [ ] 数据推送失败：同步写入下游系统失败时的补偿机制
- [ ] 并发场景：两人同时操作同一条记录时如何处理（乐观锁 / 提示）
- [ ] 流程驳回/撤销：驳回后已变更的字段是否回滚，状态如何恢复
- [ ] 附件上传失败：用户提示内容，是否允许重传，是否阻断提交
- [ ] 重复提交：同一请求被提交两次时是否幂等

**评分参考**：

| 分数 | 标准 |
|------|------|
| 9-10 | 失败补偿、并发、幂等、驳回回滚均有明确说明 |
| 7-8 | 主要异常有覆盖，个别边界场景缺失 |
| 5-6 | 只有成功路径描述，异常路径基本缺失 |
| < 5 | 完全没有异常场景说明 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 推送失败 | "推送失败时提示用户" | "推送失败后立即重试 3 次（间隔 1s/3s/5s），3 次全部失败后触发飞书告警，OP 侧展示「同步异常」标签，人工介入处理" |
| 并发操作 | "并发时处理" | "两人同时编辑同一条记录时，后保存者提示「记录已被他人修改，请刷新后重试」，采用乐观锁（version 字段）实现" |

---

### 5.7 状态流转规则

**目的**：状态是跨系统协作的核心契约，不定义清楚会导致各系统对"当前是什么状态"理解不一致。

**必须包含**：

- [ ] 状态枚举清单：所有可能的状态值及其含义
- [ ] 初始状态：数据创建时默认是什么状态
- [ ] 流转条件：从状态 A 到状态 B 的触发条件（谁触发 / 满足什么条件）
- [ ] 流转动作：状态变更后系统需要做什么（通知 / 同步 / 写日志）
- [ ] 终态定义：哪些状态是终态，不可再流转
- [ ] 非法流转处理：在错误状态下触发操作时如何拦截

**推荐状态流转表格式**：

| 当前状态 | 触发事件 | 目标状态 | 触发条件 | 流转动作 |
|---------|---------|---------|---------|---------|
| 草稿 | 提交申请 | 审核中 | 必填字段完整 | 生成申请单号，推送审批流 |
| 审核中 | 审批通过 | 已生效 | 审批节点全通过 | 同步下游系统，写变更日志 |
| 审核中 | 审批驳回 | 已驳回 | 任一节点驳回 | 驳回原因写入，通知申请人 |
| 已生效 | 发起变更申请 | 变更审核中 | — | 锁定当前记录，生成变更单 |

**推荐状态图格式**：建议使用 Mermaid `stateDiagram-v2`，可直接在文档中维护，在线编辑器：https://mermaid.live/

**评分参考**：

| 分数 | 标准 |
|------|------|
| 9-10 | 状态枚举、流转表、终态、非法流转均有定义 |
| 7-8 | 主要流转路径完整，个别边界流转缺失 |
| 5-6 | 只有文字描述，无状态枚举表，无法穷举路径 |
| < 5 | 状态完全未定义或只有结论（如"审批通过后生效"）无细节 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 终态定义 | 未提及 | "「已作废」为终态，不可恢复，不可发起变更申请；后端接口收到已作废记录的修改请求时返回业务错误码" |
| 非法流转 | 未提及 | "「已驳回」状态下不可直接提交，必须先「撤回」回到草稿状态再重新提交，否则前端按钮置灰，后端拦截" |

### 5.8 验收标准

**目的**：验收标准决定了测试能否独立设计用例、QA 能否明确通过条件，缺失时测试只能靠猜。

**必须包含**：

- [ ] 功能完成标准：核心功能做完后什么状态算达标
- [ ] 异常路径验收标准：异常场景的预期表现是否可验证
- [ ] 数据结果验收标准：数据写入、同步后的预期状态可核查
- [ ] 回归范围：本次改动影响了哪些已有功能需要回归

**评分参考**：

| 分数 | 标准 |
|------|------|
| 9-10 | 功能、异常、数据三类验收标准均有，回归范围明确 |
| 7-8 | 主要功能有验收标准，异常或数据验收有缺失 |
| 5-6 | 只有模糊描述（如"功能正常"），无法指导测试用例设计 |
| < 5 | 完全没有验收标准，测试无法独立设计用例 |

**评分锚点示例**：

| 分数段 | 不达标写法 | 达标写法 |
|--------|----------|---------|
| 功能验收 | "地址证明上传功能正常" | "①物理形态=实体时，不上传地址证明无法提交，提示「自有仓类型必须上传地址证明」；②审批通过后 OP 详情页可查看地址证明附件，点击跳转附件预览页" |
| 数据验收 | "数据同步成功" | "OA 审批通过后 5 分钟内，仓库主数据服务、金蝶均可查到 whAddProof 字段；下游一张表在下次 4h 定时任务后同步到位" |

---

### 5.9 非功能与依赖风险

**目的**：非功能要求不写进需求，上线后往往在性能、安全、合规层面暴雷。

> 本维度**不纳入主评分**，但命中第三章"独立阻断项"（如涉及性能承诺但无量化要求）时，直接判定不通过。

**需关注项**：

- [ ] 同步时效要求（实时 / 准实时 / T+1）
- [ ] 性能要求（接口响应时间、批量处理上限）
- [ ] 安全/权限/审计要求
- [ ] 外部依赖（第三方服务、基础设施）
- [ ] 数据保留周期（变更日志、附件的保留时长）
- [ ] 上线风险与回滚预案

## 八、需求类型附录

> 公司级规范定义通用基线，具体评审时选定需求类型，追加对应附录的检查项。

### 8.1 中后台表单/流程型（重点参考本规范第五章细则）

**额外必须检查**：

- 页面路径、区域划分、字段归属（详见 5.3）
- 完整字段字典、状态流转表、校验规则（详见 5.5、5.7）
- 审批链路、驳回回滚、附件权限（详见 5.6）
- 多端差异与跨系统同步顺序（详见 5.4）

**适用场景**：主数据管理、审批流改造、中后台配置类页面

### 8.2 C 端交互型

**额外必须检查**：

- 用户旅程与关键转化漏斗
- 首屏、核心路径、弱网/中断体验
- 埋点口径与实验策略（A/B Test 分流规则）
- 文案、引导、降级与灰度策略

**适用场景**：App / 小程序活动页、下单支付注册转化流程、面向消费者的交互改版

### 8.3 数据任务/报表型

**额外必须检查**：

- 指标口径、统计周期、数据来源
- 任务调度频率、补数策略、失败重跑
- 明细口径与汇总口径一致性
- 权限隔离与导出限制

**适用场景**：数据报表、指标看板、ETL / 对账任务

### 8.4 平台能力/接口型

**额外必须检查**：

- 接口契约、调用方、兼容策略（向前兼容 / 版本管理）
- SLA、限流、熔断、重试策略
- 幂等、版本管理、错误码规范
- 上线切换与回滚预案

**适用场景**：通用平台能力、基础服务接口、供多系统复用的能力建设
