# prd-humanize 参考

## 一、本参考的定位

配合 `SKILL.md`（Part 1 内容构建 + Part 2 语言规范）使用，提供颗粒度决策规则与派生实战样例。

> v1.1 起**已移除"需-根-解-损"框架**。**v1.2 起**（据账本调整人类版定稿提炼）：标题用**简短功能名**（非"标题即需求"长句）；正文讲**现状规则**、**不写"从X改成Y"的 diff**、逐条清单叫"规则/特殊场景说明"（非"改动点"）；改动后形态**优先嵌真实原型/表格文件**（飞书 view/file、sheet），无稳定外部源再贴完整原文（禁省略）；规则型内容给**正例+反例**；背景**只讲触发动机+目标、不铺取舍**；未定项标"仍在确认中"+指向来源。
> **v1.3 起**（据两样例共性问题）：**改动后形态以引入现成素材为先**（原型 HTML/截图/可信文件，有则嵌入或引用+溯源、不自写——头号原则）；标题**禁"A：B"结构**；**默认省略"不做/不支持/不需要"负面排除项**；背景"提改动或不提"皆可、正反例"正例为主反例按需"（放松）；**逐字示例以本 reference 样例为准、不依赖公开市场 humanizer-zh**。详见 §六 样例 2。

## 二、颗粒度决策规则（人类版写到多细）

| 情形 | 现状/改动前 | 怎么呈现改动后 |
|------|-----------|--------------|
| 改动对象有确定形态（模板/表单/列表/表格） | 默认省略 | **直接放改动后全文/表样例** + 逐行改动点（+ 字段取值） |
| 改动是"基于现状的微调"，不看现状无法理解 | 补一句现状 | 现状→改动后简述 |
| 现状能从原型图/演示获得 | 不写（指向原型/演示） | 只说改成什么效果 |
| 纯逻辑/算法改动 | 默认省略 | 说"解决什么+大致怎么做"，算法细节索引完整版 |

**通则**：能少写就少写；改动后形态优先用"展示"（贴出来）而非"描述"（用文字绕）。

## 三、实战样例：国际对账函更新（完整版 v1.1 → 人类版）

### 3.1 输入

- 完整版：`PRD_international_reconciliation_letter_update_v1.md`（九章；§5.1 模板 / §5.2 账期 / §5.3 费用取数 / §5.4 冻结；含识别-比对-动作、对比表、回归用例、OPEN）。

### 3.3 关键改写对照

**§一 摘要**（塌缩）：版本/范围/名词三张表 → 4 行"本期只改国际对账，做四件事：①模板文案 ②账期加半年度 ③新增费用发生额期间表 ④未签署自动冻结账本"。

**§5.1 模板**（**承载方式二选一示范，§五 C**）：
- **对账函 → 引用外部源**：模板在契约锁配置合同模板、财务 docx 已含图与详述、外部源稳定 → 人类版只写"对账函模板在契约锁配置合同模板，内容参考 docx"，**不内嵌全文**（免双源维护，外部更新自动生效）。
- **对账邮件 → 贴纯净全文**：无即用外部源、需研发**直接复制粘贴** → 贴**完整邮件双语全文**（清掉冗余格式标记），其下 4 行改动点。**禁止省略打"……"**（这正是 v1.0 试点的错误）。

**§5.2 账期**（主谓宾端到端 + §五 D）：正文"对账平台前端新增半年度枚举值（年份+上/下半年）；财务在取数时人工筛客户范围、决定客户走季度还是半年度"——谁（前端/财务）做什么，讲完整；**补"不设默认值、本次不做季度/半年度优先级区分"（主动澄清防误解）**；**删"前端处理境内外关联"**（现状已实现，纯沿用不写）。

**§5.3 费用**（位置 + 表样例 + 字段取值）：①位置（表1 之后）；②表样例（2026 Q1，账结法下期初/期末 = 0）；③各字段取值逐条（期初=账期首月期初、本期增加/减少=账期区间借/贷汇总、期末=账期末日；金蝶按账期返回汇总不跨月求和）。算法/借贷映射细节索引完整版 §5.3.3。

**§5.4 冻结**（规则要素小表）：触发 / 冻结时点(发出+30天，6/18→7/18) / 冻结对象(账本=人民币+外币) / 冻结效果(不能动账) / 解禁(人工)——非散文，用小表逐要素列。

### 3.4 删了什么（噪音）

- 现状描述、改动前后对比表、影响面"沿用不变"罗列、回归用例、OPEN、警示块 → **全留完整版**，人类版不出现。
- 上线精确日期（归需求管理）、"非做不可"强调、会议来源/讨论过程、现状已实现的连带项 → 不进人类版。
- 结果：人类版主干一屏可扫读完，规格细节一字不少在完整版。

### 3.5 本样例体现的额外考量（对应 §五）

A 删"非做不可" ｜ B 删上线日期 ｜ C 对账函引用 + 邮件贴全文 ｜ D 加"不设默认值" ｜ E 口语→书面（拍板→沟通） ｜ F 落飞书用原生表格。

## 四、常见派生错误

1. **把完整版整段搬过来只删几句** → 仍臃肿。应按 Part 1 步骤（标题即需求 + 主谓宾端到端解决方案）重组，不是删减。
2. **引入完整版没有的新事实** → 破坏一致性。人类版只能是完整版的"降维投影"。
3. **改动后形态用文字绕** → 该贴模板/表样例时贴出来，别用一段话描述一张表。
4. **把动机/取舍铺到每个改动点** → 收到背景统一讲。
6. **改动后正文用"……"省略** → 模板/邮件/正文类必须贴完整原文，禁止删节省略（Part 1 步骤 5 硬约束）。

## 五、PRD 人类版的额外人工考量（实战沉淀）

> 以下是 SKILL.md 结构化要求**之外**、人工定稿时还会权衡的点，来自国际对账函人类版（飞书 `[document-link]`）的真实修订。不强制套用，作为派生与定稿的参考判断。

**A · PRD 语义约定：写进来 = 默认要做**（源：删"非做不可"）
PRD 里出现的内容默认就是"要做的"，**不靠纯文字强调必要性**（"非做不可""势在必行"）；要论证必要性，单独成点讲。**确定不做**的：打"待讨论"备注或直接删，不在 PRD 体现。

**B · 上线时间归需求管理**（源：删"7/9 上线"）
上线时间属**需求管理**范畴，与**功能设计**（PRD 本职）是两件事。PRD 不写精确上线日期，至多写**预计月份/计划**作大致参考。

**C · 改动后内容的承载方式：贴全文 vs 引用外部源**（源：对账函改引用 / 邮件贴全文）
改动后形态既可"贴完整原文"，也可"引用外部源"，按下列判据择一（**两者都禁止自行省略打"……"**）：
- **引用外部源** —— 当该内容有**稳定、权威、且呈现已充分**的外部源（如契约锁合同模板、财务 docx，已含图与详述），引用可**免去自己双源维护**，外部更新自动生效。
- **贴纯净全文** —— 当**无稳定外部源**，或需要"即取即用"（如邮件正文要研发**直接复制粘贴**），则把原文贴进来，并**清掉冗余格式标记**，保证可直接使用。

**D · 主动澄清防误解的边界**（源：加"不设置默认值"）
识别读者/研发**可能自行假设**的点（默认值、优先级、是否区分某两类），主动写明"无默认值""本次不做 X 区分"。
> 与 A 的区别：**A 是"功能整体不做 → 不写"；D 是"对要做的功能，补一句防误解的边界声明 → 要写"**。前者防"以为要做"，后者防"对要做的产生错误假设"。

**E · 口语 → 书面语**（源：拍板→沟通、一句话→解析）
定稿时把口语词转书面（拍板 → 确认/敲定、一句话 → 释义/解析）。与 Part 2 行文规范同向。

**F · 交付适配**（源：md 表格 → 飞书原生表格）
最终落到飞书等平台时，表格等用目标平台的原生格式呈现（非内容改动，呈现层适配）。
5. **保留回归用例清单** → 默认不进人类版。

## 六、实战样例 2：账本调整人类版（完整版 v1.4 → 人类版，v1.2 定稿）

> 来源：简道云流程迁移项目，完整版 `docs/PRD_账本调整.md` v1.4 → 人类版（飞书 `[document-link]`）。project owner 在 Agent 初版基础上亲改定稿，6 处改法即 v1.2 六项偏好的实证。

| # | Agent 初版（v1.1 写法）| project owner 定稿（v1.2 偏好）| 启示 |
|---|---------------------|---------------------|------|
| 1 背景 | 铺取舍清单（精简双表/只迁一个/罚款迁出/拆单）| 只留"简道云 11 月下线→避免阻断→迁 OA"+"目标=OA 提交审批+自动入账"| 背景**只讲动机+目标**，取舍不铺 |
| 2 标题 | "表单：一单把…说清"（**A：B 结构**，反面）| "OA 账本调整表单""审批流""账务处理"| 标题用**简短功能名**、**禁"A：B"结构**（人类不这么说明一件事）|
| 3 改动描述 | 逐条"改动点"含"三层→两层""取消金额矩阵" | 删 diff，改"流程特殊场景说明""审批流说明"（讲现状规则）| **不写 diff、讲现状规则** |
| 4 改动后形态 | ASCII/文字复述表单与审批链 | 飞书 `<view><file>` 嵌 prototype.html、`<sheet>` 嵌收集表 | **优先嵌真实文件** |
| 5 审批说明 | 偏重"取消了什么" | "直属上级必过/同人跳过/等级不低于直属上级"+**示例+反例（不应当发生）**| 规则型**给正例+反例** |
| 6 §5.3 未定项 | 摊开金蝶默认值表 | 改"账务处理"+嵌 sheet+"与财务的收集表，仍在确认中，后续补充"| 未定项**标确认中+指向来源** |

**典型对照（§5.2 审批说明，project owner 定稿原文）**：
> 1. 直属上级审批：必过。如果业务部门审批和直属上级相同，则自动跳过业务部门审批。
> 2. 业务部门审批：必过。与直属上级相同则自动跳过；会限制本节点审批人等级不低于直属上级。
>    - 示例：3 级部门负责人提交，直属上级是 2 级，审批通过后过特殊节点+财务，通过。
>    - 反例（不应当发生）：3 级提交，2 级批，然后 5 级在业务部门节点继续批。

读法：人类版讲"现在怎么运作 + 正反例"，不讲"相对旧版改了什么"；能嵌真东西就嵌，不文字复述。

**两样例最大共性教训（v1.3 头号原则）**：两版人类化**都只读了 PRD 原文、没引入 PRD 关联的辅助素材**——账本调整该嵌原型 HTML（流程表单/流程图）、国际入账有外部 docx + 可信链接可引全文。结果改动后形态不够清楚、不够人类化，根因是现成可信材料没被陈列、只能全盘自写。**正确做法**：启动时盘点完整版引用的原型/截图/可信文件（§1.3 步骤 5），派生时**直接引入**（嵌入或引用 + 溯源对应），引用对不对、要不要留人类确认时调；**不要因为"可能引错"就不收集**。
