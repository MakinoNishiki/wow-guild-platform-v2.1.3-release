## 快速开始

本 Skill 在三种场景下执行 PRD 编写/重写/改写：

- **new 模式**：基于 prd-prep 输出，从零编写 9 章 PRD
- **rewrite 模式**：基于现存 PRD + 重写决策，按章重写
- **incremental 模式**：基于 B 表 + PM 决策，分簇增量改写既有 PRD

三模式共享 9 章企业格式骨架与质量自检基线；按输入差异分支聚簇方式。

```
new 模式：    prd-prep → 本 Skill → 9章PRD全量 → 评审 / 原型
rewrite：     现存 PRD + 重写决策 → 本 Skill → 重写后 PRD + changelog
incremental： B 表 + PM 决策 → 本 Skill → 改写后 PRD + changelog
```

## 模式定位

| 项目 | new 模式 | rewrite 模式 | incremental 模式 |
|------|---------|-------------|-----------------|
| **触发** | 无 PRD，需新建 | 有 PRD 但 PM 决策推倒重来 | 有 PRD + B 表 + PM 决策（增量改）|
| **输入** | `prd_prep_{module}.md` + MRD | 旧 PRD + 重写决策 | B 表（来自 prd-update-from-meeting）+ PM 决策 |
| **聚簇方式** | 簇 = 9 章天然章节 | 簇 = 9 章 + 新决策合并 | 簇 = B 表语义聚类（grep 关键词共享 / 章节聚焦 ≤4 / 概念决策共享 / 语义转换共享，4 选 1）|
| **派生位置扫描** | 可跳过（除引用上游 MRD）| **强制**（8 类清单）| **强制**（8 类清单）|
| **簇大小约束** | 单簇 = 1 章（不强制 3-7 项）| 3-7 项 / 典型 5 | 3-7 项 / 典型 5 |
| **changelog** | 必须（v1.0 起点写首条，记录 PRD 初始落地）| 必须（元指令 #15）| 必须（元指令 #15）|
| **工作流入口** | §三阶段工作流 | §分簇执行工作流 | §分簇执行工作流 |

**模式判定（启动检测自动）**：
- 无目标 PRD 文件 + 有 prd_prep → new
- 有目标 PRD + 显式"重写"指令 → rewrite
- 有目标 PRD + B 表（frontmatter `generated-by: prd-update-from-meeting`）或显式"增量改写"指令 → incremental

## 启动检测

**启动前必须按顺序确认**（含模式判定）：

```
1. 从用户输入或对话上下文确认目标模块名 / 目标 PRD 路径
2. 模式判定：
       a. 检测目标 PRD 是否已存在
       b. 若不存在 + 找到 prd_prep_[module].md → new 模式
       c. 若存在 + 用户显式"重写" → rewrite 模式
       d. 若存在 + 提供 B 表（含 frontmatter `generated-by: prd-update-from-meeting`）
          或用户显式"增量改写" → incremental 模式
3. 按模式执行对应启动检测：
       new 模式：
           → 读取 prd_prep 文件（10 章），作为增强输入，进入§三阶段工作流
           → 若 prd_prep 未找到，呈现选项 A（先执行 prd-prep）/ B（从 MRD 直接生成）
           → PRD 落地后创建 `change_log/PRD_change_log.md` 并写入首条
             `yyyymmdd-0001 | PRD v1.0 初始落地 | 全章 | 决策来源：prd-prep 输出`
       rewrite 模式：
           → 读取旧 PRD 当前版本号 + §1.1 版本记录
           → 确认 PM 重写决策范围（全 9 章 / 部分章节）
           → 进入§分簇执行工作流
       incremental 模式：
           → 读取目标 PRD 当前版本号 + B 表（验证 PM 决策完整性）
           → 报告 B 表统计：条目总数、四象限分布、PM 已决策数
           → 进入§分簇执行工作流
4. 等待用户确认后，再开始执行
```

PM 决策未完成的 B 表条目（status: pending-pm-review）不进入本次改写，由 PM 补决策后另起会话。

## 三阶段工作流

> **适用模式**：new。rewrite / incremental 模式请跳转§分簇执行工作流。

### 阶段 1：读取基线（写作前必须执行）

| 顺序 | 文件 | 读取目的 |
|------|------|---------|
| 1 | `agent_handoff.md` | 项目全貌、元指令、当前阶段 |
| 2 | `important_conclusion.md` | 关键设计决策（影响方案详情写法） |
| 3 | MRD 对应章节 | 功能范围基线、非功能需求 |
| 4 | `prd_prep_{module}.md` | 场景矩阵、逆向流程、页面原型需求、类型专属规格、TBD 结论 |
| 5 | 相邻已完成 PRD（如有） | 统一体例和措辞风格 |

### 阶段 2：按章节顺序逐章写作

- 按一 → 九的顺序逐章编写
- 每章完成后在对话中输出，等待用户确认（或用户明确指示"连续生成"时可跳过逐章确认）
- 方案详情（第五章）按子模块逐节展开，每节完整写出固定结构（见§方案详情 5.x 节固定结构）

### 阶段 3：质量自检（全文写完后执行）

对照质量自检清单逐项检查，输出自检结果（通过/失败/N/A）。失败项必须就地修复后再交付。

### 阶段 4：changelog 首条落地（元指令 #15）

PRD v1.0 落地后必须创建 `change_log/PRD_change_log.md` 并写入首条记录：

```markdown
| 编号 | 改动摘要 | 影响章节 | 决策来源 |
|------|---------|---------|---------|
| yyyymmdd-0001 | PRD v1.0 初始落地 | 全章 | 决策来源：prd-prep 输出 + MRD §x.y |
```

后续任何 PRD 改动都在此基础上追加，编号续递。

## 分簇执行工作流 (rewrite / incremental 模式)

> **适用模式**：rewrite / incremental。new 模式请回§三阶段工作流。
>
> **设计目标**：避免长 PRD 串行改写时的"改源未改派生"偏移（参见经验包：sample_nonCash_20260512_prd_batching_experience.md / log_platform 4-27 现场回归数据）。

### 阶段一：聚簇分组

**聚簇维度**（取自 nonCash 经验包 §4.2，4 选 1 即构成同簇）：

| 维度 | 判定 |
|------|------|
| grep 关键词共享 | 同一字段名 / 状态码 / 概念词在多处需统一改 |
| 章节聚焦 ≤4 | 主战场触及不超过 4 个章节 |
| 概念决策共享 | 同一 PM 决策的多个落地点 |
| 语义转换共享 | 同类命名转换（如全文中英 → 中文化）|

**簇大小约束**：
- 下限 3 项（< 3 项合并到相邻簇）
- 典型 5 项
- 上限 7 项（> 7 项强制拆簇）

**簇数与 B 表规模的关系**（动态，不预设）：
- 小型 B 表（≤10 条）：2-3 簇
- 中型（20-30 条）：4-6 簇
- 大型（40+ 条）：7+ 簇，**强烈建议跨会话执行**（见§跨会话执行规则）

**产出**：簇清单（cluster_id / 簇主题 / B 表条目编号 / 主锚点章节 / 派生锚点候选）

### 阶段二：簇划分预演 + PM 抽查

会话内输出簇清单（Markdown 表），PM 抽查 1-2 个簇验证：
- 簇主题命名是否准确
- 是否漏分（某 B 表条目应入簇 A 实际入了簇 B）

PM 一次性通过或要求重分。**不逐簇问 Y/N**，避免确认负担。

### 阶段三：逐簇执行（核心，6 步循环）

每簇按以下 6 步执行：

```
①  Reset 重读
    - 显式输出："清空前簇上下文。重读 PRD §X.Y / §X.Z + 簇 N B 表条目"
    - 用 Read 工具按 offset+limit 仅读簇内涉及章节局部，不读全 PRD
    - 重读簇内 B 表条目 + PM 决策

②  派生位置扫描（强制，详见§派生位置 8 类清单）
    - 对簇内每个改动点，依§派生位置 8 类清单逐项 grep 扫描
    - 输出"派生位置清单"给 PM 一次性通过

③  改写
    - 主锚点 + 全部派生位置一次性改完
    - 边改边在会话上下文中记录改动锚点（用于簇内自检）

④  簇内自检（4 项快速检查）
    - [ ] 字段命名 / 状态码在簇内所有改动位置一致
    - [ ] grep 簇关键词，确认无残留旧值
    - [ ] 派生位置清单全部触达（无未改项）
    - [ ] index / 摘要 / 自检表同步

⑤  changelog 写入（元指令 #15）
    - 本簇所有改动按规范写入 PRD_change_log.md
    - 编号 yyyymmdd-NNNN，决策来源标注（B 表条目编号 + PM 决策）

⑥  簇间隔离信号
    - 输出固定句式："簇 N 完成，产出 X 处改动 + Y 条 changelog。进入簇 N+1 reset。"
    - 此句式作为模型上下文锚点，强制切换注意力
```

### 阶段四：全局收口自检（轻量）

所有簇完成后跑一遍轻量自检（**不强制耦合 prd-review**）：

| 检查项 | 方式 |
|-------|------|
| 跨簇遗漏 | grep 全文一次所有簇的核心关键词，确认零残留 |
| 跨簇一致性 | 字段命名 / 状态枚举 / 案例命名全文一致 |
| changelog 完整性 | changelog 条目数 ≥ B 表已决策条目数（incremental 模式）|
| 版本号更新 | §1.1 版本记录 + index 摘要同步 |

若发现跨簇遗漏，**新增补丁簇重走阶段三**，直至零残留。
若 PM 需要更深度自检，可在本 Skill 完成后另起会话单独调用 prd-review，**不在本工作流中强制耦合**。

### 阶段五：归档

- PRD 版本号 +0.x（小修）/ +1.0（大重构 / rewrite 模式）
- 更新 §1.1 版本记录 + index 摘要 + 自检表
- 输出归档清单：修改了哪些 PRD 文件 + changelog 条目编号区间
- 询问项目负责人是否另行授权 prd-split

## 派生位置 8 类清单

阶段三 ② 派生位置扫描的固定清单。每个 B 表改动点对以下 8 类位置全量扫描：

| 序号 | 类型 | 扫描方式 | 典型残留点 |
|------|------|---------|----------|
| a | **主章节 §x.y.z** | 已在 B 表锚点中 | — |
| b | **业务流 / 场景描述** | grep 业务流子节关键词 | §5.x.y 业务流子节描述未跟随 |
| c | **案例描述** | grep "案例" / "示例" / "例 1" 段 | 案例文案 / 字段值未更新 |
| d | **字段命名表 / 状态枚举表** | grep §3.x 字段表 / §5.x 状态表 | 字段名 / 状态码新旧并存 |
| e | **index 文件层级树 + 摘要 + 自检表** | 读 00_PRD_index_*.md 三处 | 层级树 / 摘要 / 自检表未同步 |
| f | **跨 PRD 引用** | grep 其他 PRD 文件中本字段 / 概念 | 多 PRD 项目中其他文件残留旧值 |
| g | **原型图（ASCII / Mermaid / 链接）** | grep 原型图段落 + 检查 mermaid 块 | 文字改了但原型图未跟随 |
| h | **概念表 / 名词解释** | grep §3.x 术语段 | 名词解释段未跟随 |

**优先级**：a / b / c / d / e 为高频残留点（log_platform 4-27 偏移现场全部命中）；f / g / h 视项目特性按需扫描。

**扫描成本控制**：每个改动点 8 类全量 grep，单次约 8 次 Grep 调用 + 1k token 输出，远低于全文重读成本。

## 跨会话执行规则

**触发条件**（任一即可触发跨会话）：
- B 表 ≥ 7 簇
- 预估总 token > 100k
- PRD 体量 > 5000 行（如 log_platform 8 个 PRD 文件场景）

**跨会话执行流程**：

```
会话 1：阶段一聚簇 + 阶段二 PM 抽查 + 阶段三簇 1-3
        归档：discussion_record / quickstart / handoff
        关键：handoff 中"当前状态"明确记录"簇 4-7 待续"

会话 2：cold start 读 quickstart → 直接进入阶段三簇 4-7
        + 阶段四全局自检 + 阶段五归档
```

跨会话归档严格遵守元指令 #13 顺序（含步骤 0 重读 + 步骤 ④ push 询问）。

**单簇 token 成本参考**：~13k（reset 3k + 扫描 2k + 改写 5k + 自检 2k + changelog 1k）。单会话内推荐执行 3-5 簇（保留 50% token 余量给 reset 和 PM 互动）。

## 文件命名规范

### PRD 输出文件（三模式共享）

```
project_doc/PRD_{module_name}.md
```

示例：
- `PRD_account_management.md`
- `PRD_feature_permission.md`
- `PRD_data_permission.md`

**版本号约定**：
- new 模式：首次落地 v1.0
- rewrite 模式：典型 +1.0 大重构（v1.0 → v2.0）
- incremental 模式：典型 +0.x 小修（v2.0 → v2.1）

文件路径不随版本号变化；版本号通过 PRD 内 §1.1 版本记录 + frontmatter 维护。

### 输入文件命名（按模式）

| 模式 | 输入文件 | 命名规范来源 |
|------|---------|------------|
| new | `project_doc/prd_prep_{module}.md` | 由 prd-prep Skill 输出，prd-prep v2.0 规范 |
| rewrite | `project_doc/PRD_{module}.md`（当前版本）+ 会话内 PM 重写决策 | 本 Skill；PM 决策不强制落盘 |
| incremental | `docs/prd/meeting_diff_PRD_v{from}_{YYYYMMDD}.md`（已归档 B 表）或会话内 B 表 + PM 决策 | 由 prd-update-from-meeting v1.0 输出，命名规范见该 Skill §文件命名规范 |

### changelog 文件（三模式共享）

```
change_log/PRD_change_log.md
```

每条 changelog 编号格式 `yyyymmdd-NNNN`，按时间顺序续递；元指令 #15 详细规范。

## 上下游衔接

### 三模式统一链路图

```
                  ┌─── new 模式 ───┐
                  │                │
project-scope-breakdown → mrd-generation → mrd-integration → prd-prep v2.0
                  │                                                ↓
                  │                                          prd-write v3.0（本 Skill）
                  └────────────────────────────────────────────────┤
                                                                   │
                  ┌─── rewrite 模式 ───┐                            │
                  │                    │                            │
                  旧 PRD + PM 重写决策 ───────────────────────────────┤
                                                                   │
                  ┌─── incremental 模式 ───┐                        │
                  │                        │                        │
评审会议纪要 → prd-update-from-meeting → B 表 + PM 决策 ─────────────┤
                                                                   ↓
                                              新 PRD 版本 + PRD_change_log
                                                                   ↓
                                            ┌───────────┬──────────┴────────┐
                                            ↓           ↓                   ↓
                                       研发评审    HTML 原型生成        prd-split
                                                   (Codex/其他)        (拆解版本)
```

### 各模式输入衔接

**new 模式 — 与 prd-prep 衔接**：
读取 `prd_prep_{module}.md` 全部 10 章（§1 功能边界 / §2 TBD 解析 / §3 场景矩阵 / §4 逆向流程 / §5 前端页面规格 / §6 无前端功能规格 / §7 外部依赖 / §8 异常降级 / §9 非功能需求 / §10 跨模块接口）。不额外访谈用户，基于 prd_prep 结论直接写作。TBD 项保留在 8.1 TBD 汇总表中。

**rewrite 模式 — 与旧 PRD + 重写决策衔接**：
读取目标 PRD 当前版本（§1.1 版本记录 + 全 9 章）+ PM 重写决策范围。聚簇维度：9 章天然章节 + 决策合并（决策影响多章时跨章聚簇）。重写后保持原 PRD 路径不变（覆盖），版本号 +1.0 大重构。

**incremental 模式 — 与 prd-update-from-meeting 衔接**：
读取 B 表（来自 prd-update-from-meeting v1.0，文件路径 `docs/prd/meeting_diff_PRD_v{from}_{YYYYMMDD}.md` 或会话内 B 表）+ PM 决策结论。验证 B 表 frontmatter `status: pm-reviewed`（PM 已决策）。回填 B 表 `target-version` 为新 PRD 版本号 + `status` 流转为 `consumed`。

### 下游衔接

**与 HTML 原型衔接**：5.x.1 页面原型（ASCII 线框图 + 字段规格 + 交互点规格）作为 HTML 原型的设计稿输入，交付给下游 Agent（如 Codex）。本 Skill 不生成 HTML。

**与 prd-split 衔接**：rewrite / incremental 模式产出的新 PRD 版本，若已有拆解版本（按模块/阶段拆分的衍生 PRD），归档前询问 project owner 是否同步触发 prd-split 重做拆解。

**与 prd-review 关系**：平行（不强制耦合）。prd-review 是 PRD 自身评分（9 维度打分），可在本 Skill 完成后独立调用。

### 完成后必须更新的文档（按模式）

**全模式通用**：
1. `discussion_record.md`：按元指令 #1 索引制写入本次会话条目
2. `agent_handoff.md`：更新项目状态（含"当前 PRD 版本号"+"待续簇"如跨会话）
3. `change_log/PRD_change_log.md`：按元指令 #15 写入本次改动条目（new 模式写 v1.0 首条 / rewrite / incremental 写本次改动）

**incremental 模式追加**：
4. 回填 B 表 frontmatter：`target-version` 填新版本号 + `status` 流转为 `consumed`
