## 一、背景与目的

当前系统里的游戏字典（团本清单、BOSS 清单、职业、专精、活动类型、赛季口径）全部是**写死在代码里的常量**。代价：魔兽世界每次版本更新（新团本、新赛季、大米轮换），我们都要改代码、走发版——12.1（S2 赛季 2026-08-13 开启、巢穴「潮缚石窟」、8.20 新团本「烈毒之渊」）近在眼前，这条路已经走到头了。

V2.2 的目标：**把游戏字典从代码常量搬进数据库主数据表，配一个超管维护页**。此后游戏更新 = 运营在维护页录数据，不再发版。

这是产品从"工具"走向"平台"的地基工程，8.8 必须上线（8.13 S2 开门要用它录新数据）。

## 四、数据模型（新建 `sql/10_master_data.sql`）

所有表公共要求：`id uuid primary key default gen_random_uuid()`、`created_at`/`updated_at` 时间戳、全公会可读（RLS select: authenticated）、仅超管可写（RLS insert/update/delete: `auth.jwt()->'app_metadata'->>'role' = 'superadmin'`）。

### 4.1 `game_patches` 游戏版本
| 列 | 类型 | 说明 |
|---|---|---|
| version | text unique not null | 如 `12.0`、`12.1` |
| name | text | 版本名（可空） |
| release_date | date | 上线日 |

### 4.2 `game_seasons` 赛季
| 列 | 类型 | 说明 |
|---|---|---|
| name | text not null | 如 `S1`、`S2` |
| patch_id | uuid → game_patches | 归属版本 |
| start_date | date not null | 赛季起点（S2 = 2026-08-13） |
| end_date | date | 可空 |
| is_current | boolean not null default false | **当前赛季标记，全表仅一行为 true** |

约束：`is_current=true` 部分唯一索引（`WHERE is_current`），保证同一时刻只有一个当前赛季——这是 REQ-018 赛季切换的权威数据源。

### 4.3 `game_raids` 团本（含巢穴）
| 列 | 类型 | 说明 |
|---|---|---|
| name | text not null | 如 `烈毒之渊`、`潮缚石窟` |
| season_id | uuid → game_seasons | 归属赛季 |
| type | text not null | `raid` 固定人数团本 / `lair` 巢穴弹性 / `dungeon` 大米（见 4.7 亦可独立，二选一，报告说明取舍） |
| min_players / max_players | int | raid=20/20；**lair=15/25** |
| max_difficulty | text | 如 `史诗` |
| open_date | date | 开放时间（烈毒之渊=2026-08-20） |
| sort_order | int | 展示排序 |

### 4.4 `game_bosses` BOSS
| 列 | 类型 | 说明 |
|---|---|---|
| raid_id | uuid → game_raids not null | 归属团本 |
| name | text not null | BOSS 名 |
| boss_order | int not null | 第几号（1-8） |
| unique(raid_id, boss_order) | | 防重 |

### 4.5 `boss_loot` 掉落池
| 列 | 类型 | 说明 |
|---|---|---|
| boss_id | uuid → game_bosses not null | |
| item_name | text not null | 装备名 |
| slot | text | 部位（武器/头/肩/胸/…/饰品） |
| item_type | text | 护甲类型/武器类型（可空） |
| official_item_id | int | 官方物品 ID（可空，后期对接用） |
| note | text | 备注（可空，如"稀有掉落"） |

### 4.6 `tier_sets` 职业套装
| 列 | 类型 | 说明 |
|---|---|---|
| season_id | uuid → game_seasons not null | |
| class_id | uuid → game_classes not null | |
| set_name | text not null | 如 `翡翠督军的统御` |
| bonus_2 / bonus_4 | text | 2 件/4 件效果（可空，一期可只录名字） |

### 4.7 `game_dungeons` 大秘境（赛季轮换）
| 列 | 类型 | 说明 |
|---|---|---|
| season_id | uuid → game_seasons not null | |
| name | text not null | 如 `毒牙祭坛` |
| is_new | boolean default false | 本赛季新本标记 |
| sort_order | int | |

### 4.8 `game_classes` 职业（初始数据=素材包字典数据.json）
| 列 | 类型 | 说明 |
|---|---|---|
| class_key | int unique not null | 官方 ID 1-13 |
| name_zh / name_en | text not null | 战士/warrior |
| color | text | 官方色值 `#C79C6E` |
| icon | text | 静态资源路径 `/assets/icons/classes/1-warrior.jpg` |

### 4.9 `game_specs` 专精（初始数据=字典数据.json）
| 列 | 类型 | 说明 |
|---|---|---|
| class_id | uuid → game_classes not null | |
| spec_key | int not null | 官方专精 ID |
| name_zh / name_en | text not null | |
| role | text not null | `TANK` / `HEALER` / `DAMAGE`（与英雄榜枚举对齐） |
| icon | text | 静态资源路径 |
| unique(class_id, spec_key) | | |

### 4.10 超管判定实现
- 运营账号（MakinoNishiki 注册邮箱）在 Supabase Dashboard → Authentication → 该用户 → `app_metadata` 写入 `{"role": "superadmin"}`（**此步为运营手动操作，写进交付清单**）；

## 五、维护页「数据中心」（新 tab，仅超管可见）

### 5.1 入口与权限
- 侧边栏新增 tab「数据中心」，图标可用数据库/齿轮意象；**仅超管可见**（非超管账号整个 tab 不渲染，不是置灰）；
- 普通成员无任何感知——这是后台设施，不是用户功能。

### 5.2 九个维护区块（每块一个子页签或锚段，UI 按现有规范四级按钮/表格/标签体系执行）
1. **版本**：列表 + 新增/编辑/删除；
2. **赛季**：列表 + CRUD + 「设为当前赛季」开关（翻牌时二次确认"将把 X 设为非当前"，确认后事务化：旧 false→新 true）；
3. **团本**：列表 + CRUD；type 下拉（固定团本/巢穴弹性/大秘境）；巢穴类型必填 min=15/max=25 并前端校验 min<max；
4. **BOSS**：按团本分组展示；新增 BOSS 时 boss_order 自动取 max+1 可改；
5. **掉落池**：按 团本→BOSS 两级导航进入；逐条 CRUD + **批量录入模式**（多行文本框，每行 `装备名,部位,类型`，解析预览后入库）——8.20 前录 8 个 BOSS 靠它，逐条点会点死人；
6. **套装**：按赛季×职业 13 行表格，直接格子内编辑套装名；
7. **大秘境**：按赛季分组，8 本 CRUD + 新本标记；
8. **职业**：13 行只读为主（官方数据），允许改 icon 路径/色值；
9. **专精**：按职业分组 40 行，只读为主 + icon/role 可改。

### 5.3 字典导入器（一次性工具，长期保留）
- 「数据中心」首页放「导入职业/专精字典」按钮：读取项目内 `字典数据.json`（素材包产物，已含 13 职业+40 专精+色值+职责），幂等 upsert 进 game_classes/game_specs（按 class_key/spec_key 冲突更新）；
- 按钮有 loading + 结果摘要（"职业 13 行 upsert 完成，专精 40 行 upsert 完成"）。

### 5.4 通用交互要求
- 所有删除二次确认；被引用的行（如有 BOSS 的团本）删除前级联提示"将同时删除 N 个 BOSS、M 条掉落"；
- 所有保存走按钮 loading 态（FIXED-023 状态机体系）；成功右上角 toast；
- 表格遵循 REQ-026/030 规范（.num 右对齐、斑马纹、表头吸顶、窄屏横滚保底）。

## 六、代码层改造：常量 → 主数据

1. **清点**：grep 全项目游戏字典常量（团本/BOSS/职业/专精/活动类型/赛季相关），报告里列完整清单（文件:行号），一个不留；
2. **加载层**：新增 `masterData.js`——启动时（登录选完公会后）并行拉 9 表，挂 `window.MasterData`；提供 `getRaids()` `getBosses(raidId)` `getClasses()` `getSpecs(classId)` `getCurrentSeason()` `getDungeons(seasonId)` `getLoot(bossId)` `getTierSets(seasonId)` 等访问函数；
3. **缓存与刷新**：内存缓存；维护页保存成功后调用方就地刷新缓存并 re-render 受影响视图；postgres_changes 实时订阅一期不做（种子阶段手动刷新够），代码留 TODO 注释；
4. **兜底快照**：构建时把当前常量固化为 `masterDataSnapshot.js`；主数据加载失败（离线/超时 5s）→ toast"游戏字典加载失败，已使用内置快照"→ 用快照继续，**系统任何页面不得白屏**；
5. **消费方逐页替换**：活动创建（团本/BOSS/人数上下限）、考勤记录、成员管理（职业/专精下拉）、装备管理、统计报表、智能导入 WCL（专精匹配）——报告逐页列替换点。

## 七、巢穴「潮缚石窟」兼容（随本任务书落地，不另立项）
