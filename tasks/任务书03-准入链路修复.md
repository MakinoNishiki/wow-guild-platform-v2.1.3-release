# 任务书 #3：准入链路修复（创建公会 / 加入公会 / 返回登录）

> 使用方式：将本文件放入项目 `tasks/` 目录，在 Kimi Code 中 @引用并发送"阅读任务书并严格执行"。
> 开工前先阅读 `docs/开发规范.md` 并遵守其全部条款（修改前输出清单、修改后 node --check + 修改报告）。

---

## 背景

项目已从 Coze 迁移到自建 Supabase。当前状态：

- ✅ 注册（Supabase Auth）已可用；
- ❌ 登录后"创建公会"按钮点击无任何反应（无提示、无跳转）；
- ❌ "返回登录"按钮点击无任何反应；
- ⚠️ "加入公会"按钮有响应（会校验邀请码非空），但因没有公会无法验证加入流程；
- 数据库：新 Supabase 项目，10 张表已存在但全部为空；建表 SQL 来源不明（可能是旧版 `sql/01_tables.sql`），**表结构与 v3.1.0 代码可能存在字段不匹配**（头号嫌疑：创建公会需写入 `server_region`、`server_name`、`invite_code` 等字段）。

数据链路：读 = 前端直连 Supabase REST（anon+JWT）；写 = 前端 → server.js `/api/db/rest/v1/*` 代理（service_role）→ Supabase。

## 任务内容

### 1. 脚本化复现与定位（先诊断，后动手）

写一个临时诊断脚本（放 `scripts/` 目录，用完保留），从 `.env` 读取密钥（禁止打印密钥），完成：

1. 通过 Auth API 注册一个测试用户（邮箱用 `test-diag@example.com` 之类明显标识），拿到 JWT；
2. 带着 JWT 调用 server.js 的写入代理创建公会，**抓取完整的 HTTP 状态码和错误响应体**；
3. 对比 `guilds` 表实际字段（通过 REST API 元数据或空插入试探）与代码中创建公会写入的字段清单，列出差异；
4. 定位"返回登录"按钮失效原因（前端事件绑定丢失 / JS 报错中断，读代码定位）。

诊断结论写入报告，**确认根因后再修复**；禁止不诊断直接改代码。

### 2. 修复（按诊断结果执行）

- 若根因是 **schema 字段缺失/不匹配**：不要改代码迁就错误表结构。产出增量迁移 SQL（`sql/02_fix_guilds_columns.sql` 之类，带版本号和说明），由运营到 SQL Editor 执行；代码侧仅在有明确 bug 时修复；
- 若根因是 **代码 bug**（代理转发、字段拼接、前端事件绑定等）：直接修复，范围仅限准入链路相关函数；
- 若前端写入失败**无任何错误提示**（"点了没反应"的帮凶）：在准入链路范围内补上最基本的失败提示（alert 或现有提示组件即可），不做全局错误处理改造（另案）。

### 3. 限制

- 只做本任务书范围内的改动；发现的其他问题记入报告"遗留问题"，不顺手修；
- 不触碰飞书同步、本地模式相关代码（已决定删除，另案处理）；
- 密钥只从 `.env` 读取，不打印、不提交；
- 诊断产生的测试数据（测试用户、测试公会）保留不删，由运营验收时核对。

### 4. 输出报告

按开发规范：修改文件清单、修改函数、修改原因、影响范围；`node --check` 结果；诊断根因结论；遗留问题清单；给运营的验收步骤。

## 运营验收步骤（修复完成后）

1. 如有增量 SQL：先到 Supabase SQL Editor 执行；
2. cmd 重启服务（`Ctrl + C` → `node server.js`）；
3. 浏览器开 `http://localhost:5000`，注册账号 A → 创建公会（区域+服务器+名称）→ **应看到成功反馈并进入主界面**；
4. 到 Supabase Table Editor 确认 `guilds` 表出现一行、`guild_members` 表出现 owner 一行；
5. 复制邀请码，退出登录，注册账号 B → 输入邀请码加入 → 应成功；账号 A 登录后应能看到成员 B；
6. "返回登录"按钮点击应正常返回；
7. 全部通过 → GitHub Desktop 提交存档（提交信息概括本次修复）。

## 验收标准

- 上述 7 步全部通过；
- 创建/加入公会失败时有明确错误提示，不再"点了没反应"；
- 无任务书外改动（git diff 可核对）。
