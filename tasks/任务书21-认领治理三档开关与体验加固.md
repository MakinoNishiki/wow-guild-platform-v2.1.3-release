## WP1：认领体验四件套（纯前端 + 一处侦察定案）

### 需求

1. **认领二次确认弹窗**
   - 成员列表点击「认领」不再立即生效，先弹确认框，确认才提交。
   - 弹窗内必须有「认领角色」用途说明，文案要点（可按 DESIGN.md 语气润色）：
     - 认领 = 把这个角色绑定到你的账号，先到先得，绑定后他人不可抢；
     - 绑定后，该角色的出勤率、装备、心愿会聚合到「用户中心 → 我的认领」；
     - 会长/管理（owner/editor）可以随时调整或解除认领；
     - 领错了可以自己「解除认领」，或找管理处理。
   - 现有 tooltip「认领为我的角色」并入弹窗说明，不再只依赖悬浮提示。

2. **「待认领」明示状态**
   - 未认领的行：把现在的单个金锁图标改为**明确的「待认领」可点击标签/按钮**（灰字或描边样式，符合 DESIGN.md），点击即弹出第 1 条的确认弹窗。
   - 已认领的行：显示「认领人：XXX」（可见性仍受 guilds.show_claimer_label 开关控制，行为不变）。
   - viewer 与 owner/editor 看到的「待认领/认领人」状态一致；管理操作按钮（编辑/离队/删除）仍只对 owner/editor 可见。

3. **公会设置「认领人标签」开关补用途说明**
   - 在「显示角色认领人标签（心愿单/装备分配列表）」开关下方加一行灰色小字说明：控制心愿单与装备分配列表里是否显示每个角色背后的认领人；关闭后仅管理者在成员管理中可见认领状态。
   - 同一次迭代，顺手把「认领人」指派入口在成员编辑弹窗里的位置做明显一点（加分组标题或说明文字「管理者可在此直接为成员指定认领人」），解决代派功能入口太深的问题。

4. **账号显示名单一真源（先侦察，再定案，再改）**
   - 侦察三项并写入报告：用户中心「显示名称」保存时写到哪里；页面右上角用户面板的名字读自哪里；guild_members.display_name 当前在哪些地方展示。
   - 定案倾向（无意外按此执行）：**账号显示名以 auth user_metadata.display_name 为唯一真源**——右上角用户面板、用户中心、以及其他所有展示账号名的地方统一读它；用户中心保存统一写它。
   - guild_members.display_name 若保留，仅作为「公会内昵称」，UI 上必须与账号显示名明确区分（不同文案、不同编辑入口）；若评估后决定下线其展示用途，需先把现存数据去向列清单给运营确认再动手。
   - 验收标准：在用户中心改名后，右上角**立即**（不依赖重新登录）显示新名字；刷新、换账号登录后依旧一致。

## WP2：认领治理三档公会开关（含 SQL 迁移 + server.js 升级 + 前端）

### 需求

1. **三种模式语义**
   - `free`（自由认领，默认）：现状。viewer 可自助认领未认领角色、可解绑自己；owner/editor 可代派。
   - `approval`（认领需审核）：viewer 点认领 → 生成**认领申请**（不直接生效），该成员对其显示「认领审核中」；owner/editor 在成员管理看到待审核列表（带角标），可批准（生效，写 raid_members.user_id）或拒绝。viewer 解绑自己已认领的角色不受限。
   - `assign`（仅管理者分配）：viewer 看不到认领入口（或点击提示「本公会由管理者统一分配认领」）；只有 owner/editor 通过编辑弹窗指派/调整/解除。
   - 公会设置新增「认领方式」三档选择，**仅 owner 可改**，每档配一行用途说明；存量公会一律默认 `free`，不改任何人的现状。

2. **SQL 迁移（单独一节，按既有纪律执行）**
   - `guilds` 加列：`claim_mode TEXT NOT NULL DEFAULT 'free'`，加 CHECK 约束限定 ('free','approval','assign')；
   - 新表 `claim_requests`：`id uuid pk default gen_random_uuid()`、`guild_id uuid not null references guilds(id) on delete cascade`、`member_id uuid not null references raid_members(id) on delete cascade`、`user_id uuid not null`、`status text not null default 'pending'`（pending/approved/rejected）、`resolved_by uuid`、`created_at/resolved_at timestamptz default now()`；
   - 部分唯一索引：同一 member_id 仅允许一条 pending（`create unique index ... on claim_requests(member_id) where status='pending'`）；
   - 参照既有业务表的 RLS 策略模式补齐 claim_requests 的读（申请人读自己的、owner/editor 读本公会的）；
   - **执行纪律**：迁移前先备份（guilds 全表导出到 backup/当日目录）→ 执行 → `NOTIFY pgrst, 'reload schema';` → REST 复核；任务书附**执行语句与回滚语句**（回滚=删表+删列）。

3. **server.js 升级**
   - 现有 viewer 窄例外（#19 WP1）保留并扩展：
     - 认领放行前多读一行 guilds.claim_mode：`free` 走现状；`assign` 拒绝并提示「本公会由管理者统一分配认领」；`approval` 不直写 raid_members，转而下一条；
     - 新增 claim_requests 的窄例外：viewer 可 INSERT，条件——请求体字段 ⊆ {guild_id, member_id, user_id}、body.user_id=本人、目标成员当前未认领、所在公会 claim_mode='approval'；不满足一律落通用分支（owner/editor 权力原样）；
     - claim_requests 的 PATCH/DELETE 走通用业务表分支（owner/editor 审批操作），viewer 只可撤回自己 pending 的申请（DELETE 且 user_id=本人，可选做，不做需在任务书说明）；
   - 批准认领时若目标成员已被抢先认领（并发），返回明确错误提示，不覆盖。

4. **前端**
   - 成员管理：approval 模式下申请人看到「认领审核中」状态；owner/editor 看到「认领审核」区块（待批数量角标 + 批准/拒绝按钮 + 申请人名字）；
   - 公会设置：认领方式三档（仅 owner 可见可改），配说明文案；
   - 审批结果：若既有通知系统可直接复用（notifications 表 + 既有未读数 RPC），给申请人发一条结果通知；若接入成本大，本期只做列表内状态可见，任务书报告里说明取舍；
   - assign 模式下 viewer 的认领入口隐藏；hover 提示归属说明。

5. **验证（全量附输出）**
   - 三模式 × （viewer 认领/解绑、owner 代派/审批）全矩阵 curl + 浏览器实测，含：free 不回归（复用并扩展 scripts/verify-viewer-claim.js）、approval 全生命周期（申请→审核中→批准生效/拒绝）、assign 下 viewer 403 且 owner 代派 200、并发抢批不覆盖；
   - SEC-001 回归脚本全过；
   - 迁移执行/回滚记录、备份路径；
   - **测试公会/测试账号/测试数据验收完自清理并复核为零**（沿用 #19 标准）。
