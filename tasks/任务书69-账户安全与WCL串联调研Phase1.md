## 二、子任务 1：当前账户体系审计

### 2.1 审计目标
摸清现有注册/登录/密码/会话机制的真实实现，识别高危风险点。

### 2.2 审计清单（逐项检查，出报告）

| # | 检查项 | 怎么查 | 期望输出 |
|---|--------|--------|----------|
| 1 | 密码存储方式 | 查 users 表 password 字段（或相关表）的存储格式 | 明文 / MD5 / SHA256 / bcrypt / argon2 / 其他？ |
| 2 | 密码是否加盐 | 同上看是否有 salt 字段或 salt 前缀 | 是 / 否 |
| 3 | session/token 机制 | 查登录后 cookie/localStorage 存什么，服务端如何校验 | JWT / session_id / 其他？过期时间？ |
| 4 | 登录失败处理 | 查登录接口是否有失败计数、锁定、验证码 | 有无防暴力破解机制 |
| 5 | 邀请码机制 | 查 invite_codes 表结构，是否可无限使用、是否有过期 | 结构 + 使用规则 |
| 6 | 权限校验 | 查 owner/editor/viewer 分级在哪些层校验（API / 前端路由 / 组件） | 校验层级清单 |
| 7 | 敏感操作日志 | 查是否有操作审计日志（登录、改密、改权限等） | 有 / 无，在哪张表 |

## 三、子任务 2：Supabase Auth 能力摸底

### 3.1 摸底目标
评估 Supabase Auth 开箱即用能力，判断接 Auth 的改动量和迁移成本。

### 3.2 摸底清单

| # | 检查项 | 怎么查 | 期望输出 |
|---|--------|--------|----------|
| 1 | Supabase 项目是否启用 Auth | 控制台 → Authentication → Providers | 是 / 否，已启用哪些 Provider |
| 2 | 邮箱+密码注册 | 文档 + 控制台测试 | 是否支持邮箱验证、密码重置、密码修改 |
| 3 | 现有用户迁移方案 | 文档研究 | 如何把现有用户（邀请码注册用户）迁移到 Supabase Auth（不丢失数据） |
| 4 | 自定义字段 | 文档研究 | Supabase Auth 是否支持在用户元数据里存 guild_id / role 等自定义字段 |
| 5 | RLS 兼容 | 文档研究 | 启用 Supabase Auth 后，现有 RLS 策略是否需要重写 |

## 四、子任务 3：WCL API 公会查询验证

### 4.1 验证目标
确认 WCL V2 API 的 `guildReports` 查询在国内网络环境下可用，摸清返回字段，为公会绑定功能提供技术可行性依据。

### 4.2 验证步骤

**步骤 1：获取 access_token**
- 用任务书 #11 里的 WCL_CLIENT_ID / WCL_CLIENT_SECRET（.env 里取，或让运营临时提供）
- POST `https://www.warcraftlogs.com/oauth/token`
- 验证是否能拿到 token，记录耗时

**步骤 2：guildReports 查询**
- 用截图中的 WCL 公会信息测试（或用户提供一个公开 WCL 公会）
- GraphQL 查询：

```graphql
query {
  reportData {
    guildReports(
      guildName: "公会名"
      serverName: "服务器名"
      serverRegion: "cn"
      page: 1
    ) {
      data {
        code
        title
        startTime
        endTime
        zone { name id }
        owner { name }
      }
      total
      current_page
      last_page
    }
  }
}
```

- 验证：国内网络是否可直连、返回数据结构、报告列表字段完整性

**步骤 3：公开报告解析**
- 从 guildReports 结果中取一个 report code
- 用任务书 #11 的 `reportData.report` 查询解析玩家列表和 fights
- 验证：公开报告无需额外权限即可解析
