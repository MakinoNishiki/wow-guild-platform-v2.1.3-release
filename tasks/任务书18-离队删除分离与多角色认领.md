## 背景与实测事实（运营侧已侦察，直接采信）

- 现状"删除成员=改成离队"，测试垃圾无法从名单清除（5 个纯数字测试成员已由运营手动清库）。
- **实测：硬删 raid_members 会级联删光该成员的 activity_attendance 与 wishlists 记录**（外键 ON DELETE CASCADE）。因此"真删除"必须先做历史计数校验，这是本设计的核心护栏，不是可选项。
- raid_members 已有 `user_id` 列（认领标记）；user_characters 一对多已原生支持。
- server.js 代理已放行 owner/editor 对 raid_members 的 DELETE、对 guilds 的 PATCH（仅 owner），WP1 不需要动后端。

## WP1：「离队」与「删除」分离（纯前端，app.js/index.html）

### 需求

1. 成员管理的成员行操作拆成两个独立动作：
   - **离队**：维持现有行为（PATCH status=离队），确认文案改为"离队后保留其全部历史记录，移出正式名单"。
   - **删除**：新增。点击后先并行计数该成员的 activity_attendance（member_id）、wishlists（member_id）、loot_records（character_id=该成员 id）：
     - **三项全 0** → 二次确认文案"将彻底删除该成员，不可恢复"→ DELETE raid_members → 从列表移除；
     - **任一 >0** → **拦截**，弹窗："该成员有 X 条考勤 / Y 条心愿单 / Z 条装备记录，删除会将这些历史一并清空且不可恢复。若该成员确实退会，请使用「离队」。"（只提示，不提供强删入口）
2. 已离队成员（筛选/分组视图）中同样提供「删除」，计数逻辑一致——方便日后清理误入的零历史垃圾。
3. viewer 角色看不到这两个按钮（沿现有权限显隐逻辑）。

### WP1 验收

- 零历史测试成员：可删除，删后库中 raid_members/attendance/wishlists 均无残留；
- 有历史成员（如 潮缚石窟 活动的出勤成员）：点删除必被拦截且文案数字准确；
- 离队行为与现有完全一致；viewer 无按钮。

### WP1 提交口径

标题：`任务书#18-WP1：成员管理「离队/删除」分离，删除加历史计数护栏`

## WP2：一用户多角色认领（前端为主 + 一处 SQL 迁移）

### 先侦察后动手（结论写进报告）

1. 查 `sql/` 目录里 raid_members 的建表语句：`user_id` 或 `(guild_id, user_id)` 上是否有 UNIQUE 约束/唯一索引——有则在迁移 SQL 里一并 DROP；
2. 找出当前"认领"入口与"已认领一个就限制再认领"的具体代码位置（前端判断？接口？）；
3. 找出所有"按 user_id 反查 member"的代码点（我的考勤/我的装备/心愿单/统计），标注哪些假设了"一个用户只对应一个成员"；
4. **查明 loot_records.character_id 的真实指向**（raid_members 还是 user_characters）——认领人标签的取数路径取决于此，接错线会显示错误认领人。

### 需求

**R1 多认领**：一个用户在同一公会可认领多个 raid_members（大号+小号）；每个成员仍只能被一个用户认领（user_id 单值，先到先得，已认领的显示认领人且他人不可抢）。解除认领对每个已认领成员单独可用；owner/editor 可为成员指定/调整认领人（沿现有编辑权限）。

**R2 个人视角聚合**：我的考勤/装备/心愿单等按 `user_id=我` 的全部已认领成员聚合取数；当前按单成员取数的视图全部改造。

**R3 用户中心「我的认领」区块**（展示 + 解绑，轻耦合）：
- 逐条展示：角色名、职业/专精、所属公会、公会所在区服（取 guilds 的 server_region/server_name，raid_members 本身不带服务器字段）、在队状态；
- 每条带「解除认领」按钮（只能解自己的，confirmed 后清空该成员 user_id）；
- 认领动作不放这里——认领仍发生在公会语境（成员管理/名单页）。

**R4 认领人标签 + 公会级开关（含 SQL 迁移）**：
- 心愿单列表、装备获取（loot_records）列表：角色名旁加灰色小字辅助标签——"认领人：XXX"或"未认领"；不喧宾夺主；
- **可见性由公会自治**：guilds 表新增布尔列（建议名 `show_claimer_label`，默认 true），公会设置页加开关"显示角色认领人标签"，仅 owner 可改（server.js 现有 guilds PATCH owner-only 已覆盖）；
- 前端读取本公会该字段决定渲染与否；开关关闭时两个列表不渲染标签；
- SQL 迁移 = ALTER TABLE guilds 加列（+ WP2 侦察项 1 的唯一约束 DROP，如有）。**迁移单独一步执行：先触发一次手动备份 → 执行 → 报告附执行与回滚语句。**

**R5 管理操作不受影响**：考勤录入、装备分配按 member 维度，天然兼容，不得改坏。

### WP2 验收

- 用户 A 在同一公会认领甲、乙两个成员成功；第三人无法认领甲；
- A 的个人视角看到甲、乙的考勤/装备聚合数据；
- A 在用户中心「我的认领」看到甲、乙（公会、区服、状态正确），解绑乙后乙回到"未认领"，他人可认领；
- 开关开：心愿单/装备列表显示认领人标签（含"未认领"态）；开关关：两处标签消失；viewer 看不到公会设置里的开关；
- 迁移执行后回滚语句演练过（或至少报告给出并经运营过目）。
