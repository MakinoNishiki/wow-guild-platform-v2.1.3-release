## 一、SEC-001：代理层公会级鉴权

### 现状风险

所有写操作经 server.js `/api/db/rest/v1/*` 代理以 service_role 执行，RLS 被绕过；代理目前只验证 JWT 有效性，**不校验"该用户是否有权写这个目标公会的数据"**。任何登录用户构造请求即可篡改任意公会数据。

### 设计要求

先输出**鉴权设计**（规则映射表 + 实现方案），确认思路清晰后再实现：

1. 代理收到写请求后：验证 JWT → 确定目标 guild_id → 查 `guild_members` 确认该用户身份与角色 → owner/editor 放行，viewer 或非成员返回 403；
2. 目标 guild_id 的确定规则要显式列出：请求体含 guild_id 的表直接用；`activity_attendance` 等无 guild_id 的表需联查父表（activities）取得；
3. 例外清单（不走公会鉴权，走自身规则）：
   - `guilds` INSERT：任何登录用户可创建；
   - `guild_members` 角色变更/删除：仅 owner；用户删除自己的成员行（退出公会）允许；
   - `user_profiles` / `user_characters` / `notifications`：仅限本人 user_id；
4. 鉴权逻辑做成 server.js 内的统一中间件/函数，不在每个分支里复制粘贴；
5. 鉴权失败返回 403 + 中文错误信息，前端能展示。

### 验证（脚本实证，写入报告）

写 `scripts/verify-authz.js`，至少覆盖：
- 公会 A 的 owner/editor 写 A 公会数据 → 201；
- 公会 A 的 viewer 写 A 公会数据 → 403；
- 公会 A 成员写公会 B 数据 → 403；
- 无 JWT / 伪造 JWT → 401；
- 本人写自己的 user_characters → 201；写他人的 → 403。
