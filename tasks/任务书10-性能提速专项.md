# 任务书 #10：性能提速专项（保存/删除延迟治理）

> 使用方式：放入项目 `tasks/` 目录，Kimi Code 中 @引用并发送"阅读任务书并严格执行"。
> 开工前先读 `docs/开发规范.md`。铁律：**先计时诊断、用数据说话、再优化；禁止做"假成功"乐观更新**（BUG-004 的教训）。

---

## 零、顺手项

全站"批量导入"文案更名为"**智能导入**"（按钮、弹窗标题、提示语）。

## 一、计时诊断（先出数据）

给关键写路径加计时（server.js 日志 + 前端 console.time），覆盖：保存成员、保存活动、保存装备、删除活动、批量导入 5 个场景，分解到：

| 环节 | 位置 |
|---|---|
| JWT 验证 | server.js |
| 鉴权联查（guild_members 查询） | server.js |
| 转发写入 Supabase | server.js → Supabase |
| reload 数据重拉（分表计时） | 前端 |
| render 渲染 | 前端 |

输出**耗时分解表**（每环节 ms），找出最大的 1-2 个瓶颈，写进报告后再动手。

## 二、优化方向（按诊断结果取舍，不必全做）

1. **server.js 缓存层**：
   - JWT 验证结果短 TTL 缓存（如 60 秒，按 token 缓存）；
   - 鉴权联查缓存（user+guild → 角色，TTL 60–300 秒）；该用户/公会发生写操作或成员变更后立即失效——缓存失效策略必须写进代码注释，安全优先于速度；
2. **前端增量 reload**：cloudCrud 写入成功后，只重拉变动表（及明确关联的表），不再全量 10 表重拉；render 防抖；
3. **按钮 loading 态**：保存/删除按钮点击后立即置 loading（防重复点击、等待有感知），完成后恢复；
4. 诊断若发现其他瓶颈（如串行可并行化），在报告中说明后处理。

## 三、目标与约束

- 目标：常规保存/删除 **P95 体感 < 1 秒**（以计时日志对比优化前后）；
- 不破坏 cloudCrud 数据流（写→reload→render 顺序不变，只让每环更快）；
- 不做假成功：所有提示仍以真实请求结果为准；
- 安全红线：鉴权缓存不得导致权限变更延迟生效超过 TTL，报告中专项说明。

## 四、验证

- `node --check` 全过；
- `node scripts/verify-authz.js` 26/26 回归（缓存不能破坏鉴权正确性——含"viewer 写入仍 403"的缓存场景）；
- 优化前后耗时分解对比表。

## 运营验收步骤

1. 重启服务，分别保存成员、创建活动、添加装备、删除活动各 2 次，体感应明显变快（1 秒上下）；
2. 保存时按钮有 loading 状态，不会重复提交；
3. viewer 账号操作仍被正确拦截（鉴权缓存没放行坏人）；
4. "批量导入"已改名"智能导入"；
5. 全过后 GitHub Desktop 提交存档。
