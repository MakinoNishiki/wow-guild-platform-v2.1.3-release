## 一、背景与目标

当前线上架构：前端 ddctl.com（美国服务器，HTTPS）+ Supabase 云（海外机房，数据库/鉴权/API）。
国内用户写入频繁 524 超时（跨太平洋链路），REQ-035 立项迁移。

**目标**：将 Supabase 云整体迁移至国内服务器（腾讯云上海 101.35.124.22，Ubuntu 24.04，4核4G/60G/月流量500G），以 Docker 自托管 Supabase 开源版原样落地，**业务代码零重写**，迁移后：

1. 国内用户读写不再跨太平洋，524 根治；
2. 老用户登录态保留（复用原 JWT_SECRET，全员免重登）；
3. 数据一行不丢（逐表对账）；
4. 可随时回退（旧 Supabase 云项目保留 1~2 周）。

**非目标**：不动前端服务器（ddctl.com 仍在美国）；不改任何业务逻辑；不做域名备案（本期搁置）。

## 四、执行步骤（Kimi Code）

### S1 连通性与环境摸底
1. SSH 登录验证 sudo 可用；
2. 复核内存/磁盘（前置条件表 #3）；
3. 安装 Docker + docker compose 插件（Ubuntu 24.04 官方源或阿里云镜像源均可，注意国内拉镜像可能需配镜像加速器）；
4. 腾讯云控制台防火墙（朋友配合）+ ufw：放行 SSH、443（或最终选定的接入端口），其余保持关闭。

### S2 部署自托管 Supabase（精简栈）
1. 拉取 supabase/supabase 官方 docker 部署（master 分支 docker/ 目录）；
2. **精简以适配 4G 内存**：禁用本项目未使用的组件——realtime、storage、imgproxy、vector/analytics（cloud.js 未使用实时推送与文件存储，先查代码确认无引用再禁，禁完不影响的功能名单写入修改报告）；
3. .env 关键项：
   - `JWT_SECRET` = **原 Supabase 云项目 JWT_SECRET**（老用户免重登的唯一机关，错一个字符全公会重登）；
   - 由同一 JWT_SECRET 重新生成 `ANON_KEY` / `SERVICE_ROLE_KEY`（HS256，role 分别为 anon / service_role）；
   - `POSTGRES_PASSWORD` = 新生成的强随机密码（与原云项目无关）；
   - `API_EXTERNAL_URL` / `SITE_URL` 按 S6 拍板的接入地址填；
4. 启动栈，确认 Studio、Kong、GoTrue、PostgREST 容器全部 healthy。

### S3 演练导出（旧库 → 本地文件）
1. 用运营提供的连接串 pg_dump 全量导出：**schema = public + auth**（含表结构、数据、索引、约束、RLS 策略、触发器；storage schema 本项目未用可不导，先确认）；
2. 优先 Direct 连接（IPv6 不通则走 Session pooler）；
3. 导出完成立刻出**行数清单**（每张表 count），与第三节基线比对并写入修改报告。

### S4 灌库与对账
1. dump 灌入自托管栈内 PG（容器内 postgres 角色）；
2. **逐表对账**：导出侧 vs 灌入侧，张张过、行行等，对照表写入修改报告；
3. 核对 RLS 策略已随库落地（pg_policies 抽查 9 张主数据表 + activities 等核心业务表）；
4. 核对扩展：pgcrypto、uuid-ossp、pgjwt、pg_net 等 Supabase 依赖扩展在自托管镜像中默认就位，逐个 `SELECT extname FROM pg_extension;` 确认。

### S5 超管与字典完整性
1. 重授超管：`update auth.users set raw_app_meta_data = raw_app_meta_data || '{"role":"superadmin"}'::jsonb where email = '564245086@qq.com';`
2. 抽查主数据内容：13 职业 / 40 专精 / S2 套装名 13 职业齐（如 战士=翡翠督军的统御、唤魔师=灾厄回响）/ boss_loot 无 zzz 类测试残留。

### S6 对外接入（HTTPS）
约束：前端 ddctl.com 是 HTTPS，浏览器混合内容铁律 → API 必须 HTTPS。
本期不备案，按朋友既有实践（db.ddctl.com:19832 自定义端口模式）执行：
- **默认方案**：DNS 加 A 记录 `api.ddctl.com → 101.35.124.22`（朋友操作），Caddy 反代 Kong，Let's Encrypt 自动证书，监听 **8443** 端口（避开未备案域名 80/443 被管控的风险），最终接入地址 `https://api.ddctl.com:8443`；
- 若运营/朋友拍板其他接入方式，以拍板为准并写入修改报告；
- 上线前 curl 验证：证书有效、/rest/v1/ 返回正常、国内多地延迟抽查（修改报告贴数据）。

### S7 前端切换（两行配置）
1. cloud.js 中 Supabase URL → `https://api.ddctl.com:8443`，anon key → S2 新生成的 ANON_KEY；
2. **先 localhost:5000 全量验收**（见第五节），全绿后再由运营将前端文件发布至美国服务器（发布方式照旧流程）；
3. **时机红线**：正式切换前做"最终导出"（重复 S3→S4），导出→灌库→前端切换**一气呵成不超过 30 分钟**，窗口期内通知运营暂停录入，丢失窗口期写入的风险由运营知悉确认；
4. 切换完成后，旧 Supabase 云项目**只读保留**，任何人不得再写入。

### S8 自动灾备
1. 国内服务器配 cron：每日凌晨 3:30 pg_dump 全量 → gzip → 推送至加州备份库（db.ddctl.com:19832，库名 wow_butler_backup，凭据运营私发）；
2. 推送后自动校验远端行数（抽查 3 张表），失败告警方式写入修改报告；
3. 本地保留最近 7 份 dump，磁盘占用纳入监控。

### S9 交付物
修改报告（按规范）：实际改动点 / 精简组件名单及理由 / 对账表（基线 vs 灌入）/ 接入延迟实测 / 切换窗口记录 / 台账登记（REQ-035 完成态）/ changelog 补录 / 回退预案确认。**未经验收不得提交 git。**
