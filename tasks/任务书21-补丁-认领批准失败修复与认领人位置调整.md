## 修正项 A（P1 逻辑 BUG）：审核/分配模式下，管理者「认领自己」被误拒

### 复现与根因（顾问侧探针已坐实，直接采信）

approval 模式下，会长（owner）点击认领自己的角色 → 提交申请 → 在审核区块点「批准」→ 报错 toast「批准失败：本公会认领需审核，请提交认领申请」。

探针复现矩阵（线上实测）：

| 操作 | 结果 | 判定 |
|---|---|---|
| approval 公会 owner PATCH raid_members {user_id: **自己**} | 403「本公会认领需审核」 | ❌ BUG |
| approval 公会 owner PATCH raid_members {user_id: 他人} | 200 | ✅ 正常 |
| viewer 直认领（approval） | 403 | ✅ 防线正常 |

根因：任务书 #21 WP2 在 server.js 认领窄例外里加了 claim_mode 判定——body ⊆ {user_id} 且 user_id=uid 的「认领形态」PATCH，在 approval/assign 模式下一律拒绝。**该拒绝发生在角色判定之前**：当 user_id=uid 时请求永远不会落入通用业务分支，于是 owner/editor 的管理权被短路；而 user_id=他人时不构成「认领形态」，走通用分支反而正常（上表第二行）。

### 修复要求

1. server.js 认领窄例外：approval/assign 模式下拒绝「认领形态」PATCH **之前**，先解析请求者在该公会的角色（复用 getGuildRoleCached，不新写查询）——
   - **owner/editor → 不落拒绝，放行落入通用业务分支**（通用分支本来就会再校验一次管理权，双保险）；
   - viewer/非成员 → 维持现状拒绝（文案不变）。
2. 前端（approval 模式）：owner/editor 点击「认领」时**不走申请弹窗**，改走与 free 模式相同的二次确认弹窗直接认领（管理者无需审核）；viewer 仍走「提交认领申请」。assign 模式现状（管理者编辑成员时指定）不动。
3. 审核区块本身不动；修复后「owner 批准他人申请」「owner 批准自己的遗留申请」两条路径都必须通。

### A 项验收（窄例外全矩阵重跑）

- approval：owner 自认领 200 落库 / owner 批准自己的 pending 申请 200 / owner 批准他人申请 200 / viewer 直认领 403 / viewer 申请 201 / viewer 代他人 403；
- assign：owner 自认领 200 / owner 代派 200 / viewer 全部 403；
- free：三模式回归（本人认领 200 / 解绑 200 / 代他人 403 / 夹带 403）；
- SEC-001 回归 + viewer-claim 回归 + npm test 全绿；测试数据自清理复核为零。
