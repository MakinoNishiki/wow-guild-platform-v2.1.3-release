# REQ-195 团员考勤前端交付与浏览器验收

日期：2026-11-16。状态：实现与隔离验证完成，待运营分块验收；未提交、未部署，未写生产数据。

## 本次行为

- 成员管理仍管理具体游戏角色。勾选主号、小号后点击「关联为同一团员」，选择已有团员或建立新团员并确认；同账号已认领角色仅提供勾选建议，不擅自合并。
- 新活动创建时将尚无归属的在队角色各自建立独立团员。考勤详情按团员显示一行，展开勾选实际参战角色。选任一角色自动正常出席；两个角色都参加仍只计一次。未上场的其他小号不产生额外缺席记录。
- 请假、缺席清除实际参战勾选；确实迟到、替补仍可由管理员标记本人。全部出席、批量标记复用原入口。
- 已保存活动保留当场名单，不把后来的新成员自动追记为历史缺席。「补入本场团员 → 加入本场名单」可明确补登，保存后才入库。未保存的角色勾选、补入名单和状态均受离开确认保护。
- WCL 预览将匹配角色按团员合并为正常出席。首次写入同时保留未参战团员的待核对缺席行，避免应到名单消失；重复同步可以补充同人的参战小号，手工修正得到保留。
- 后续改变角色关系不会改变已保存的团员快照。同份 WCL 再次同步优先使用活动内已有角色归属，避免一个历史角色计算为两人。
- 仪表盘、成员列表、统计报表提供明确「按团员（新活动）」和「按角色（历史活动）」口径选择，不能把两种分母混加。历史团员即使已无当前角色，仍依据活动快照出现在团员排行。
- 角色、拾取和装备获得者继续是具体角色，不改为团员。

## UI 审计与设计

前置审计见 `design-plans/req195-person-attendance.md`，依据用户成员管理截图和原页面控件。沿用现有暗色、金色主按钮、职业色和弹窗规范。关联弹窗限制 680px，字段使用现有 form-group；考勤保持原操作栏，角色通过折叠区展示。

界面新模块在 `js/personAttendance.js`，通过 `app.js` 既有渲染、保存、统计和 WCL 入口衔接。写入统一走 cloudCrud，回读确认团员归属、考勤状态及参战角色 ID 集合，失败保留表单；服务端权限仍是最终防线。

## 实际验证

运行 `scripts/verify-req195-ui.cjs`，真实 Chrome（headless）操作站内按钮、选择框与表单，读写隔离 Supabase。26 项通过，浏览器 pageerror 为 0。使用合成账号、公会和角色；WCL 响应为合成夹具，预览与确认按钮、数据库写入和刷新回读是真实链路，**不代表对线上 WCL 报告服务的再次实测**。

实际覆盖：

1. 成员管理勾选未认领主小号 → 关联团员 → 确认保存 → 读库归属一致。
2. 新建活动 → 两名团员/三个角色 → 勾小号出席 → 保存 → 刷新保留；再勾主号仍只一人一次。
3. 人工请假 → 注入保存失败 → 表单/按钮保留 → 重试成功，角色证据清空。
4. 战斗日志展开 → WCL 预览 → 确认写入：保留未参战团员；再次同步补入小号证据而不加人次；手工考勤不被覆盖。
5. 成员管理调整两个角色到新团员 → 重开原活动 → 重复同步 WCL，原两名团员与历史角色快照不变；统计仍显示历史团员。
6. 新增真正临时团员 → 原活动不自动追加 → 建立未关联团员 → 手动加入本场 → 勾角色保存，真实数据库新增一条本场团员考勤。
7. 旧角色活动打开、标记、保存，仍为 legacy；报表切换新旧口径、仪表盘口径延续，没有混合统计。
8. 新模型备份恢复、旧备份覆盖新模型公会均在写入前拦截，原数据不变。

## 本批边界与运营验收

- 旧活动保留旧口径，**历史转换预览/确认 UI 尚未开放**，不是已完成历史转换。服务端保留显式转换能力，不能用作前端已交付依据。
- JSON 导出保留；**团员关系与按人考勤备份恢复尚未开放**，新模型恢复和可能覆盖新数据的旧备份会明确拦截，不能承诺可直接导入恢复。
- 团员考勤依赖 SQL46 已迁移且数据读取成功；未就绪会提示，禁止错误创建为旧数据写入新默认模式。旧活动仍保留原编辑链路。
- 活动实际参战角色快照会按管理员更正更新，界面提示关系变化的历史角色属于当前已保存证据；本批没有新增一套完整操作版本审计查看器。
- 运营需在上线后分别验收：未认领主小号关联、任一角色参加只算一次、真实 WCL 换号合并、历史口径保留、临时团员后补。装备分配验收与本块分开记录，不能以隔离自测代替运营通过。
