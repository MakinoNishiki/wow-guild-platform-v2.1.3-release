# 家宅图鉴来源分类、万圣节装饰与图标统一调研

> 日期：2026-10-26 ｜ 方式：仓库静态资料核对 + 公开网页交叉查证 ｜ 未读取 `.env`，未连接数据库/服务器

## 结论摘要

1. “无来源”大批增加的直接原因已定位：原 2062 条旧目录已跑过 `source_text → sources` 结构化解析；后续 #76 导入的 251 条新家具数据没有 `sources` 字段，但 251 条的 `source_text` 均非空。图鉴来源筛选只读 `sources[].type`，所以这些条目无论卡片详情里是否显示了来源原文，都会被筛进“无来源”。证据来自本地数据快照及 `js/decorData.js` 的筛选实现。
2. 12.1.5 万圣节新增装饰，Wowhead 当前 26 项清单中本地新增集命中 25 项；本地缺 `record_id=26013` Scarecrow Pepe。另 `record_id=26880` 高耸的毒心雕像已有商人来源文字及一般节日/幽灵标签，但缺「万圣节」tag。需要确认官方客户端目录是否已有 26013，再按原插件链采集完整字段，不手工拼造整行。
3. 26 张 #82-Patch1 图标是按物品 `item_id` 找到的物品图标，不是家宅目录专属 `iconTexture`；实际 PNG 为 64×64 且金色品质边框已烘焙进图。225 张同批目录专属图标来自 `iconTexture`，原图为 400×400，再按原管线缩到 128×128。两者来源和像素细节不同，不能靠把 64px 放大解决。26 条都有 `asset_id`，可先用 wow.export 做少量模型静态预览试验，确定可读性后再批量替换；未实测前不宣称必定成功。

## 一、来源分类数据现状

### 旧目录 2062 条

- `scripts/decor/out/decor_catalog.json` 是 2026-09-17 采集的旧目录快照；配对 `scripts/decor/out/decor_sources.json` 后，`sources=[]` 为 76 条。
- 旧 `source_text` 为空 75 条；另 1 条为佩佩 `record_id=25546`，原文仅有两个地区，没有来源类型首键。#50 WP2 将该记录明确列为无法归类，未把地区猜成获取来源。
- #50 WP2 的旧语法解析覆盖 1987 条非空 `source_text`：1986 条已归类，1 条留待核实。它能区分 vendor/profession/quest/drop 等来源，也保留 festival_note 与 vendor 的并存关系。

### #76 新增的 251 条

- `data/decor-catalog-12.1.5-new-items.json` 有 251 条；JSON 每条均有非空 `source_text`，但对象不含 `sources` 字段。
- 来源文本粗统计：出现商人键 220 条、专业技能键 22 条、任务键 9 条、掉落键 8 条（跨类型可重叠）。这是原文键命中数，不代表互斥分类总数。
- `scripts/import-decor-batch.js` 按文件原样 upsert；不会自动执行 `parse_source.py`。#79 报告也记录这 251 条走裸 `source_text` 显示路径。
- `js/decorData.js` 的来源筛选和计数分别只查 `r.sources[].type`；当 `sources` 缺失或为空时计入 `none`。故这里是导入链未派生结构化字段，不是已经证明 AI 把 251 条来源判断错了。

### 节日筛选现状

- `DecorDict.SOURCE_TYPES` 已有 `festival_note`（UI 显示“节日”），旧美酒节记录被解析为 `festival_note`，同时保留一条或多条 `vendor`。
- 新万圣节来源语法未进入 #50 解析映射。现有新批中 25 条来自本地/公开清单对照；23 条 source_text 有 vendor，2 条是专业技能；12 条有“可在万圣节开始前购买”原文，11 条以物品 33226（Tricky Treat）标价。获取方式和节日归属是两个维度，补来源时必须保留 vendor/profession/achievement，同时给节日筛选可识别的关系，不能将这些获取方式抹掉。
- `tags` 是暴雪 Housing API 原样采集的目录标签，项目已有 BUG-108 勘定要求保留其来源语义。不得只为让筛选命中而擅改官方 tag；26880 缺 117 的情况需先对当前客户端值复核，并把节日归属作为来源数据关系处理。

## 二、万圣节新增对照

- Wowhead 的 12.1.5 Housing 更新页将 Hallow’s End 项目列为 26 项，包含 Scarecrow Pepe；其 Scarecrow Pepe 条目指向 Decor `record_id=26013`，物品页显示 item ID `282287`、来源为成就“A Frightening Friend”。
- 本地 `data/decor-catalog-12.1.5-new-items.json` 与旧 2062 条快照合计命中 25/26；旧快照不含这些 12.1.5 record ID。缺失项为 Scarecrow Pepe / `record_id=26013` / item `282287`。
- 本地已命中的 25 条中，`record_id=26880`（高耸的毒心雕像）缺 tag 117；其余 24 条有「万圣节」tag。是否应把该缺 tag 作为 API 数据异常回填，须先看当前客户端新扫描值，不能凭 Wowhead 分类直接改官方 tags。
- 公开 Wowhead 清单/条目是第三方交叉证据，不等同于当前国服客户端实时返回。暴雪官方 12.1.5 已知问题公告提到“若干新装饰的图标在商人处显示不正确”，但没有逐项点名，不能据此推断具体 26 条是哪几张。
- 旧目录里已有 5 件蛛网装饰带万圣节 tag 并有 vendor 来源；这说明“万圣节主题”与“只能在节日期间获取”不能混为一个事实字段。另旧美酒节样本表明 UI 当前的节日来源签可以与商人签共存。

## 三、图标差异与可行路径

| 集合 | 取数来源 | 本地源图现状 | 对结果的影响 |
|---|---|---|---|
| #82-WP2 225 张 | House Catalog `iconTexture` → CASC | 400×400 原图，项目入库 128×128 | 清晰、无物品品质金框，和既有图鉴素材一致 |
| #82-Patch1 26 张 | Wowhead item tooltip 按 `item_id` 反查物品图标 ID → CASC | 原始 64×64，金色品质框烘焙在图像内 | 显示更软，且风格像物品图标而非家宅目录图 |

26 条原始 House Catalog 记录缺少 `icon_file_id`，所以“直接重复 225 张的 `iconTexture` 提取”目前没有可用 ID。插件 `WoWButlerDecor` 现有白名单保存 `iconTexture`、`asset`、`uiModelSceneID`、source 与 tag，但没有 `iconAtlas`。推荐验证顺序：

1. 用当前客户端对 26 条同时探测 `iconTexture` 和 `iconAtlas`。若出现真实数字 `iconTexture`，直接复用现有 CASC PNG 管线；若只有 atlas 名，需证明可定位底图及裁切坐标后才导出。
2. 如果目录本身仍无可用 icon，优先抽 3–5 条（不同尺寸/类别）用对应 `asset_id` 从 wow.export 导出模型预览图，统一视角、背景、透明边缘与 128px 输出，再同现有图鉴卡片并排目视比较。
3. 试验通过后才处理剩余条目。模型预览使用独立的 record_id 映射/路径，不能把渲染图伪装成原 FileDataID PNG；保留 64px 物品图作失败回退，直到替代素材验收。

预期人工介入上限：若本地已有 12.1.5.70575 游戏目录，只需把插件更新到包含诊断字段的版本、执行一次 `/wbd scan`、`/reload` 并把 SavedVariables 文件放入项目约定的本地输入目录；不是逐件手动查图。模型批量处理、映射与校验应由脚本完成。此处没有运行客户端或导出模型。
