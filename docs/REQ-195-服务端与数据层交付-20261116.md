# REQ195 团员考勤：服务端与数据层

引用《开发规范》《问题与需求清单》《UI工作方法》，结构方案经2026-11-16运营确认。后续已获生产授权并完成结构迁移，默认legacy暂保旧版兼容，待候选139部署后执行46a启用；详见REQ-195-生产迁移记录-20261116.md。尚未提交、未部署应用。

## 实际改动

- SQL46新增公会团员、角色person_id与团员考勤。既有活动标记legacy，新活动默认person；原角色考勤完全保留。
- /api/people/ensure 为无归属在队角色各建一个团员，重复无新增；不自动合并同名/同认领者。
- /api/people/link 按明确选定角色关联团员，已有关系需确认；新团员用requestId幂等，响应丢失重试不重复建身份。
- /api/people/save 按活动+团员唯一保存考勤与参战角色快照。旧活动转换需显式确认；取消活动拒绝编辑。已有快照的角色即使后来归属变化或删除，仍允许保留原活动证据。
- 同活动的一个参战角色只能归属一个团员。服务端按本次拟保存与未被替换的旧记录共同校验，冲突整批拒绝；若确需纠正，须在同一批中从原团员移除证据、再加入新团员，避免角色改归属后重复计次。
- 角色离队、删除、恢复同步维护团员是否仍有活跃角色，避免空团员继续自动列入下一场。
- 所有写操作由cloudCrud进入；服务端每次核对owner/editor，SQL事务再次核验并锁定公会。普通成员只读，公会外不可写；通用代理与直连字段触发器防绕过。
- 两张新表分页读取；成员带person_id，活动带person_attendees/attendance_mode。旧结构功能门禁保留旧考勤。

## 数据不变边界

装备分配、心愿、认领与权限继续原角色/账号体系。关联团员不会自动认领或更改权限。原activity_attendance不在迁移中删除或重算；历史团员快照不随角色关系变化。
