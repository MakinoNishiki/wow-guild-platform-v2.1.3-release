## 背景与本次结果

运营真实团本中已导入4件装备，核对后停留在拾取表，没有当天活动，无法继续生成分配记录。原先“核对”仅确认拾取事实；现补上“转分配”，无需重填装备，也无需先补考勤。

流程：插件导出 → 导入并匹配 → 核对拾取 → 转分配 → 保存待分配或明确最终获得者 → 分配记录继续编辑。活动可稍后补关联。拾取人可能代拿，不自动填入最终获得者。

本次是现有拾取与分配模块的衔接，不宣称完成游戏交易自动采集。REQ-192掉落数量完整性提醒与延迟拾取自动关联仍待实现、真机验证。

## 实际改动

- 已核对的单件拾取显示“转分配”；已有分配显示“查看分配 · 状态”，修改同一条记录。数量大于1先提示核实，不错误转成单件。
- 带入名称、装等、难度、部位、图标品质和拾取证据。默认待分配，最终获得者为空。跨服同名显示服务器，通过成员ID保存。
- 活动可空；已有活动可选，后续创建活动后再补关联。分配记录中的首领允许人工补充，原始拾取首领保持不变。
- 复用loot_records.source_drop_id唯一约束和来源触发器，无新增SQL。服务端重新检查管理权限、来源/获得者/活动公会归属；普通成员可查看已有分配，不能创建或修改。
- 保存统一经cloudCrud和专用分配接口；已有来源的通用编辑被拦截。重复创建返回原记录，不覆盖已作出的决定。失败保留表单，保存期间禁用重复操作。
- 修改最终获得者时同步新旧心愿单；保存成功但响应丢失后的重试也补齐心愿标记。若同成员已有另一条同装备分配，不误取消其已获取状态。
- 删除分配保留原始拾取证据，可由管理者再次显式转分配；不把删除分配解释为删除掉落事实。
