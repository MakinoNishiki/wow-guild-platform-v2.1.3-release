## 二、账户链路现状

### 2.1 密码存储：**本项目不存密码，算法为 bcrypt（Supabase Auth / GoTrue 服务端）**

证据链：

1. 前端注册/登录/改密全部只调 Supabase Auth SDK，密码不出 SDK 边界：
   - 注册：`js/cloud.js:212` `client.auth.signUp({ email, password, options: { data: { display_name } } })`
   - 登录：`js/cloud.js:198` `client.auth.signInWithPassword({ email, password })`
   - 改密：`js/cloud.js:281` `client.auth.updateUser({ password: newPassword })`；当前密码校验直连 GoTrue token 端点（`js/cloud.js:263` `${supabaseUrl}/auth/v1/token?grant_type=password`）
2. 业务库无任何密码列：对 `sql/` 全部 40+ 个文件 grep `password|passwd|credential` **零命中**；user_profiles 表（`sql/01_tables.sql:174-181`，含 sql/25 的 tag_num、sql/27 的 preferences 增量）只有 nickname/avatar/settings/tag_num/preferences，无凭证字段。
3. Supabase Auth 底层是 GoTrue，密码哈希算法为 **bcrypt**（GoTrue 固定实现，cost 因子服务端配置，本项目不可见也无法降级）。

**结论一句话：密码不落自家任何表，由 Supabase Auth（GoTrue）以 bcrypt 哈希存储，前端与 server.js 全程只经手明文传输（TLS）而不经手存储。**

补充——密码入口强度（应用层，纯前端校验）：`js/app.js:1539-1553` passwordRuleError 要求 ≥8 位 + 字母数字混合 + 拦截 top-20 弱密码，三档强度条；注册/改密两表单复用同一套规则（`index.html:52`、`index.html:2048` 占位文案一致）。服务端下限对齐 GoTrue `GOTRUE_PASSWORD_MIN_LENGTH=8`（`js/app.js:1468` 注释）。注意：该校验是前端 JS，可被绕过直接打 GoTrue 接口，服务端仅兜底"≥8 位"。

### 2.2 注册 / 登录 / 会话恢复流程

- SDK 初始化：`js/cloud.js:47-54`，`createClient(url, anonKey, { auth: { autoRefreshToken: true, persistSession: true, storage: localStorage, storageKey: 'wow_raid_supabase' } })`。anon key 经 `/api/supabase-config` 下发（`js/cloud.js:33-35`）。
- 会话事件：`js/cloud.js:176-190` onAuthStateChange 监听 SIGNED_IN / SIGNED_OUT / TOKEN_REFRESHED；回调内不 await（防 auth 锁死锁，注释在 172-175）。
- 登出：`js/cloud.js:243-253` `auth.signOut()` + 清内存态 + 清本地缓存（`js/cloud.js:406` 清 `wow_raid_attendance_data`）。
- 改密后强制重新登录（REQ-096，`js/cloud.js:276-277` 注释 + app.js changePassword 走统一 logout 路径）。
- index.html 认证 DOM：登录表单（email+password，`index.html:25-36`）、注册表单（显示名+email+password，`index.html:41-60`）、公会表单（8 位邀请码 / 创建公会，`index.html:67-101`）。

## 三、四层逐项结论

### 3.1 session 机制

| 项 | 结论 | 证据 |
|---|---|---|
| 载体 | Supabase JWT（access_token + refresh_token）**明文存 localStorage**，key=`wow_raid_supabase` | `js/cloud.js:47-54` |
| 过期/刷新 | `autoRefreshToken: true`，SDK 自动用 refresh_token 续期；access_token 默认 1 小时（GoTrue 默认，本项目未覆盖配置的证据） | `js/cloud.js:49` |
| 取 token 方式 | 每次写操作 `getSession().access_token` 挂 `Authorization: Bearer` 调 /api/db 代理 | `js/cloud.js:66-70, 86-90` |
| 服务端校验 | server.js 调 GoTrue `/auth/v1/user` 验真（非本地验签），6s 超时 | `server.js:141-209` |
| 吊销语义 | 登出调 SDK signOut（吊销 refresh_token）；但 server.js 有 60s JWT 缓存，见高危项 H4 | `server.js:517-538` |

**结论**：标准的 supabase-js SPA 模式。代价是 token 对任何在同源页面执行的 JS 可读——XSS 即账号完全接管（含 refresh_token 长期接管），且全站无 CSP 兜底（见 H1）。

### 3.2 登录失败处理

- 前端：错误映射 `mapAuthError`（`js/app.js:1462-1474`）把 GoTrue 英文错误翻中文——"邮箱或密码错误"（不区分邮箱不存在/密码错，防账号枚举，良好）、"操作过于频繁，请稍后再试"（`js/app.js:1471`，覆盖 rate limit / too many requests）。
- **应用层零防护**：登录请求直连 Supabase GoTrue，不经 server.js，server.js 上不存在登录端点，自然无失败计数/锁定/验证码；前端也无失败次数限制（`js/app.js:1595-1635` handleLogin 仅做按钮防重复提交）。
- 唯一防线是 Supabase 平台默认限流（`js/app.js:1471` 的映射文案证明线上确实会触发），阈值由 Supabase 项目配置决定，本项目代码与仓库内无任何配置证据。
- server.js 内仅有的两个限流桶与登录无关：/api/track 60 次/分/IP（`server.js:374-399`）、/api/analytics/summary 30 次/分/uid（`server.js:417-445`）。

**结论**：登录失败处理 = 友好提示 + 依赖 Supabase 默认限流；应用层无锁定、无验证码、无审计日志。撞库/爆破的防护水位不可控、不可观测。

### 3.3 邀请码结构与校验层级

- **生成**：`js/cloud.js:1512-1519` generateInviteCode——32 字符字母表（`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，已剔除易混淆 I/O/0/1）× 8 位，`Math.random()`（**非加密安全 PRNG**）。熵 = 32^8 ≈ 1.1×10^12 ≈ **40 bit**。
- **存储**：`guilds.invite_code TEXT UNIQUE NOT NULL`（`sql/01_tables.sql:13`），一会一码，建会时生成一次（`js/cloud.js:501-507`）。
- **校验链路**：`js/cloud.js:529-563` joinGuild → `dbQuery('guilds', 'invite_code=eq.' + code)` 走 /api/db 代理 GET（service_role 读，绕过 RLS）→ server.js 放行条件仅"带 invite_code 或 id 精确过滤"（`server.js:668-671`）→ 命中后 INSERT guild_members role='viewer'（`js/cloud.js:550-555`）。输入前端转大写（`js/app.js:1803`）。
- **限速**：该 GET 通道无任何限流——/api/db 路径上不存在速率桶，且 JWT 验证结果缓存 60s，脚本化枚举的边际成本≈一次 HTTPS 往返。
- **无生命周期管理**：代码库全量 grep 证实 `guild_invite_codes` 表（`sql/01_tables.sql:31-41`，设计了 expires_at / max_uses / used_count）**在 js/ 与 server.js 中零引用，是死表**；邀请码无过期、无使用次数上限、**无轮换/重置入口**（grep `regenerate|重置邀请码|更换邀请码` 零命中）。泄露后唯一处置手段是解散公会。
- **附带观察（中危）**：`joinGuildById`（`js/cloud.js:566-600`，BUG-010 用户中心接受邀请路径）允许任何登录用户凭公会 UUID 直接入会（代理 GET `guilds?id=eq.X` 同样放行，`server.js:669`）——即"知道公会 UUID 即入会"，邀请码不是唯一入口。UUID v4 熵约 122 bit 不可枚举，风险低于邀请码枚举，但设计上绕过了邀请码语义。

**结论**：校验层级 = 前端大写化 → 代理精确匹配（唯一真实校验）→ viewer 落库。40 bit 熵在"无限速、无审计、不可轮换"三个前提下偏弱；死表 `guild_invite_codes` 证明曾规划过期/次数能力但未接线。

### 3.4 权限校验层级（三道防线各自防什么）

| 层 | 机制 | 证据 | 防什么 / 不防什么 |
|---|---|---|---|
| L1 前端 | `updatePermissionUI()` 给 body 加 `viewer-mode` 类隐藏编辑入口；`canEdit()` 判 owner/editor | `js/app.js:2149-2154`、`js/cloud.js:1593-1599` | 只防"误操作"，纯 UI 收口，浏览器改个类名即绕过——注释自承"真正防线在 server.js 代理鉴权"（`js/app.js:2149-2150`） |
| L2 代理 | `/api/db`：Bearer JWT → GoTrue 验真（60s 缓存）→ `authorizeProxyRequest()` 逐表逐方法鉴权（角色查 guild_members，120s 缓存）→ service_role 转发 | `server.js:1379-1446`（入口）、`server.js:653-890`（鉴权主函数） | **这是真正的写防线**。覆盖：公会归属解析 `resolveGuildIds`（`server.js:608-644`）、防自我提权（`server.js:696-705` owner 行只能建在本人公会、editor 不能作为入会角色）、viewer 窄例外白名单化（认领 `server.js:801-829`、claim_requests `server.js:835-857`）、主数据表仅超管 `app_metadata.role='superadmin'`（`server.js:784-790`）、未知表一律拒（`server.js:889`）、RPC 白名单仅 1 个函数（`server.js:1450`） |
| L3 RLS | 全部业务表 ENABLE RLS（`sql/02_rls.sql`）；读路径主力：公会成员可读、本人数据限本人（user_profiles `sql/02_rls.sql:263-275`）；SECURITY DEFINER 辅助函数三枚（`sql/02_rls.sql:8-43`） | `sql/02_rls.sql` 全文 | 防"anon key + JWT 直连 PostgREST"的越权读，是绕过 server.js 时的最后防线；文件末注释（`sql/02_rls.sql:278-281`）明言写操作不走 RLS（service_role 绕过），故写安全完全押在 L2 |

**结论**：三层分工清晰、L2 鉴权代码质量高（白名单制、窄例外字段级裁剪、缓存失效"安全优先于速度"注释 `server.js:510-516`），且有 30 场景回归脚本 `scripts/verify-authz.js`。结构性弱点在 L2 之外：token 存储形态（H1）、登录与枚举面无限流（H2/H3）、缓存吊销延迟（H4）。

## 四、高危项清单（按严重度排序）

### H1 【高】session JWT 存 localStorage × 全站无 CSP × 主应用无统一 HTML 转义 —— XSS 即账号完全接管

- **证据**：
  - token 明文 localStorage：`js/cloud.js:47-54`（`persistSession: true, storage: localStorage`），access_token 与 refresh_token 同仓。
  - 无 CSP：server.js 安全头仅 4 枚（X-Content-Type-Options / X-Frame-Options / Referrer-Policy / Permissions-Policy，`server.js:1162-1166`），全文件 grep `Content-Security-Policy` 零命中；index.html 亦无 CSP meta。
  - 转义面：`js/app.js` 有 **110 处 innerHTML** 且无任何集中转义函数（grep `escapeHtml|function esc` 零命中）；对照组 `js/dataPublic.js:142` 与 decorData 有自己的 `esc()`——登录后主应用反而是转义最弱的一层。用户可控输入（公会名、成员名、notes、display_name 等）入库后在多处渲染，存在注入面（本次未逐点验证，110 处 innerHTML 是暴露面而非已确认漏洞）。
- **影响**：任一存储型 XSS 得手 → 读取 localStorage 拿走 refresh_token → 长期完全接管账号，且可经 /api/db 代理以受害者身份写库（L2 认 token 不认人）。无 CSP 意味着内联脚本、外联脚本均无最后一道闸。
- **建议**（按性价比排序）：① 给 server.js 响应加 CSP（起步：`default-src 'self'; script-src 'self'`——项目已全量本地化、无 CDN 依赖，`index.html:13` 的 supabase-js 都是本地 vendor 文件，上 CSP 的工程阻力低）；② 对 app.js 的 innerHTML 渲染面做专项 XSS 审计，收敛出统一转义助手；③ 中期评估迁往 `supabase-js` 的 cookie/storage 自定义方案或缩短 refresh_token 寿命。

### H2 【高】登录/注册/邀请码验证三面均无应用层限流，全靠 Supabase 默认额度

- **证据**：登录直连 GoTrue 不经 server.js（`js/cloud.js:198`）；前端无失败计数（`js/app.js:1595-1635`）；mapAuthError 已有"操作过于频繁"映射（`js/app.js:1471`）证明限流触发依赖平台默认；server.js 全文件仅有的限流桶是 /api/track 与 /api/analytics/summary（`server.js:374-399, 417-445`），/api/db 零限流；邀请码验证通道 `GET /api/db/rest/v1/guilds?invite_code=eq.X` 对任何登录 JWT 放行且不限速（`server.js:668-671`），JWT 验证结果还缓存 60s（`server.js:531-538`）使枚举成本极低。
- **影响**：① 撞库/爆破的阈值不可控不可观测，无告警无日志；② 已登录攻击者可脚本化枚举 40 bit 邀请码空间（虽需约 10^12 次，但无限速+无审计意味着可长期低速进行），命中即泄公会 id/name/owner_id 并可直接以 viewer 入会；③ 注册端点同理可被批量注册。
- **建议**：① server.js 给 /api/db 的 GET guilds 分支加按 uid+IP 的滑动窗口限流（复用 trackRateLimited 的既有模式，工作量小）；② 在 Supabase 项目侧确认/收紧 Auth 限流配置并开启告警（运营操作，零代码）；③ 邀请码枚举附加审计日志（guild_id + uid + 时间，失败次数累计）。

### H3 【中高】邀请码终身有效、不可轮换，生命周期管理表是死表

- **证据**：邀请码仅在建会时生成一次（`js/cloud.js:501-507` + `1512-1519`）；无轮换/重置入口（grep `regenerate|重置邀请码|更换邀请码` 零命中）；`guild_invite_codes` 表（含 expires_at/max_uses/used_count，`sql/01_tables.sql:31-41`）在 js/ 与 server.js **全库零引用**；`Math.random()` 非加密安全 PRNG（`js/cloud.js:1516`）。
- **影响**：邀请码经 QQ 群/截图等渠道泄露后**无法吊销**，唯一处置是解散公会；与 H2 的无限速枚举叠加。另 PRNG 非加密安全，理论上有状态恢复风险（实际利用难度高，列为次要）。
- **建议**：① 加 owner 自助"重置邀请码"入口（PATCH guilds.invite_code，L2 已有 owner-only 分支，`server.js:682-689` 天然支持）；② 生成改 `crypto.getRandomValues`；③ 中期把 `guild_invite_codes` 表接线（过期+次数）或明确删表止损。

### H4 【中】JWT 缓存 60s / 角色缓存 120s 的吊销延迟窗口

- **证据**：`server.js:517-547`（JWT_CACHE_TTL=60s、ROLE_CACHE_TTL=120s）；注释自认"用户登出/删号后最长 60 秒内旧 token 仍被认作有效用户"（`server.js:511-515`）；经代理的 guilds/guild_members 写会立即清角色缓存（`server.js:1431-1433`），但**直接改库**（Supabase Dashboard 操作）的权限变更最晚 120s 生效；JWT 缓存无主动失效通道——服务端封禁用户（Dashboard ban）后最长 60s 仍可写。
- **影响**：权限收回/账号封禁存在最长 2 分钟的越权写窗口。窗口小、代码注释已知情，属可接受残余风险，但需在成本评估会议上显式确认。
- **建议**：维持现状可接受；若要收紧，给 /api/db 加一个管理端"踢人"接口（清指定 token/uid 缓存），或把 JWT 缓存降到 15-30s（代价是 GoTrue 调用翻倍，写延迟回升，与任务书 #10 的性能目标冲突，需权衡）。

### H5 【中】service_role key 明文存于项目根目录 .env，且有备份副本

- **证据**：`.env` 含 6 个 key（SUPABASE_URL / SUPABASE_ANON_KEY / **SUPABASE_SERVICE_ROLE_KEY** / WCL_CLIENT_ID / WCL_CLIENT_SECRET / DEPLOY_RUN_PORT）；根目录另存 `.env.bak-prerotate` 轮换前副本；`.gitignore:2` `.env*` 已排除 git（良好）；server.js 手写解析、系统环境变量优先（`server.js:28-47`）；另有 `loadEnv()` 用 python3 调 Coze workload identity 拉全量环境变量兜底（`server.js:76-115`），依赖机器上 python3 可用且凭证有效。
- **影响**：service_role key = 绕过全部 RLS 的全库读写权。任何能读项目目录的人/进程（含误打包、备份外发、其他服务同机部署）即拿到全库。这不是代码缺陷，是密钥管理成熟度问题。
- **建议**：① 确认 `.env.bak-prerotate` 等历史副本的留存必要性，不需要即删；② 密钥迁移到部署平台的密钥托管（环境变量注入），.env 仅留本地开发；③ 建立定期轮换纪律（已有轮换先例，把"删旧副本"写进轮换 checklist）。

### H6 【观察项】/api/supabase-config 公开返回 anon key + 已知公会 UUID 可绕过邀请码入会

- `/api/supabase-config`（`server.js:1204-1209`）返回 url + anonKey 无需鉴权——anon key 本就是公开凭证，配合 RLS 设计如此，**不算漏洞**，记录以消歧。
- `joinGuildById`（`js/cloud.js:566-600`）+ 代理放行 `guilds?id=eq.X`（`server.js:669`）= 知道公会 UUID 即入会。UUID 不可枚举，但公会 UUID 出现在通知、URL 等多处，实质是"邀请码不是唯一入会闸门"。建议产品层确认这是有意设计（BUG-010 邀请通知链路依赖它），并评估是否要求"必须存在指向本人的邀请通知"作为额外条件。

## 五、决策素材摘要（供成本评估会议用）

- **密码栈无忧，无需投入**：密码不落自家库，Supabase Auth（GoTrue）服务端 bcrypt 哈希；前端只做 ≥8 位+字母数字+弱密码黑名单的提示性校验。整改预算应为零，把资源让给 H1/H2。
- **最高性价比整改是 H1 的 CSP**：项目已全本地化（supabase-js 都是 vendor 文件），加一行 CSP 响应头即可砍掉 XSS 利用面的最大放大器；真正的硬骨头是 app.js 110 处 innerHTML 的转义审计（建议单独立项）。
