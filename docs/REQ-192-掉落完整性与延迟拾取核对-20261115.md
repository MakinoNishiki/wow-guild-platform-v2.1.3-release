# REQ-192 掉落完整性与延迟拾取核对

2026-11-15运营提出：首领实际掉4件，3件先拾取，另1件尸体内未捡；希望导入时提醒差异，由管理者决定是否继续。属于团队收官可靠采集块的补充，当前为方案与取证，未实现，不新增生产/schema授权。

## 已有证据

运营后续截图4条新记录入库，均344；前三条20:41首领盘卷祭坛，晚拾取21:06首领为空且服务器罗宁可见。用户确认补拾取、重新复制后正常提交。可确认1.0.6导出至线上提交本次通过；不能推定链接报错由少一件触发，也不能推定已有完整性闸门。现有采集依赖CHAT_MSG_LOOT、首领归属窗口180秒，晚拾取不能可靠关联原击杀。

## 用户方案

运营补充确认：晚拾取的是优等生（罗宁）的板甲腰带，对应截图21:06的「剧毒悔恨束带」、装等344、首领为空。此件作为延迟拾取关联的真实验收样本；不要与20:41另一名玩家拾取的同名腰带合并，也不能仅凭同物品ID去重。

按活动/首领/难度/击杀场次呈现：已观察掉落4件，已匹配拾取3件，1件尚未匹配；可查缺失装备与原因。管理者选择“返回继续拾取/稍后重导”或“仍提交已记录的3件”，不阻止先保存有效证据。普通成员可继续提交，不因差异获得最终分配权。

缺数据只能说“暂无法核实掉落总数”，不能显示齐全或凭团队人数/静态掉落池猜固定4件。已观察的清单也可能不完整，数量一致不证明整场齐全。比较应按物品变体与数量多重集合，不只比较总行数；战团绑定、排除物品、待识别物品分别说明，统一统计范围后再计算差异。

## 技术取证与边界

客户端接口文档提供C_LootHistory.GetSortedDropsForEncounter、GetSortedInfoForDrop及LOOT_HISTORY_UPDATE_ENCOUNTER/DROP事件，字段含lootListID、itemHyperlink、winner、allPassed。它可作为“观察到的掉落清单”的候选证据；中奖不等于已拾取，未中奖也不等于仍在尸体。必须在当前国服客户端实测：全放弃留尸体、延迟拾取、重载、同物品两件、不同难度与重复击杀。

不能未经验证假定lootListID跨客户端稳定；需要明确与击杀场次的组合键及有效范围。清单事件与实际拾取分开保存、导出，不能将掉落清单自动写为拾取或分配。迟到拾取优先核对未匹配清单，存在多个候选时交管理者选择，不能无限延长“上一个首领”时间窗口。网站不是实时连接游戏，提交页仅表示本次导出截止时的状态；补拾取后需重新导出提交，已有幂等逻辑保留。
