## ④ 结论

1. **guildReports 国内直连可行**：唯一可用直连域名是 `www.warcraftlogs.com`（OAuth 与 GraphQL 同域），单次 GraphQL 耗时 0.5~1.2s，属于可接受范围；`api.warcraftlogs.com` 与 `www.warcraftlogs.cn` 均 DNS 不可解析。server.js 现网实现已走 www 域名，无需改造。
2. **数据完备度够用**：单次 report 查询即可拿到 玩家列表（name/server/subType，server 字段直接是中文服务器名，可与 raid_members.server 对齐）+ fights（含 encounterID/friendlyPlayers，可算每个玩家的 Boss 战参战场次）——这正是 server.js report-summary 现有查询，证明「公会报告列表 → 选报告 → 考勤比对」全链路数据齐备。
3. **serverSlug 支持中文**：guildData 查询直接传 `serverSlug:"金色平原"` 命中，免维护 slug 映射表；返回体里另有规范英文 slug（the-golden-plains）可存档。
4. **guildReports 数据新鲜度取决于公会自身上传行为**：目标公会仅 3 份 2016 年公开报告。接口本身正常，但「按公会拉报告」功能的价值前提是公会持续上传公开日志；total 字段可直接用于「该公会暂无近期公开报告」的空态提示。

## ⑤ 决策素材摘要

- 直连方案定案：GraphQL 固定走 `www.warcraftlogs.com/api/v2/client`（与现网一致），不必引入代理或镜像域名；`api.warcraftlogs.com` 在国内 DNS 不解析，文档示例代码不可照抄。
- 延迟画像：token ~1.2s、单查询 0.5~1.2s；「公会报告列表 + 报告详情」两次串行约 1.2~2s，前端加 loading 态即可，无需缓存报告数据（与现网"报告数据不缓存"口径一致）。
- 成本画像：整轮（token+3 查询）≈3 点 / 3600 点小时额度，按公会维度做「选报告同步考勤」频次远低于限额，无配额风险。
- 公会定位免映射：guildData 的 serverSlug 直接吃中文服务器名，配合 serverRegion:"CN" 即可；worldData 回退分支可作为找不到时的诊断手段保留在脚本里。
- 空态必须设计：公会可能零公开报告或只有远古报告（本例 total=3 全是 2016 年），UI 需有「暂无近期公开报告」分支，建议按 startTime 提示最近一份的日期。
- 玩家匹配字段齐备：actors 的 name+server（中文）+subType 可直接复用 REQ-095 的 matchMemberByNameServer 匹配链，无需额外查询。
