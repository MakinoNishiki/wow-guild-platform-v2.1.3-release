# 12.1.5 家宅图标补齐与图鉴 3D 预览调研

> 调研日期：2026-10-26。范围：仓库静态资料、项目源码与公开一手技术资料；未读取 .env/密钥，未连接线上服务器或数据库，未修改生产代码。

## 结论摘要

- **已核实事实：** `data/decor-catalog-12.1.5-new-items.json` 共 251 条，其中 225 条有 `icon_file_id`，26 条为空。26 条全部有 `asset_id` 与 `model_scene_id`。这表示目录采集结果已带有可用于模型预览的关联字段，但尚未逐件验证模型可被导出、贴图完整或视觉匹配。
- **主要推断：** 当前插件白名单只复制 `iconTexture`，没有 `iconAtlas`；Blizzard 的 UI API 明确允许目录图标采用 `iconTexture` 或 `iconAtlas` 两种形态。因而“只采集 iconTexture”的字段链路很可能造成缺失。但尚未检查这 26 条客户端 API 原始返回值，不能把它写成已证实根因。
- **可自动化方向：** 优先让插件探针记录 `iconAtlas` 并与 `record_id` 配对；若缺失项确为 atlas，评估客户端 API 的 atlas 元数据/贴图解析生成静态小图；对于已有 `asset_id` 的记录，可测试 wow.export 从同一 CASC build 批量导出 GLB/预览 PNG，作为图标补齐备选。不要把价格中的货币图标误当家具图标。
- **3D 可行性：** 技术上可行，但与当前既有决策“图鉴一期不做 3D”冲突，应该单立小型验证任务/先做少量模型试点。推荐离线从 wow.export 导出 GLB，再用本地托管的浏览器查看器按需加载；不建议在访问者浏览器内直接接 CASC。

## 1. 当前项目链路与可核实边界

项目插件 `addon/WoWButlerDecor/WoWButlerDecor.lua` 的 `ITEM_FIELD_WHITELIST` 包含 `itemID`、`name`、`iconTexture`、`asset`、`uiModelSceneID`、`quality`、尺寸、分类、来源等字段；没有 `iconAtlas`。插件诊断计数也只统计 `iconTexture` 的缺失/数字/其他形态。转换脚本 `scripts/decor/convert_decor.py` 将 `iconTexture` 映射到 `icon_file_id`，不处理 atlas。最终 JSON 和表结构字段清单没有 `icon_atlas`。所以 atlas 在当前链路上无法进入输出数据。

`js/decorData.js` 用 `icon_file_id` 组成本地图标路径 `assets/decor-icons/{id}.png`，为空时走 `_placeholder.png`。既有报告记录：家宅数字 FileDataID 走 Blizzard render CDN 曾实测 10/10 返回 403，不能直接把装备 CDN 方案套到家宅目录。

来源：项目本地 `addon/WoWButlerDecor/WoWButlerDecor.lua`、`scripts/decor/convert_decor.py`、`js/decorData.js`、`docs/TASK-079-修改报告.md`；Blizzard UI 结构文档镜像 [HousingCatalogUIDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/HousingCatalogUIDocumentation.lua)，访问日期 2026-10-26。镜像为游戏客户端公开 UI 源码，不是 Blizzard API 开发者站点；字段定义应视为客户端实现证据。

## 2. 为什么可能缺失，以及怎样最少人工补齐

### 事实

1. Blizzard 客户端 API 的 `HousingCatalogEntryInfo` 将 `asset`（3D 模型）、`iconTexture`（纹理文件）和 `iconAtlas`（图集元素）分别定义；文档注明目录项应有 `iconTexture` 或 `iconAtlas` 之一，并且 `asset` 可能为空或因 UI ModelScene 不支持而为空。
2. Blizzard 自带目录 UI 在渲染时，先显示 `iconTexture`/`iconAtlas` 图标；没有图标时，如果有 `asset` 则用模型场景显示 3D 模型；两者都没有才使用问号。见 [Blizzard_HousingCatalogEntry.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_HousingTemplates/Blizzard_HousingCatalogEntry.lua)（访问日期 2026-10-26）。
3. 项目当前采集器和转换链仅保留 `iconTexture`，没有 atlas 字段。因此即使客户端返回 atlas，当前导出也会丢失它。
4. 26 条缺图记录都有 `asset_id`，但这只是数据关联事实，不证明特定模型的视觉预览或 icon 一定可导出。

### 推断与待实测

- **最可能的管线缺口（推断，中高可信）：** 采集器把 `iconTexture` 当作唯一图标入口，未保留 `iconAtlas`。验证办法是下一轮本机插件探针在所有记录中同时输出 `iconTexture` 类型和值、`iconAtlas` 字符串/空值，并把 26 个 record_id 单独汇总；禁止将来源价目里的货币贴图名当作家具图标。
- **暴雪端本来就未提供图标（可能）：** API 允许任一图标字段缺省，且当前数据采集来源/客户端 build 可能有未完成或特殊条目。需要实际查询对应客户端 API 才能区分。
- **CASC / CDN 未同步（未证实为本批根因）：** 之前 225 个有 ID 图标已能从当前 build 批量导出，而家宅 render CDN 有既有 403 证据。该证据不能证明无 ID 的 26 条在 CASC 中没有图像；它只说明“没有 FileDataID 可供现有脚本按 ID 导出”且 render CDN 不适合作兜底。

### 自动化路线（建议顺序）

1. **零猜测诊断：** 插件探针为 26 条输出 `{recordID,itemID,name,iconTexture,iconAtlas,asset,uiModelSceneID}`，保留 atlas 名而不只做分类计数。与本地 JSON 依 `record_id` 对齐。人工仅需在游戏内运行一次扫描、取 SavedVariables 文件；此步骤不需手工逐件查资料。
2. **若 `iconTexture` 是数字：** 复用项目 `scripts/decor/export_icons.js` 按 FileDataID 拉取、解码和校验；这是已验证成熟路径。
3. **若只有 `iconAtlas`：** 探索游戏客户端导出时附带 atlas 的 resolved fileDataID、裁切坐标与尺寸，或复用 wow.export 的纹理/图集数据生成裁切图。先对 2–3 个 atlas 样本做像素级/目视比对，验证缩放、边缘和透明度；只有名称且没有底图 ID/坐标时不能直接生成正确图片。
4. **atlas 仍不可还原时：** wow.export 以 `asset_id` 导出相应家具的 3D PNG 预览，作为静态图标后备。需要样本验证模型朝向、相机、场景背景、同名/同 asset 的映射；可批处理，不必手工搜索 26 次。
5. **最后才人工：** 若客户端既不返回可用 iconTexture/atlas 元数据，wow.export 也不能解析模型或映射有歧义，才对失败子集人工从 Wowhead/WoWDB 比对。仅凭名称或价格素材不可自动填 ID。

交叉比对样例：Wowhead 页面 [Runic Kyrian Reliquary（record 28569）](https://www.wowhead.com/decor/runic-kyrian-reliquary-28569) 展示 3D 与图片入口、名称和 12.1.5 信息；它是第三方二手资料，可用于人工图像语义抽核，不是暴雪官方数据事实。此轮没有逐条打开 26 个 Wowhead/WoWDB 页面，所以不声称已完成 26/26 的第三方图像核对。

## 3. 家宅图鉴拖拽旋转 3D 预览可行性

### 权威素材与格式

- [wow.export 项目及变更记录](https://github.com/Marlamin/wow.export/blob/main/CHANGELOG.md)记录：0.2.7 加入 3D WebGL2 查看器及 Housing Decor 浏览/导出页；0.2.13 增加家宅装饰分类筛选并修复模型加载/导出问题；GLB（glTF Binary）作为单文件自包含导出格式在 0.2.3 加入。项目当前本机版本/具体模型可用性仍应按样本实测；源模型格式可能含 M2/WMO 等游戏专有结构，导出 GLB 后再进入浏览器是较现实路线。
- Khronos [glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)定义 glTF 为运行时无关的 3D 资产交付格式，GLB 是二进制容器，适合将模型与资源打包。
- [Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader)可加载 glTF 2.0；[OrbitControls](https://threejs.org/docs/pages/OrbitControls.html)支持相机围绕目标旋转。备选 [Google model-viewer](https://modelviewer.dev/docs/index.html)原生支持 glTF/GLB、`camera-controls`、lazy loading 与 poster。两者均可实现鼠标拖拽/触屏旋转。
- 项目是 Vanilla JS、零构建；引入运行时须评审。Three.js 更灵活但需维护 viewer 与资源释放逻辑；model-viewer 上手更快但要确认本地 vendoring、浏览器兼容和体积。不要新增 CDN 运行时依赖；按项目政策若要采用，先评审并把依赖本地化。

### 推荐产品形态与性能边界

建议做**详情弹窗中的单模型预览**作为第一阶段，而不是把全部 2062 件模型同时塞进列表：点击卡片或明确的“查看 3D”操作后才下载该条 GLB；加载中显示现有图标/poster；关闭弹窗即停止渲染并释放 GPU 几何、材质、纹理；移动端支持单指旋转、页面纵向滚动不被劫持；无 WebGL/加载失败时保留静态图标。自动旋转默认关闭或仅轻微慢速，尊重减少动态效果偏好。

先对不同类型选 3–5 个样本（小物件、植物/半透明、家具/大型模型、异构模型各一）测 GLB 大小、首次加载、显存/内存、贴图完整度、外观语义、相机 framing；按懒加载与单模型同时活跃控制成本。若不能让导出的模型在浏览器与游戏目录预览基本一致，就停止扩大素材批量化。

### 权利/发布边界

暴雪 [EULA](https://www.blizzard.com/en-us/legal/simple/bfbbb648-bcc6-4b78-a5c7-e2fe20c135df/blizzard-end-user-license-agreement)将游戏内容及相关美术、模型等知识产权归于 Blizzard 或其许可方。公开一手资料不能据此推导“可以把抽取模型长期托管在本项目网站”。上线/公开分发前需项目所有者自行确认适用条款、非商业/粉丝项目政策和素材托管范围；本报告不构成法律意见。较低暴露的技术验证可限于本地开发环境，不把 GLB 上传到第三方云或公开仓库，直到政策确认。

## 4. 与项目既有决策的关系及建议任务拆分

任务书 #51 已记录“图鉴一期 3D 不做”；任务书 #51 补丁也把卡片 3D 按钮列为不做项，后续二期再评估。现有研究证明的是“有可行离线 GLB + 浏览器 viewer 技术路线”，不自动推翻产品决策。

建议新任务只做**样本可行性验证**：①新增插件探针字段 `iconAtlas` 输出并抓取 26 条诊断；②挑 3–5 个 `asset_id` 从同一 CASC build 导出 GLB；③本地静态页面/临时 harness 验证 viewer 旋转、模型完整和性能，所有文件放临时目录；④交付模型映射/体积/失败分类与权利风险结论。通过后再另立正式交互实现任务和产品决策。不建议现在直接把 26 个 icon_file_id 猜填或批量入库 GLB。
