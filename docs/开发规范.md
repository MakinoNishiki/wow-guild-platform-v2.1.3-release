# WoW Guild Platform 开发规范

> 版本：V1.0（基于项目交接总文档 V2.1.3 整理）
> 效力：本规范是项目开发的最高约束。任何人或 AI 工具参与开发，必须先读本规范；每份开发任务书必须声明引用本规范。
> 冲突处理：本规范与其他文档冲突时，以本规范为准，并回写修正其他文档。

---

## 第一章 数据流铁律

### 1.1 唯一数据流（DB-first）

```
用户操作
  → cloudCrud(dataType, operation, payload, options)
  → 写入 Supabase
  → reload（重新读取数据库最新状态）
  → 更新 appData 与 localStorage 缓存
  → render 页面
```

### 1.2 禁止事项

1. **禁止绕过 `cloudCrud()`**：任何数据写入不得直接调用 `saveCloudData()` 或其他底层函数。唯一例外：明确属于内部批处理的场景，且须在代码注释中写明原因。
2. **禁止直接修改 `appData.xxx` 后不同步数据库**。
3. **禁止在内部联动（如装备→心愿单）中循环触发完整 reload**：必须使用 `skipReload` / `skipCache`，批量完成后统一 reload + render。
4. **飞书同步等所有外围模块同样受 1.1 约束**，无例外（当前遗留问题，列入修复队列）。

### 1.3 数据原则

- Supabase = 唯一真实数据源。
- localStorage = 仅缓存，断电可丢。
- JSON 导入导出 = 仅用于备份/迁移。

## 第二章 安全与权限

### 2.1 密钥纪律

- `service_role` key 只允许存在于服务端环境变量，禁止出现在前端代码、git 仓库、文档、聊天记录中。
- 所有敏感配置走环境变量，禁止硬编码。

### 2.2 写路径鉴权（P0 整改方向）

- 凡经 server.js 代理使用 service_role key 绕过 RLS 的写入，代理层必须完成"用户 → 公会成员身份 → 角色（owner/editor/viewer）"三级校验，校验失败拒绝写入。
- 新增任何代理接口，必须先声明其权限要求，再实现。

### 2.3 数据库结构变更

- **禁止直接修改数据库结构**（含生产后台手改）。任何 schema 变更必须先提出并获确认。
- schema 变更以带版本号的增量 SQL 文件形式提交（含回滚说明），存放于 `sql/` 目录。
- **表结构单一事实源 = `sql/` 目录**。文档中的表结构描述如与 sql/ 不一致，以 sql/ 为准并修正文档。

## 第三章 修改纪律（每次改动必须执行）

### 3.1 修改前输出

- 修改文件清单
- 修改函数/位置
- 修改原因
- 影响范围与风险

### 3.2 修改后输出

- `node --check` 通过（涉及的所有 js 文件）
- 修改报告：实际改动点、验证方式、遗留问题
- 小步修改、小范围验证；单次改动不跨多个不相关模块

### 3.3 不允许的行为

- 任务书之外顺手加功能、顺手重构无关代码
- 大规模重写（单文件 SPA 的组件化按专项任务书逐步进行，方向：`pages/ components/ services/ store/`，短期不启动）

## 第四章 代码风格与架构约定

1. 前端为 Vanilla JS SPA，保持零构建原则；引入任何依赖或构建工具须先评审。
2. 新代码按模块边界组织：数据层（cloud.js）/ 业务逻辑（app.js 各模块）/ 渲染层；函数不再无条件全局暴露，新增代码优先局部化。
3. 样式遵守 DESIGN.md：暗色主题、CSS 变量配色、职业色、≤8px 圆角、768px 响应式断点。
4. 命名：数据表与字段用蛇形（snake_case），JS 变量函数用驼峰（camelCase）；禁止新旧命名混用（事故案例：`supabase` vs `supabaseClient`）。
5. 错误处理：用户可见操作失败时给出明确提示，禁止静默失败。
6. **弹窗防误关（强制）**：任何包含未保存编辑内容的弹窗，点击遮罩层/按 ESC 时不直接关闭，必须弹二次确认（"内容未保存，确定放弃吗？"）；无编辑内容的弹窗维持现状。实现统一走 app.js 弹窗控制区：打开时 `snapshotModalForm()` 快照、关闭走 `requestCloseModal()`；**所有新弹窗必须在 `modalDirtyChecks` 中登记"有未保存内容"判定函数**，判定函数应尽量覆盖弹窗内全部可编辑字段。
7. **弹窗层级（强制）**：全站弹窗一律走 `openModal`/`closeModal`，层级由 `modalStack` 弹窗栈统一管理——任何 openModal 都把该弹窗置顶（z-index 按打开顺序递增，基数 1000 步进 2），禁止个别弹窗写死 z-index。

## 第五章 版本与发布

1. **版本号唯一事实源 = git tag**；所有文档引用版本号以 tag 为准。
2. 每次发布必须有对应 RELEASE 文档：改动清单、验收结果、已知限制。
3. 环境分层：本地开发 →（测试用 Supabase 项目）→ 生产；测试与生产数据库必须分离。
4. 部署前四道门禁：开发自测（留证）→ 代码审查（checklist 全过）→ 验收用例表执行通过 → RELEASE 文档更新 + 打 tag。缺一不发。
5. **更新日志同步为发布门禁（BUG-021，任务书 #13 确立）**：任何提交前，更新日志必须按「新增功能 / 体验优化 / 问题修复 / 其他」四维分类填写，缺一不可提交。
